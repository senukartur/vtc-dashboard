VTC-007 owns generation and ordering. Coordinate one migration integrator across feature branches. Run root `pnpm db:generate`, review SQL plus snapshots/journal and check regeneration for drift. The initial `0000` migration contains only audit storage and indexes, explicitly using InnoDB/utf8mb4. VTC-013 adds two ordered additive migrations: `0001_mean_masked_marvel.sql` creates identity storage, then `0002_acoustic_starfox.sql` adds challenge stage and identity-epoch columns. Follow the [email replacement rollout gate](../../../docs/development/identity.md#email-replacement-rollout), including draining old identity processes and reissuing outstanding codes. Later domain schemas remain with their owners.

Use `pnpm db:migrate` explicitly, or `node node_modules/@vtc/db/dist/migrate-cli.js` from a production API artifact. Startup/install never migrate or seed. The runner uses the generated Drizzle SQL/journal and its own checksum-checked `_vtc_migrations` ledger with durable `applying`/`applied` state, on a dedicated locked connection. Never mix it with the upstream migrator or schema push.

MySQL DDL may implicitly commit. A failed migration remains dirty and refuses automatic replay; earlier DDL can persist. Follow the [partial-DDL runbook](../../../docs/development/persistence.md#partial-ddl-recovery-runbook), restoring a consistent backup or preparing reviewed forward repair. The separate synthetic recovery rehearsal is not production backup/restore proof.

VTC-150 Step 1 appends `0032_bizarre_iron_patriot.sql` after `0031`. Drain API and worker writers and verify a consistent backup before using the dedicated locked migrator. The migration adds the membership `joined_at` time and makes `display_timezone` nullable while keeping its `UTC` default and existing values. It adds four notification toggles, nullable trip-fact depot and raw company-code columns and nullable application referral columns with their checks. It also adds the admissions TruckersMP check table, which cascades with its application, and the `trip_owner_accepted_reporting` index. Each existing table changes in one statement and the check table is created with its key and index, so a fresh install runs few DDL statements. The `trip_facts` statement adds the columns and both depot foreign keys and rebuilds the table once with a table copy under a metadata lock, so its duration grows with the table. One DML transaction after the DDL backfills `joined_at` and two toggles. `joined_at` takes the later of registration and the latest return. An audited inactive-to-active membership change is the authoritative return. A reinstatement assignment counts only as legacy evidence when a membership change for the same user was audited within one second of it, so a general assignment with that purpose to an active member is not a return. VTC-140 reuses this rule. `review_queue` copies `trip_rejected` and `new_applications` copies `event_changes`. Both updates are deterministic and idempotent. The other toggles default to true, and older trip facts keep null company columns. The migration adds no grants.

Application rollback keeps the additive schema. VTC-140 re-derives `joined_at` with the same rule for reinstatements made after `0032` and before it activates, then writes it on every return. Reinstatements with no evidence keep the registration date. VTC-142 re-copies both toggles when it activates them, and VTC-144 adds runtime grants for the check table before activation. An interruption during DDL leaves the `0031` prefix intact and a sticky applying state. Restore the backup or apply a reviewed forward repair through the [partial-DDL runbook](../../../docs/development/persistence.md#partial-ddl-recovery-runbook). After the DDL, rerun the backfill block before following the same runbook for the ledger.
