# VTC-009 pull request CI

VTC-011 extends this baseline with a separate deployment rehearsal on PRs matched by the [path rule](#rehearsal-path-rule) and on the weekly or manual main run, and main-push-only production image artifacts, built alongside quality. Required CI requires both lanes and explicit main artifact success; PR artifact publication must be deliberately skipped. See the [deployment runbook](../operations/development.md) for the separate disabled-by-default protected workflow, trust boundaries and hosted acceptance. No app deployment/provisioning occurs merely because the quality workflow runs.

[VTC-009](https://trello.com/c/tgxPEMmP) adds [CI](../../.github/workflows/ci.yml) for every opened, synchronized, reopened or ready-for-review pull request, including drafts, and pushes to `main`. VTC-009 had no path filters; VTC-070 adds one owner-approved rule for the deployment rehearsal only (see [rehearsal path rule](#rehearsal-path-rule)). Stable job names are **Quality suite** and **Required CI**. VTC-010's [main ruleset](../../.github/rulesets/main.json) was applied on 2026-10-17 and read back with effective branch rules; the [review guide](review.md#evidence-and-remaining-gates) records the observed blocked failing PR and separate pending delivery gates. The file itself does not apply hosted settings.

## Parallel quality groups

[VTC-070](https://trello.com/c/mpb58k87) runs **Quality suite** as a matrix of legs, each on its own runner with its own image build and isolated stack: `core` (check, build, isolation and wrong-baseline proof, unit, contracts, failure-reporting), `integration`, `persistence-recovery` and `e2e`. Since [VTC-073](https://trello.com/c/AOO1luSe), `integration` runs in two shards and `e2e` in six (each e2e shard configuring all three projects, with per-case selection since VTC-071), so there are ten legs. VTC-073 passed the tools' own `--shard=<i/n>`. Since [VTC-080](https://trello.com/c/E5rjsbVu) the runner passes Vitest or Playwright an explicit file list packed by measured duration instead (see [shard weights](#shard-weights)). Measured before the change, integration took 356–484 s and the longest of four e2e shards about 520 s, so together they set the ~10 min Quality floor. Each leg runs `node scripts/test-ci.mjs --group <group> [--shard <i/n>]`. Only `core` runs `pnpm check`; the other legs skip it and still build. Together the legs run every lane, probe and proof of the former single job; `ciGroups` and its unit test keep that set equal to `all`. No lane, test or deadline was removed or added.

`fail-fast` is off, so every leg reports. `needs.quality.result` is `success` only when every leg succeeds; a failed, cancelled or skipped leg makes it non-success, and the unchanged `requiredCi` evaluator then fails **Required CI**. Each leg uploads its own fixed-schema `quality.json` as `quality-<group>-<leg index>-<run>-<attempt>`; the results are not merged, so read the leg that failed. Leg check names are `Quality suite (<leg>)`; the ruleset binds only **Required CI**, so the rename needs no ruleset change. Each leg has a 40-minute job budget and a 35-minute suite step.

### Shard weights

The tools' own `--shard` splits by file count, which left integration 1/2 80–170 s slower than 2/2 (hosted runs 41897676407, 41897925335 and 41880961375). The committed weights average hosted runs 41907368135, 41908817366 and 41910496311. Since [VTC-080](https://trello.com/c/E5rjsbVu), `laneShardFiles` in [`scripts/test-selection.mjs`](../../scripts/test-selection.mjs) lists the lane's files and `planShards` packs them greedily, heaviest first, each into the currently lightest shard (ties by file name and lowest shard index). The leg then runs that explicit file list. Weights are per-file milliseconds in [`scripts/test-shard-weights.json`](../../scripts/test-shard-weights.json). A file without a weight, such as a new test, counts as the mean of the known weights, so it still runs; stale entries are ignored. The plan is deterministic, and a unit test proves that for every shard count from 1 to 8 each file runs in exactly one non-empty shard, and that each file name passed to Vitest (substring filter) or Playwright (regular expression) matches only that file.

To refresh the weights, open the `Run isolated quality group` log of each integration and e2e leg of a recent successful run. After the stage lines it prints `<file>: <ms>ms` for every file it ran; e2e values are summed over selected projects, which are configured in the same leg. The same records are in `quality.json` as `fileTimings`. Use rounded averages over at least two runs: runner speed varies by 10–30 % between runs, and an integration file can take noticeably longer after some files than after others in the same process, so a weight is an estimate. A weight measures only the test run: allocation, image build and the e2e server start are per leg and do not depend on the files.

## Parallel rehearsal legs

The owner approved this split on 2026-11-04 ([VTC-072](https://trello.com/c/ZGeQiuFW)). It is based on the hosted profile of run 41806662228: core took 9m14s, the window 24m54s and recovery 1m58s. About two thirds of the window waits for real minute boundaries, so splitting the work is the only way to shorten it. **Deployment rehearsal** now runs as a matrix of four legs, each with its own runner, images, allocation and core group:
- `window 1-3`, `window 2-3` and `window 3-3` run `node deploy/development/test.mjs --window-shard <i>/3`. Each runs core and then its shard of window scenarios.
- `recovery` runs `--core-recovery`.

`windowShards` in [`rehearsal-child.mjs`](../../deploy/development/rehearsal-child.mjs) fixes the shards: `[2,3,5]`, `[4,6,9]` and `[1,7,8]`, balanced by hosted durations to about eight minutes each. Each shard keeps the original ascending order. Scenario 1 reads the whole feed from an empty cursor and leads its shard; scenario 4 relies on actor roles that scenario 5 later changes. A scaffold test proves that the shards cover every scenario exactly once.

Each window leg passes its list to the harness. The harness accepts a subset only for a disposable `vtc011-*` rehearsal project; hosted acceptance still requires all nine. The leg verifies that the fixture evidence, the final scenario and the window receipt name exactly that list. The default `node deploy/development/test.mjs` still runs core, all nine window scenarios and recovery on one allocation for local and manual use.

Trade-offs:
- Recovery now follows core directly, without a window before it on the same allocation.
- Core runs four times, which costs runner minutes but no wall time. The repository is public, so standard runner minutes cost nothing.

`fail-fast` is off, and `needs.deployment.result` is `success` only when every leg succeeds, so the unchanged `requiredCi` evaluator fails **Required CI** on any failed, cancelled or skipped leg. Leg check names are `Deployment rehearsal (<leg>)`. Group guards and every individual bound are unchanged.

## Rehearsal path rule

The owner approved this rule on 2026-11-03 (VTC-070), reversing VTC-009's "no path filters" for the deployment rehearsal only; Quality suite still runs on every PR. The **Rehearsal scope** job runs [`scripts/ci-scope.mjs`](../../scripts/ci-scope.mjs). On a pull request it diffs the merge candidate against its base parent. The rehearsal runs when a changed path matches what it exercises: `deploy/`, `third_party/` (vendored image libraries), `Dockerfile`, `.dockerignore`, any `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc`, `packages/{db,jobs,outbox,blob-storage}/`, top-level `apps/api/src/*` files (server, app composition, jobs and acceptance entries), `apps/api/src/platform/`, the identity, manual-reports, messaging and notifications modules, `ci.yml`, `ci-scope.mjs` and `ci-result.mjs`. Anything else skips it. A unit test pins the list.

The owner set the main policy on 2026-11-04 ([VTC-072](https://trello.com/c/ZGeQiuFW)). A main push skips the rehearsal. Since [VTC-074](https://trello.com/c/l2YfHUZK) (owner decision 2026-11-04) it builds the release artifact alongside Quality suite instead of after it, which saves about 2.5 minutes. **Required CI** still requires both, and the deploy workflow accepts only the artifact of a successful CI run (`requireRelease` in `deploy/development/policy.mjs`), so an artifact from a failed run expires unused after seven days. "Re-run failed jobs" after a failed Quality leg keeps the successful attempt-1 artifact; the policy then takes the newest artifact attempt of the run, so that run stays deployable. The strict ruleset requires an up-to-date branch, so the main tree is the merge candidate the PR already tested. That candidate was rehearsed only if the path rule matched it. Accepted risk (owner, 2026-11-04, "PR rule + weekly run"): a change the rule misses, or runner or image drift, can reach a deployable main artifact without a rehearsal. The weekly run only detects it and does not block or recall artifacts already built. As that safety net, a weekly `schedule` run (Mondays 03:17 UTC) and any manual `workflow_dispatch` on main run all four legs and publish no artifact. Their concurrency group includes the event, so a main push does not cancel them. The deploy workflow skips scheduled and dispatched CI runs; only push runs carry a release artifact. Any other event fails the scope job.

`requiredCi` follows a successful **Rehearsal scope** job: a pull request skips by the path rule and publishes no artifact, a main push skips and must publish the artifact, and a scheduled or dispatched run on main must rehearse and publishes no artifact. A failed, cancelled or missing scope result, an unexpected output, a required rehearsal that did not succeed, a rehearsal that ran on a main push, or a skip on a scheduled run fails **Required CI**. Widen the list when a new feature changes what the production image or the rehearsal exercises.

`node scripts/test-ci.mjs` without arguments still runs the whole aggregate in one stack for local equivalence checks.

## Execution and trust

`node scripts/test-ci.mjs` wraps the authoritative [isolated launcher](testing.md). It runs that checkout's check/build, allocation and wrong-baseline proof, all six lanes (unit, contracts, real MySQL integration, persistence, recovery, built-app Playwright journeys with central viewport selection), and existing assertion/failure-reporting proofs. It propagates the actual suite/cleanup exit code, without a second database bootstrap or migration changes. Node 24.22.2 / pnpm 12.14.0 / MySQL 8.4.11 images and strict SQL baseline remain pinned.

GitHub uses `ubuntu-24.04`. Before VTC-070 the single quality job had a 70-minute budget and a 65-minute suite step; each parallel leg now has 40 and 35 minutes, retaining the five-minute outer gap for bounded cleanup and reporting. PR/ref concurrency cancels obsolete runs. Hard cancellation, runner loss or Docker engine loss can interrupt cleanup; ephemeral hosted runners limit persistence but do not prove cleanup completed. Local interrupted runs may require the launcher's explicit owned-project recovery. Existing development resources are never reused.

VTC-036 gives the deployment rehearsal a 75-minute aggregate job budget for the required core, real-minute notification window and recovery groups. Separate local development measurements were core 876.925 seconds, canonical nine-scenario window 1,582.475 seconds and recovery 198.083 seconds: 44 minutes 17.483 seconds of group work, plus production build (111.614 seconds), operator build (6.054 seconds) and allocation/evidence/cleanup. These component measurements are not a completed default all-three-groups run or hosted acceptance. The unchanged group guards total 63 minutes 20 seconds (1,000 + 1,800 + 1,000 seconds); the outer budget leaves finite build/cleanup headroom. Individual worker, SQL, migration, lease, retry and operation bounds remain unchanged. The production artifact retains 20 minutes, and Required CI retains its names, dependencies and failure evaluator. Fresh exact-candidate CI and independent verification must still execute the complete default rehearsal. Since VTC-072, CI runs it as [parallel legs](#parallel-rehearsal-legs).

Independent local verification of `ca0728a6ae15302281c3d5155c735398b3b837cf` completed the unfiltered cached-dependency Linux quality equivalent in 3,001.274 seconds (50 minutes 1.274 seconds), with all lanes and cleanup passing. The 65-minute suite budget adds approximately 30 percent aggregate headroom to that measured run; the 70-minute job preserves the five-minute outer gap. This is not an ordinary GitHub CI result or a universal runtime prediction. The same candidate's required default deployment rehearsal failed at window entry after core passed, so quality success does not establish complete rehearsal or hosted acceptance. Fresh corrected-candidate verification, ordinary exact-head CI and separately authorized hosted proof remain required; no individual test or operation deadline was increased.

The quality token has only `contents: read`; checkout does not persist credentials. Quality/rehearsal code receives no repository/deployment secrets or write token. Actions use reviewed immutable commits supporting Node 24. There is no mutable dependency cache. Downloads happen during image build. Application test runtime networking is internal, without published ports or Docker sockets; children retain existing environment/schema-grant restrictions. The separate deployment operator rehearsal alone uses a Docker socket to allocate its owned resources. Ordinary `pull_request` runs the PR merge candidate without elevated `pull_request_target` execution. The protected deploy workflow uses its separately restricted environment and read-only Actions token.

The test image adjusts its unprivileged `node` account to the launcher's POSIX UID/GID at build time. Windows uses 1000:1000. An existing non-root GID may be reused: the image's `node` group can share that numeric GID with a base-image group. Newly created output mounts are therefore writable on Linux hosts whose user is not UID 1000. Root UID/GID are rejected. Build arguments affect only the disposable image. The [ownership profile checks](testing.md#runner-ownership-profiles) build the actual Dockerfile's small `runner-ownership` stage and exercise unprivileged writes on disposable Linux filesystems.

**Required CI** runs with `always()` after **Quality suite** and uses the tested `requiredCi` evaluator. Only explicit `success` passes; failure, cancellation, skipped, absent and unknown results fail. The one exception is a PR rehearsal skipped by the path rule, which the evaluator accepts only with a successful scope result. Critical jobs have no `continue-on-error`. A workflow that never starts produces no successful check. The applied rule binds that stable name to GitHub Actions app `15368`, with an up-to-date base and no bypass actors. In [fixture PR #17](https://github.com/senukartur/vtc-dashboard/pull/17), failed Required CI was observed with a non-draft, conflict-free, up-to-date PR reporting `BLOCKED`, zero required approvals and no unresolved threads. No merge was attempted. Administrators who can change the workflow retain the usual repository trust boundary.

## Safe diagnostics

The wrapper consumes and discards raw child stdout/stderr without retaining or printing them. It retains at most 64 fixed-schema stage records with allowlisted stage/status and bounded numeric exit/duration. Unknown lines, exceptions, configuration, payloads and extra stage fields are discarded. Stage events are advisory diagnostics; process exit determines success. This reduces disclosure but is not a universal secret detector.

The version-1 result also contains `browserFailures`, capped at 32 records. The dedicated Playwright reporter maps only committed spec locations to the fixed file identifiers in `scripts/browser-diagnostics.mjs`, the three configured Chromium project names, a line from 1 to 100000, and `failed`/`timedOut`/`interrupted`. Startup errors, no started tests and unmapped locations produce fixed global categories instead. A failed E2E stage without a valid reporter record receives `unreported-runner-failure`; its cause remains unknown. Both collection and report construction reject browser records containing unknown fields or values. Lines over 1024 characters are discarded. No titles, error messages, stacks, request data, arbitrary paths or URLs enter these records. The file/line identifies a test declaration, not necessarily the failing assertion. These bounded diagnostics do not determine the process verdict or prove a root cause.

Only the controlled qualification-promotion refresh scenario may add `scenario`, `phase` and `primaryPhase`, all from finite enums in the same module. Its one runtime annotation is updated before each awaited boundary. A body failure records its phase before `finally`; the current phase continues through release and persistence, so a cleanup timeout can be distinguished from an earlier failure. `primaryPhase: "none"` means no body exception was observed, not proof of successful execution. A completed cleanup can leave `phase: "complete"` alongside an earlier primary failure.

The reporter reads runtime `TestResult.annotations` only for the fixed `qualifications` file, inspecting at most 32 annotations and one relevant description of at most 512 characters. Unknown metadata and invalid/duplicate phase annotations fall back to the known coarse failure. Other annotation descriptions and optional source locations are not read or emitted. The reporter, collector and final report reconstruct and revalidate only the closed phase fields; older coarse records remain valid. This adds diagnostic provenance, not a functional qualification fix or an explanation of an earlier timeout. Test deadlines, retries, process verdicts and Required CI remain unchanged.

Since VTC-080 the result also contains `fileTimings`, capped at 128 records of exactly `lane` (`integration` or `e2e`), `file` (a committed test file name matching that lane's fixed pattern) and `durationMs` (an integer up to 24 hours). The Vitest reporter `test/support/file-timing-reporter.ts` and the Playwright safe reporter print them as `VTC_FILE_TIMING` lines; the collector and the report revalidate every field, and any other value is dropped. They are measurements for [shard weights](#shard-weights), not verdicts.

Since VTC-071 the result additionally contains `browserTimings`, capped at 4,096 records. Each record has exactly `spec` (the fixed identifier from `browserFiles` in `scripts/browser-diagnostics.mjs`), `project` (one of the three configured Chromium project names), and `durationMs` (an integer from 0 to 86,400,000). There is one record per executed case result, including failures/timeouts/interruption and excluding skipped cases; repeated spec/project pairs are intentional. The current policy enumerates 790 ordinary project executions, below the cap, and its regression checks the expanded selection remains below the cap. These identifiers disclose neither test titles nor arbitrary paths. The safe reporter never reads titles, errors or attachments for timings and prints `VTC_BROWSER_TIMING` lines; the collector rejects oversized lines (over 1,024 characters), invalid fields and excess records. The final report reconstructs/revalidates the closed records, and the console prints only those validated values. Chunked lines are reassembled within that bound. Existing per-file aggregation still feeds shard weights independently. Timing records are advisory and never change process exit codes, qualification-phase failure metadata, retries or deadlines. See the [coverage matrix](test-matrix.md) for counting and baseline comparisons.

The deployment rehearsal keeps child output private too. After evidence retention it prints one `deployment_rehearsal_timing` line (VTC-072), rebuilt by `rehearsalTiming` in `deploy/development/rehearsal-child.mjs` from the private window evidence: per passed scenario only its ordinal, start offset from the fixture start and duration (strictly ascending ordinals from 1 to 9, so a window shard publishes its own subset; each value an integer of at most two hours), plus the scheduler tick count and summed tick work seconds. Any malformed scenario record publishes nothing; run IDs, samples, worker metrics and other evidence fields never leave the runner. The line is a measurement, not a verdict.

Each invocation replaces `.local/ci/quality.json` with a newly generated fixed-schema result. The workflow uploads exactly that file, under a unique run/attempt name with three-day retention. `include-hidden-files: true` is required for this exact file under `.local`; no recursive `.local` upload is allowed. Missing reports fail the upload. Private `stack.env`, allocation JSON, Docker output, arbitrary errors, traces, screenshots and browser directories are never artifact inputs. Browser diagnostics remain ignored local output under `.local/testing`.

## Failure evidence and delivery gates

Run each explicit local negative check separately:

```sh
node scripts/test-ci.mjs --probe unit
node scripts/test-ci.mjs --probe integration
node scripts/test-ci.mjs --probe e2e
```

Each still checks/builds its own isolated stack, selects the existing deliberate assertion, verifies the exact `VTC008_*_ASSERTION_PROBE` diagnostic and real exit 1, and exits **1** after cleanup. The E2E probe additionally requires a safe `assertion-probe` record from every configured project and propagates those records into `quality.json`. The ordinary failure-reporting self-proof validates the same records privately without adding expected failures to a successful suite's result. An earlier allocation, server or guard error is `probe-not-reached`, never deliberate-assertion evidence. There is no workflow probe input or normal-suite bypass. Ordinary expected-failure self-proofs verify the harness; they are not red hosted CI demonstrations. Unit tests separately prove aggregate rejection and sanitization of synthetic secret-shaped output.
