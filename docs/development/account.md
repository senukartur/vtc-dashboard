# VTC-017 account lifecycle

[VTC-017](https://trello.com/c/GxOre5i3) adds RU/EN account workflows to the existing Yukon Union React shell. Product policy remains in [CONCEPT.MD](../CONCEPT.MD); [identity](identity.md), [admissions](admissions.md) and the [browser contract](../contracts/dashboard/README.md) own authorization, bounds and wire semantics. This adds no authentication method, schema, production activation or external provider integration.

## Routes and one-time links

`/login`, `/password-recovery`, `/password-reset` and `/invitation` are public account entry points. Every `/account/*` route requires a checked `/me`. Since [VTC-047](https://trello.com/c/2fuL2GdI) account settings have four deep-linkable sections: `/account/profile`, `/account/security`, `/account/connections` (shown only with `company.read`) and `/account/preferences`. Each is a real route with its own title, breadcrumb (Account / section), history entry and main-focus move; switching sections resets unsaved input. `/account` replaces itself with Security, and the fragments of the former single page land in their section (`#preferences` in Preferences; `#verification`, `#password` and `#email` in Security). Signing in lands on `/account/dashboard`, or returns to the protected same-app `/account` location (path, search and hash) whose Sign in link was used; any other or malformed return state falls back to the dashboard. Unimplemented destinations remain unavailable and the role-grouped sidebar is filtered by current capabilities. Trainee and Driver have equivalent member navigation; additive staff capabilities come from the server. Synthetic `/foundation` navigation remains separate.

Initial HTML sets `referrer=no-referrer` before resource references. Its synchronous script captures the reserved reset/invitation token into a non-enumerable memory handoff, replaces the current history URL with the canonical path, and discards all query/fragment data before React or resources run. Case and trailing-slash variants match the router. The API also sets `Referrer-Policy: no-referrer`. `main.tsx` consumes/deletes the global handoff before rendering. The mounted route copies it and clears the root handoff after mounting, including development StrictMode. Success clears the route token; disposal abandons feature memory. Reload/back cannot recover the scrubbed proof: reopen the original private link when needed.

GET never redeems. Missing, duplicated or malformed tokens get an unavailable screen. There is no public invitation-details endpoint, so the invitation screen claims no recipient, nickname or expiry. POST alone confirms creation. Expired, used and replaced invitations share request-another-invitation guidance. Redemption creates neither a session nor verified email; normal sign-in follows.

[VTC-046](https://trello.com/c/LmTefQDW) makes these entry screens compact without changing their semantics. They keep the public header with its language select. A single 360px form column is centred; from 1024px a static decorative brand panel (`aria-hidden`, project-authored road lines, the existing landing eyebrow and heading, no motion) sits beside it. Password fields have an in-field toggle with a fixed accessible name and `aria-pressed`/`aria-controls`; swapping the input type keeps value, name and autocomplete, and every submit masks the fields again. Sign-in puts "Forgot your password?" on the password label row, keeps submit last and links to the landing application section below the form. Recovery, reset and invitation start with a back-to-sign-in link. The invitation form lists the next steps already defined by the concept (password, sign-in, Steam verification); no expiry, nickname or password checklist is shown because no such data or live rule exists. Hints sit below their control, including on the Account page, which shares the form. API calls, errors, rate limits and success/unavailable states are unchanged.

## Session, transport and private state

The app owns one TanStack Query session boundary with checking, authenticated, anonymous/ended and unavailable states. Account entry, relevant commands, focus and online recovery revalidate the real `/me`. Initial public landing/previews do not initiate identity requests. `/me` and pending-email reads have a 15-second client deadline and external cancellation. Network/dependency failures hide account data and offer retry without asserting logout.

Private queries include the access generation; logout, identity switching, confirmed `/me` unauthorized and credential completion advance it, cancel private reads, remove all private DTOs and clear mutation history. Obsolete requests cannot restore another identity's data. Protected forms are disposed with the boundary. A wrong login/code 401 is handled locally, with a separate current-session check for protected commands; it never itself establishes session loss.

Writes use generated DTOs, strict runtime response validation, same-origin credentials, no-store, freshly requested current CSRF, explicit expected statuses, and no automatic retry. Bodyless writes omit JSON body/content type. Declared commands send UUID idempotency keys; preferences additionally send `/me`'s strong ETag as `If-Match`. Passwords, codes and tokens are absent from TanStack mutation variables/history, query keys, browser storage and errors. Attempts live only in feature memory, expire after ten minutes, and retain an immutable payload/key for explicit unchanged uncertain retries. Changed input starts another attempt. This lifetime is a client memory bound, not server proof-expiry policy. Client command deadlines are 15 seconds; timeout does not prove rollback.

Sign-out starts from the shell user menu (the More sheet on phones) or the Security section's Session row and hides private content while unresolved: main shows the sign-out status, the bell and user menu are hidden, and the banner language select stays available. A new access generation abandons the pending attempt, so an old logout cannot end a later identity's session. Only a committed logout response, or an independently confirmed invalid session, establishes anonymous state. An uncertain result offers retry and a session check. Server authorization remains authoritative.

## Preferences and protected changes

Saved language and IANA display timezone come from `/me` and live in the Preferences section as settings rows. Choosing another interface language saves it at once; the timezone is free text with runtime suggestions and an explicit Save. Each command sends the other preference's saved value, never an unsaved edit. Each row has its own status region (pending, then "Language saved" or "Timezone saved"); duplicate presses are ignored while a save is unresolved. The session-only language switch in the user menu and More sheet stays and is explained in the language row; it preserves recoverable inputs and does not change the saved choice. A stale preference 409 exposes explicit refresh-for-review, reloads authoritative values, and requires review/reapplication. Personal timezone never changes company reporting periods; an unset company timezone does not prevent preferences.

Verification requests show queued feedback, not a sent/delivered claim. The current email must be verified before password/email change: until then the Security section shows a notice with the verification request, and the email and password "Change" actions stay visible and focusable but `aria-disabled`, described by that notice and without a disclosure. After verification they become disclosures with fixed names and `aria-expanded`; a collapsed password panel stays mounted, so a requested code survives. A pending or unreadable email replacement keeps its panel open after reload. Password changes require the code sent to that verified channel and the existing 12–128-character technical password policy; login preserves its wider wire bounds. Completion ends all sessions and requires sign-in.

Email replacement follows both proof stages. Confirming the current-channel code returns **202 pending**; the original login address remains authoritative. `/me/email-change` discovers either stage after reload, with its current ID, proposed address and explicit expiry display. A new request replaces either stage. Only committed proposed-address confirmation completes replacement and ends sessions. Wrong, expired, replaced and taken-target proofs have generic feedback without address-availability disclosure. The UI has no administrative bypass.

Email request, confirmation and explicit refresh share a local interaction fence through the authoritative pending read. Both forms remain unavailable while a replacement command or its follow-up read is unresolved. An uncertain request also refreshes pending state before another proof can be submitted. A changed challenge ID clears the previous code; a recoverable wrong proof for the same ID preserves input for explicit retry. Read failures retain recovery controls without treating cached challenge data as current authority.

Connection status is the Connections section at `/account/connections`, reached from the account section navigation and the user menu (the More sheet of the bottom bar on phones). It shows Steam and TruckersMP rows and personal telemetry credential rows with dates in the display timezone, and requests nothing without `company.read`. No provider endpoint (TruckersMP linking, credential reissue) is fabricated.

## Verification and limits

`test/unit/account.test.ts` checks runtime/contract fixtures, early ingress, bounded reads, bodyless/CSRF/ETag transport, safe failures, immutable replay and canceled late-cache resurrection. Controlled `account.spec.ts` covers RU/EN forms, focused linked summaries, in-field visibility toggles, entry-screen layout and link order, mobile-menu restoration, links, session loss, preference conflicts, capability navigation, and the settings sections (deep links, legacy fragments, history, focus, the verification lock, disclosures, Security sign-out, row statuses, Connections and Profile rows, responsive layout and target sizes); captures contain only nonfunctional synthetic data. `account-real.spec.ts` uses built Fastify/admissions/identity and isolated MySQL/local-mail intents for rendered invitation/login/preferences/logout, verification, password/recovery and reloadable two-proof replacement. Allocation-scoped test keys and mail decryption stay in memory; there is no HTTP inbox/debug endpoint. Destructive journeys use fresh ordinary members, preserving bootstrap credentials. Real journeys disable traces/screenshots/video, use fixed failure categories and compare sensitive values as booleans.

Run `node scripts/test-local.mjs unit` and `node scripts/test-local.mjs e2e` in pinned Docker for development feedback. Delivery independently verifies the exact committed candidate with `node scripts/test-ci.mjs` and the packaged `node deploy/development/test.mjs` rehearsal, including account deep links/assets/early ingress/noindex/no-store/referrer policy. Actual results, rendered review, independent security review and CI belong to the delivery report/PR; these instructions claim none of them. Local queued mail is not real inbox delivery. Hosted activation, VTC-039 hardening, later modules and production acceptance retain separate gates.


VTC-038 links the account connection section and responsive navigation to the real [administration and connections workspace](administration.md), including personal telemetry one-show/revoke recovery and Steam/TruckersMP status; since VTC-044 the user menu and responsive navigation provide that link, and since VTC-045 phones reach it from the More sheet. Existing account challenge and protected email-change semantics remain unchanged.
