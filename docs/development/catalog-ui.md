# Catalog administration and selectors

VTC-020 adds `/account/catalogs` inside the authenticated member shell. Current `company.read` permits published search and history. Current `qualifications.manage` permits import, review, explicit mapping and publication, matching the [catalog API](catalogs.md). Catalog facts remain separate from qualification rules; this screen does not edit limits or infer launch configuration.

The existing Yukon Union dark surfaces, Huninn typography, blue actions, visible focus and the [compact control scale](ui-foundation.md#compact-control-scale) support a repeated staff job: inspect a maintainer-prepared update and publish the exact reviewed candidate. The first viewport contains game, current published revision and search. Review shows build, dated inventory, comparison revision, provenance, changes, coverage and publication gates. Native search/select fields and the existing Radix dialog supply keyboard and focus behavior. Responsive verification targets 390×844, 768×1024 and 1280×800 with RU/EN expansion.

## Compact layout (VTC-066)

This section supersedes the first-viewport clause above. The header holds the single h1, a status badge (published revision in use, or no published catalog; nothing while loading or after an error), the ETS2/ATS `SegmentedControl` named "Game" (it keeps the `game` URL parameter and resets revision and region) and a policy-backed description. From 1051px the layout has two columns: published revisions and upload/import (or the staff-only note) on the left, the candidate and published search on the right. Narrower screens use one column in DOM order: revisions, upload, candidate, search. On staff screens the first desktop viewport shows the game switch, candidate heading and meta, change summary, publication conditions and review tabs.

- **Revisions** are an xs table of import time (UTC) with the full ID. The first published row is Current and later rows are Replaced. An open unpublished candidate for the same game adds an Under review, Validated or Rejected row; it shares the page-level `["candidate", id]` query with the review, so it adds no request. Loading, error with Refresh, empty and Load more states are explicit.
- **Upload** keeps its logic. An `Import progress` list (Uploaded, Imported, Ready for review) derives done/current/failed/not-started states from the stored artifact and operation, using a glyph plus visually hidden text. Recover moves into its disclosure with the URL-recovery note.
- **Candidate** shows a state badge, meta, provenance disclosure, three change tiles (added/changed/retired) and four publication conditions. Every condition has a ✓/✕ glyph and text that states its status. Without a candidate, staff see guidance instead.
- **Review tabs** use the shared Radix tabs (Changes · n, Coverage with missing+failed count, Mappings with unresolved count, Translations). State lives in `CatalogReview`, so the change-type filter survives tab changes. Each table sits in a named, focusable horizontal scroll region with a 560px minimum, so the page never scrolls sideways. Panels show pending, error with Retry, None only after a successful empty page, and Load more.
- **Mapping** decisions open a dialog with one radio per explicit candidate and a required reason. Pending commands block Escape and outside clicks; success closes the dialog, refreshes review and announces the saved mapping.
- **Publication** keeps "Review publication" with `aria-describedby` pointing at a status line. The line either lists the unmet conditions in a fixed order (version mismatch, state, coverage, English, source review, mappings) or says that all conditions are met. The enable rule is unchanged. The confirmation names the game, build, candidate/version and expected pointer version.
- **Permissions**: without `company.read` the page renders only the h1 and a boundary notice and sends no catalog request. `company.read` alone shows revisions and search and sends no `/admin/` request.

The API has no data for these mockup elements, so they are omitted: rollback/republish, draft or rejected import history, revision names and per-revision builds, the "without Russian name" count, coverage check method, mapping source display names, operation timestamps and predicted pointer values.

## Published values

`apps/web/src/shared/catalog-selectors/` exports `CatalogSelector` and `{entityId, revisionId}` selection types. A consumer supplies game, published revision, kind, optional canonical region, selected value and change callback. Search text never creates data. Localized prefix search is debounced/cancellable and uses bounded cursor pages. The selected historical entity loads independently of active pages. Requested/rendered locale, English fallback and retirement remain explicit. Locale changes retain IDs. Incompatible game/kind/region/revision displays the retained historical value and an empty active selection. Consumers must validate compatible context before submitting a new form; filter changes must not silently submit the retained historical value.

Revision discovery returns the current pointer first, then historical publications. Optional `regionId` on `GET /catalogs/entities` filters the canonical region before pagination without changing unfiltered behavior. Foreign-game, absent or incompatible regions produce no matches. Signed cursors bind region, search, locale, revision and actor/session scope; changed filters start fresh pages. This does not establish production completeness or trusted aliases.

Queries use existing user/session-generation scope, private-cache metadata, no-store same-origin credentialed transport and runtime schemas typed against generated DTOs. Confirmed session loss clears private queries through the account boundary. Permission errors refresh current capabilities and hide failed query data. Privileged mutations are never optimistic.

Publication refreshes mutable candidate/review state before current-publication discovery. Pinned immutable entity pages are retained; a changed current revision creates fresh selector query keys. This replaces a nine-query invalidation burst observed in the synthetic publication/retirement journey against the API's five-slot fail-fast pool. The operation and publication pointer refresh on return; candidate review has an explicit refresh action and server ETag checks. This is scoped request-scheduling evidence, not a universal throughput guarantee or a production pool change.

## Import and review

Upload reads current policy and accepts one `application/json` file with browser-generated multipart framing. It displays returned artifact UUID, SHA-256 and byte length, plus import progress derived from artifact and operation state. Import is a separate command; its durable receipt is not publication. Validated operation/candidate UUIDs in the URL support authorized reload recovery. File contents and review reasons never enter browser storage or query mutation history. Operation polling pauses hidden/offline, stops terminally and refreshes on return. Failed, expired, unavailable and uncertain states offer safe recovery.

Child pages bind `reviewVersion`. Changes tables use the entity as row header (returned English label, else canonical ID) and list allowlisted `before → after` facts, retirement and change type. Coverage rows list returned pack states (Failed is distinct from import failure), contributions, reasons and public provenance. Translations list only changes that returned label fields, with English and Russian columns, an explicit fallback marker for a null Russian label, English completeness and the Russian fallback policy. The API has no complete draft search/list, full translation queue or label editor; maintainers correct, review and reimport a new exact artifact.

Mapping requires an explicit returned candidate UUID, preserved provider/map/source context and reason, chosen in the mapping dialog. Missing source/map/candidates, or a candidate that is no longer a draft, show "Reimport required" and direct maintainers to correct and reimport. Draft labels appear only when actually returned in diffs; otherwise canonical IDs are shown. Real mapping edits invalidate exact-artifact source review. An approved hash cannot authorize edited data; synthetic test mode is not production approval.

Publication confirmation identifies game, build, candidate/version and separate pointer version; the publish bar explains every unmet condition before confirmation opens. It requires candidate ETag plus `expectedPublicationVersion`, a reason, complete coverage/English/source review and no unresolved mappings. Only server success confirms publication. Conflict or missing-precondition responses close confirmation, invalidate review and require explicit refresh/new confirmation. Pending commands are locked; unchanged uncertain retries retain their logical key until explicit reset or confirmed result. Server retention is configurable and not exposed as a browser guarantee: after a long interruption, inspect operation/candidate/current publication before starting a fresh action.

## Evidence and boundaries

Unit tests cover selection context, runtime validation, locale-key parity, logical-attempt replay beyond sixty seconds and the pure review model: publication blockers equal the previous gate, import steps, revision rows, labels and values. Real MySQL cases cover duplicate labels across regions, filtering before keyset pagination, localized search, retirement exclusion, incompatible regions and cursor conflicts with representative synthetic `EXPLAIN`. Controlled browsers cover locale/ID stability, filters, mappings, review pagination, upload/uncertainty, permissions and dialog behavior, plus the compact first screen, tab keyboard order and counts, publication conditions, review tables, revision rows and states, request boundaries per permission and fine/coarse-pointer target sizes. `catalogs-real.spec.ts` exercises browser → built API → target MySQL upload, durable import, review, publication and historical display. Its worker is allocation-guarded test support, uses bounded passes and stops before closing its UnitOfWork. Real-auth traces/screenshots/video are disabled.

Run the pinned Docker launcher from [testing.md](testing.md): `node scripts/test-local.mjs unit`, `integration`, `e2e`, or all stages without an argument. Exact outcomes/candidate SHA belong to delivery and CI reports; this document does not claim future runs passed. Synthetic rendered captures stay in ignored local output. Actual source/dataset evidence and the [owner-approved source-use scope](../product/mvp-policies.md#catalog-source-use-basis) are documented with VTC-019. Current-candidate acceptance and downstream report/rule integration remain separate delivery/launch gates.
