# Durable in-app notifications

[VTC-036](https://trello.com/c/Cg1UNpek) implements the six existing browser operations, durable recipient state and bounded notification/reminder work. Delivery is opt-in: `NOTIFICATIONS_ENABLED=false` is the default. Enabling requires Identity, Trips, Qualifications, Events and Trip Decisions (including that module's prerequisites), migrations `0016_notifications` and `0017_event_notification_material`, the reviewed grants below and a separate random 32-byte lowercase hexadecimal `NOTIFICATIONS_CURSOR_KEY`. Apply `0017` before starting the current API or worker image, even when notification delivery remains disabled. No startup migration or production numeric configuration is inferred. [VTC-037](https://trello.com/c/qLXP57RC) provides the bell/history/preferences UI, visible/offline scheduling and cross-tab toast handling.

## Browser workspace and scheduling

Authenticated company members have a bell beside the language control and `/account/notifications`. The accessible popover previews the latest bounded window; the full page offers history pagination, individual reads, read-through and exactly six preferences. All/Unread filters apply to **loaded history**, not a server-wide unread search. The authoritative unread count comes from polling; an unavailable count is shown as unknown, never zero. RU/EN messages use a closed registered-key mapping with escaped display text and a generic unknown-message fallback. Relative times also show an absolute timestamp in the user's explicit display timezone. A null target keeps its entry with a generic unavailable/no-access explanation; the API does not supply a more specific reason. Qualification target IDs identify assignments, so navigation opens the existing game-specific qualification workspace rather than fabricating a member/details route. Application and member targets open their existing authorized workspaces.

One shell controller polls every 30 seconds after a completed refresh while visible and online. Hidden/offline transitions cancel the in-flight feed read and clear live toasts; visibility, focus and reconnect coalesce an immediate refresh on return. Catch-up is sequential with at most 25 pages per cycle, with immediate continuation when necessary. Poll, history and preferences remain separate private query namespaces. After catch-up, a bounded initial-window read re-projects current target/access state for the bell and queued toasts; its checkpoint is deliberately ignored so concurrent arrivals still pass through cursor catch-up. Active history and the shared upcoming-event query refresh as well. The nearest-event header remains independent of RSVP, reminder preferences and notification feature activation. Source-to-screen healthy delivery typically targets approximately 90 seconds; this is not a guaranteed maximum, and local accelerated workers do not establish hosted minute timing.

The checkpoint, history positions, CSRF material and private notification content live only in memory, scoped to member, session generation, identity epoch and effective capabilities. Read-through uses only an accepted poll checkpoint; an uncertain read-through retains its original checkpoint and idempotency key even beyond the generic ten-minute retry window and after later arrivals. Only a definitive result or scope loss clears that attempt. Invalidated signed poll cursors return 409; they have no clock expiry. An existing cursor gets at most one serialized silent no-cursor recovery read. A failed baseline returns to normal polling/error backoff even when an older result had `hasMore`. History cursor conflicts reset the complete infinite collection before reading a new first page. A rejected read-through clears/rebases the checkpoint and requires another explicit user action; it never automatically retries the write at a newer boundary. Individual read POSTs have no body. Preferences use PUT with all six flags, a strong ETag and a bounded command identity: uncertain retries preserve the same input/revision/key, changed input creates another identity, and conflicts require explicit reload/review. BroadcastChannel carries only a literal refresh hint. It never carries data, cursors or authority. Authorization failures immediately hide notification content/toasts and reconcile `/me`; a disabled/unavailable Notifications API does not imply logout.

Initial load, reload and history never emit live toasts. Only subsequent eligible, unread cursor-feed messages can claim one. A bounded 512-ID in-memory observation set also suppresses already seen baseline/replayed IDs before coordination. A Web Locks exclusive section coordinates a bounded localStorage list of at most 256 opaque notification UUIDs with ten-minute expiry; no identity, cursor or private display payload is stored. Claims wait at most one second, recheck current authority/visibility inside and after the lock, and fail closed to history-only delivery if coordination or storage is unavailable. Dismissing a toast does not mark its saved notification read. Successful refreshes revalidate queued toast projection/eligibility.

`test/unit/notifications-ui.test.ts` checks mapping, transport, command identities and atomic claims. Controlled `notifications.spec.ts` exercises browser scheduling, history/preferences/failure/session races, cross-tab claims and synthetic rendered RU/EN layouts. `notifications-real.spec.ts` uses the built API, MySQL, real Events producers and normal notification maintenance/queue handlers; API and worker use the same allocation-derived independent cursor key. Its synthetic 250-ms worker is test support only. Traces, automatic screenshots and video are disabled for these authenticated journeys; explicitly synthetic UI captures stay in ignored launcher output. Exact-candidate executed results belong in delivery/PR evidence. Shared feature activation, hosted HTTPS/minute timing and production readiness remain separate gates.

## Categories, access and preferences

All categories retain only a registered message key, nickname/game/event title where applicable, subject identity and revision. Reasons, evidence, mail/invitation links, source payloads and private provider identities never enter notifications or job references. The six existing preferences default to enabled; disabling a category suppresses pending/future delivery at effect time and preserves already saved history. It does not retroactively remove saved notifications or recreate effects skipped while disabled.

| Source / saved category | Recipient / current access | Preference | Freshness / identity |
| --- | --- | --- | --- |
| `trip.lifecycle_changed` / `trip.started` | Active company members; safe nickname/game only | `tripStarted` | Once per canonical start, supported source occurrence/receipt within 120 seconds |
| Same / `trip.finished`, `trip.cancelled` | Active company members; private trip target becomes null | `tripFinished` | Once per canonical terminal transition, same source gate |
| `trip.decision_changed` / `trip.rejected` | Author or current `trips.review` staff | `tripRejected` | Current immutable decision only; once per decision |

| `event.changed` / `event.start_changed`, `event.route_changed`, `event.cancelled` | Participants reconstructed immediately before the material change, with current active access | `eventChanges` | Still-effective material state; one effect per recipient/material definition |

Administrative inbox changes share `eventChanges` and trip review work shares `tripRejected` because the approved contract has exactly six preferences. No new wire field is introduced. Creation/title/description-only event edits, attendance, ordinary progress changes, rule/catalog publication, source snapshots and fact refreshes do not create additional user messages. RSVP changes maintain schedules without notifying unrelated members. A missing/unknown event version fails visibly instead of becoming a best-effort notification.

A later cosmetic definition does not consume or erase an earlier start/route update. Delivery classifies the immutable material revision against its immediate predecessor and requires its exact latest material-transition anchor; returning to an equal older value does not revive that older transition. Current projection uses indexed point reads, without a backwards history walk. Every 25-recipient continuation retains that material event's original change sequence and permanent effect identity, including after disabled delivery. A later signup cannot replace its audience. Current access and preferences still apply. A newer start, route or cancellation suppresses an obsolete corresponding live alert; saved history remains available. Poll/history projection batches the existing bounded page's material references against current safe title/game and state, so display labels do not become material identity.

## Transactions, cursors and current authorization

`notification_recipients` is the per-recipient lock and lossless signed BIGINT sequence allocator. Insertion, the sequence increment, queue effect receipt, continuation and job completion share one transaction. No checkpoint can pass an earlier uncommitted allocation. UUIDs, occurrence time and a global auto-increment are not cursor order. Permanent recipient/effect and job/event-consumer uniqueness prevent replay effects. Canonical group lookup also checks historical alias IDs before adding a start/end notification; reconciliation is not another lifecycle transition.

The initial poll returns the latest bounded visible window chronologically and a non-null current checkpoint even when empty. Catch-up advances ascending with `hasMore`; a completed page advances across hidden entries to the current committed checkpoint. History has its own signed descending namespace and always returns `liveToastEligible=false`. Cursors bind recipient, session, credential/access epochs, direction and filters; they never authorize a request. A poll checkpoint carries separate signed poll and read-through proofs for the existing `throughCursor` command. History positions cannot mark messages read. A read-through command cannot mark arrivals above its checkpoint. Individual reads are recipient-only and idempotent. Preferences use strong ETags and permanent command receipts; reused keys with changed input conflict.

Identity rechecks current session/membership/capabilities on every operation, including receipt replay. Worker capabilities come from the owning Identity facade rather than fabricated session actors. Items and unread counts share one relational access predicate. Removed staff permissions hide private items/counts. Expired, invalidated, old-access-epoch or no-longer-member-capability unread reminders are excluded. Already-read reminders retain safe history with `liveToastEligible=false` under current recipient/company access; event edits, RSVP, cancellation and time passing do not erase that history. Enabled composition invalidates unread reminder generations synchronously through a Notifications-owned facade. While delivery is disabled, Events records only its own pending generation; no notification/routing grant is needed. Items and counts use the same Events-owned correlated eligibility read predicate for unread reminders, so obsolete unread reminders are hidden immediately on re-enable even before maintenance. The narrow port accepts trusted typed query columns and runs within the already-authorized caller transaction; it exposes no user SQL or private response fields. Polling rechecks current event/RSVP eligibility and trip target access before serialization. Current canonical decision identity also suppresses stale rejection live alerts after reconciliation while preserving their historical record/access. A subsequent completion suppresses an already saved start's live flag.

Worker business reads hold Identity's shared company fence and use owning shared/current read ports, without creating missing qualification state or requiring business UPDATE privileges. Qualification eligibility reads the same current level/rule/totals semantics through SELECT/share paths; writer defaults remain unchanged. Events exclusively claims bounded pending markers before enqueue/acknowledgement because that is an owned mutation, avoiding shared-to-exclusive marker upgrades. Whole-transaction bounded retries still handle genuine transaction conflicts. Notification routing exclusively locks derived pending intents, then reads immutable outbox rows FOR SHARE; it never requires UPDATE/DELETE on immutable evidence.

## Source timing and reminder recovery

Trips supplies immutable provider, delivery mode, receipt and supported source time. A live telemetry start/end is eligible only when its verified actual `event` occurrence is not in the future and was received within 120 seconds. Its live expiry remains occurrence + 120 seconds; recent worker time cannot refresh backfill, unknown-clock or delayed evidence. Delivery backlog/poll age is checked again. Undated manual submissions never fabricate a live gameplay occurrence. Current terminal state suppresses a late obsolete start toast; source revisions and open refreshes remain one canonical effect.

Events owns its pending-notification marker, immutable definitions, response revisions and bounded recipient/eligibility facades. Each mutation keeps a pending marker; minute maintenance seeds at most 25 current event generations and acknowledges them transactionally. One reminder job is keyed by event/change generation, with current scheduling/participation checked again in each bounded 25-member page. Recipient effects use stable event/start/response identity. The saved immutable definition remains the original start-time anchor; cosmetic or route revisions at the same start do not recreate the reminder or invalidate its unread state, including while delivery is disabled. Start/status changes replace the schedule and invalidate obsolete unread reminders; decline/unanswered invalidates only that member. Cancellation, inactive membership, role loss and obsolete scheduling/participation cannot deliver or remain unread. Already-read records retain history under current access.

The technical scheduling grace is two minutes after the UTC due instant (`startsAt - 1 hour`), with event start as an additional hard expiry. It permits normal minute scheduling; it is not a new company participation rule. An outage beyond that window skips the missed reminder. Due/future queue indexes and the Events pending index bound steady work; there is no enumerate-every-event cron scan. Large fanout/chained work may need later minute invocations.

## Routing and old-producer compatibility

The first installed subscription uses indexed `outbox_routing` pending intents. Explicitly enabled composition injects an append-only outbox adapter that appends a closed-family intent for `notifications.v1` on the immutable event transaction. Enabled runtime producers need INSERT only on this derived table. Default-disabled producers append only immutable outbox events; the compatibility sweep recovers that interval after activation. Pausing delivery retains existing intents and jobs. No mutable global or environment read inside producers chooses routing behavior. Routing locks at most 25 pending rows in `(consumer,recorded_at,event_id)` order, validates typed envelopes, inserts permanent jobs and deletes intents atomically. Invalid known-family envelopes become visible failed jobs rather than blocking all later events. A rollback restores both sides; job event/consumer identities remain permanent.

A separate durable `outbox_routing_scans` primary-ID cursor repairs retained history and old/rollback producers. Every route scans at most 250 immutable outbox rows through the primary index, checks permanent jobs, and inserts missing intents with its cursor advancement on the same transaction. Reaching the end resets the cursor and starts another lap. A lower-ID uncommitted row passed earlier is therefore rediscovered after commit on a later lap: there is no permanent timestamp/ID high-water acknowledgement. Concurrent workers serialize the scan cursor and independently lease routed jobs. Already-routed history has bounded scan work rather than an unbounded anti-join. Current producer intents bypass the compatibility scan's history-dependent delay.

Migration is additive DDL only; there is no bulk history INSERT/SELECT, database trigger, privileged definer or global server-policy change. Recovery of old writers may take multiple minute runs proportional to retained history; it is not covered by the healthy current-producer 90-second target. Activation must inspect progress through a complete compatibility scan/catch-up before claiming historical completeness. Existing old versions may continue writing while paused/rolled back; re-enabled sweep recovery preserves their events. A recovered typed `event.changed` or `event.response_changed` first page also validates its immutable owning history and re-marks that Event for scheduling, on the same transaction as its consumer receipt. This repairs an acknowledged false marker preserved by a pre-0016 producer. Event marker ownership is acquired before shared Event history reads. The next bounded maintenance invocation seeds the current generation; this chained minute and history-dependent sweep delay are recovery latency, outside the healthy current-producer target. The original legacy subscription path remains unchanged for its existing fixtures. Any partial DDL remains sticky `applying`; use the existing [recovery procedure](persistence.md#partial-ddl-recovery-runbook).

## Material identity upgrade and repair

Additive `0017_event_notification_material` preserves the entire `0000`–`0016` prefix. Events owns a nullable, strictly decoded versioned JSON prefix: last inspected definition and latest start, route and status transition versions. Normal definition commands maintain all anchors atomically with their immutable revision/outbox, including while notifications are disabled. Cosmetics retain material anchors; combined start/route changes preserve the existing start-category precedence. Cancellation is terminal under the existing Events rules; this migration introduces no uncancel command. Reminder identity remains Event/start/response, independent of material notification anchors.

A virtual `(notification_material_pending,id)` index discovers missing, malformed or stale prefixes even when old consumer jobs are permanently complete and the reminder marker is false. It detects legacy producers that advance the Event without updating the derived JSON. One maintenance repair selects one pending Event and reads at most 25 contiguous forward definitions; delivery preparation can advance the same prefix in bounded chunks. Unknown state versions, invalid data and history gaps fail visibly. No migration bulk seed, backwards hot-path scan, trigger or privileged definer is required. Index construction still evaluates existing rows and must pass the ordinary DDL budget/recovery gates.

Closed prepare/deliver continuations accept exact legacy delivery references. Preparation owns Event X, advances at most 25 definitions and commits its continuation without recipient effects. Delivery reads current anchors with shared locks, retains the original material audience/cursor and commits at most 25 recipient effects. Its permanent user-effect identity is unchanged. A stale legacy prefix queues preparation; current page/history projection suppresses material live eligibility until repair is complete and retains permission-filtered history with current safe labels. The worker receives only `UPDATE(notification_material)` in addition to the existing pending-marker column right. Generated columns need no UPDATE privilege.

Existing or rolled-back producer history can require multiple minute passes; activation must inspect this indexed backlog and catch up before claiming healthy fresh-delivery timing. Disable notifications before rolling back to a worker that cannot decode the new closed phased references; retain immutable outbox/jobs and the additive `0016` and `0017` schema for forward catch-up. Old queued references remain accepted by the new reader. Do not clear sticky migration state or drop material columns to make rollback appear complete. Local upgrade/recovery evidence and separately authorized hosted application remain distinct.
