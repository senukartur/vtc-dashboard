# Durable in-app notifications

[VTC-036](https://trello.com/c/Cg1UNpek) implements the six existing browser operations, durable recipient state and bounded notification/reminder work. Delivery is opt-in: `NOTIFICATIONS_ENABLED=false` is the default. Enabling requires Identity, Trips, Qualifications, Events and Trip Decisions (including that module's prerequisites), migration `0016_notifications`, the reviewed grants below and a separate random 32-byte lowercase hexadecimal `NOTIFICATIONS_CURSOR_KEY`. No startup migration or production numeric configuration is inferred. VTC-037 owns the bell/history/preferences UI, visible/offline scheduling and cross-tab toast handling.

## Categories, access and preferences

All categories retain only a registered message key, nickname/game/event title where applicable, subject identity and revision. Reasons, evidence, mail/invitation links, source payloads and private provider identities never enter notifications or job references. The six existing preferences default to enabled; disabling a category suppresses pending/future delivery at effect time and preserves already saved history. It does not retroactively remove saved notifications or recreate effects skipped while disabled.

| Same / `trip.finished`, `trip.cancelled` | Active company members; private trip target becomes null | `tripFinished` | Once per canonical terminal transition, same source gate |

Creation/title/description-only event edits, attendance, ordinary progress changes, rule/catalog publication, source snapshots and fact refreshes do not create additional user messages. RSVP changes maintain schedules without notifying unrelated members. A missing/unknown event version fails visibly instead of becoming a best-effort notification.

## Transactions, cursors and current authorization

`notification_recipients` is the per-recipient lock and lossless signed BIGINT sequence allocator. Insertion, the sequence increment, queue effect receipt, continuation and job completion share one transaction. No checkpoint can pass an earlier uncommitted allocation. UUIDs, occurrence time and a global auto-increment are not cursor order. Permanent recipient/effect and job/event-consumer uniqueness prevent replay effects. Canonical group lookup also checks historical alias IDs before adding a start/end notification; reconciliation is not another lifecycle transition.

The initial poll returns the latest bounded visible window chronologically and a non-null current checkpoint even when empty. Catch-up advances ascending with `hasMore`; a completed page advances across hidden entries to the current committed checkpoint. History has its own signed descending namespace and always returns `liveToastEligible=false`. Cursors bind recipient, session, credential/access epochs, direction and filters; they never authorize a request. A poll checkpoint carries separate signed poll and read-through proofs for the existing `throughCursor` command. History positions cannot mark messages read. A read-through command cannot mark arrivals above its checkpoint. Individual reads are recipient-only and idempotent. Preferences use strong ETags and permanent command receipts; reused keys with changed input conflict.

Identity rechecks current session/membership/capabilities on every operation, including receipt replay. Worker capabilities come from the owning Identity facade rather than fabricated session actors. Items and unread counts share one relational access predicate. Removed staff permissions hide private items/counts. Expired, invalidated, old-access-epoch or no-longer-member-capability reminders are excluded. Enabled composition invalidates saved reminder generations synchronously through a Notifications-owned facade. While delivery is disabled, Events records only its own pending generation; no notification/routing grant is needed. Items and counts use the same Events-owned correlated eligibility read predicate over current definition/response, so obsolete reminders are hidden immediately on re-enable even before maintenance. The narrow port accepts trusted typed query columns and runs within the already-authorized caller transaction; it exposes no user SQL or private response fields. Polling rechecks current event/RSVP eligibility and trip target access before serialization. A subsequent completion also suppresses an already saved start's live flag.

## Source timing and reminder recovery

Trips supplies immutable provider, delivery mode, receipt and supported source time. A live telemetry start/end is eligible only when its verified actual `event` occurrence is not in the future and was received within 120 seconds. Its live expiry remains occurrence + 120 seconds; recent worker time cannot refresh backfill, unknown-clock or delayed evidence. Delivery backlog/poll age is checked again. Undated manual submissions never fabricate a live gameplay occurrence. Current terminal state suppresses a late obsolete start toast; source revisions and open refreshes remain one canonical effect.

Events owns its pending-notification marker, immutable definitions, response revisions and bounded recipient/eligibility facades. Each mutation keeps a pending marker; minute maintenance seeds at most 25 current event generations and acknowledges them transactionally. One reminder job is keyed by event/change generation, with definition and recipient response identities checked again in each bounded 25-member page. Definition changes retain RSVP, replace the schedule and invalidate old saved reminders; decline/unanswered invalidates only that member. Cancellation, inactive membership, role loss and old generations cannot deliver or remain unread.

The technical scheduling grace is two minutes after the UTC due instant (`startsAt - 1 hour`), with event start as an additional hard expiry. It permits normal minute scheduling; it is not a new company participation rule. An outage beyond that window skips the missed reminder. Due/future queue indexes and the Events pending index bound steady work; there is no enumerate-every-event cron scan. Large fanout/chained work may need later minute invocations.

## Routing and old-producer compatibility

The first installed subscription uses indexed `outbox_routing` pending intents. Explicitly enabled composition injects an append-only outbox adapter that appends a closed-family intent for `notifications.v1` on the immutable event transaction. Enabled runtime producers need INSERT only on this derived table. Default-disabled producers append only immutable outbox events; the compatibility sweep recovers that interval after activation. Pausing delivery retains existing intents and jobs. No mutable global or environment read inside producers chooses routing behavior. Routing locks at most 25 pending rows in `(consumer,recorded_at,event_id)` order, validates typed envelopes, inserts permanent jobs and deletes intents atomically. Invalid known-family envelopes become visible failed jobs rather than blocking all later events. A rollback restores both sides; job event/consumer identities remain permanent.

A separate durable `outbox_routing_scans` primary-ID cursor repairs retained history and old/rollback producers. Every route scans at most 250 immutable outbox rows through the primary index, checks permanent jobs, and inserts missing intents with its cursor advancement on the same transaction. Reaching the end resets the cursor and starts another lap. A lower-ID uncommitted row passed earlier is therefore rediscovered after commit on a later lap: there is no permanent timestamp/ID high-water acknowledgement. Concurrent workers serialize the scan cursor and independently lease routed jobs. Already-routed history has bounded scan work rather than an unbounded anti-join. Current producer intents bypass the compatibility scan's history-dependent delay.

Migration is additive DDL only; there is no bulk history INSERT/SELECT, database trigger, privileged definer or global server-policy change. Recovery of old writers may take multiple minute runs proportional to retained history; it is not covered by the healthy current-producer 90-second target. Activation must inspect progress through a complete compatibility scan/catch-up before claiming historical completeness. Existing old versions may continue writing while paused/rolled back; re-enabled sweep recovery preserves their events. The original legacy subscription path remains unchanged for its existing fixtures. Any partial DDL remains sticky `applying`; use the existing [recovery procedure](persistence.md#partial-ddl-recovery-runbook).

Delivery reports own actual results and candidate SHA; this document does not assert hosted acceptance.

The full deployment rehearsal's [restricted-role proof](../../deploy/development/notifications-grants-smoke.mjs) allocates a private run guard under its existing root operator. Before adding optional notification grants, its base runtime identity must fail direct notification/routing reads while normal Identity, Admissions and Events commands succeed with delivery disabled. The operator then applies only prepared grant deltas; separate runtime/worker phases prove enabled producer/read/preference work, disabled-interval catch-up, reminder delivery, duplicate passes and immutable-data/DDL denials. Vitest child processes receive no root credential. This disposable rehearsal does not apply hosted grants or activate a scheduler.

The [prepared grants](../../deploy/development/notifications-grants.prepared.json), [prepared Compose overlay](../../deploy/development/notifications.compose.prepared.yaml), [hosted application/acceptance/rollback procedure](../operations/notifications.md) and [HTTP polling probe](../../deploy/development/notifications-probe.mjs) are unapplied.
