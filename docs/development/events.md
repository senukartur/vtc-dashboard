# Events and voluntary participation

VTC-034 implements the Events backend APIs from [the browser contract](../contracts/dashboard/openapi.json) and [CONCEPT.MD](../../CONCEPT.MD), scenarios 1, 2, 5, 14, 20–22, 30, 31, 33 and 39. The [VTC-035 workspace](event-workspace.md) provides rendered RU/EN event workflows; VTC-029 owns trip adjudication; VTC-036 owns subscriptions, notifications and reminders. Source integration does not activate a hosted service or apply a live migration.

## Activation and routes

Events is disabled by default. Set `IDENTITY_ENABLED=true`, configure identity as documented in [identity](identity.md), then set `EVENTS_ENABLED=true` and an independent cryptographically generated 32-byte lowercase hexadecimal `EVENTS_CURSOR_KEY`. The key must differ from identity, mail, admission, catalog, trip, qualification, telemetry and manual-report keys. Missing/invalid enabled configuration fails startup; disabled Events mounts no routes. Local Compose passes both Events settings. API composition installs the owning service without a notification subscription or worker. Catalog selections additionally require the enabled catalog adapter and published same-game facts; null selections can operate without catalogs.

| Route | Access and result |
| --- | --- |
| `GET /api/v1/public/events`, `GET /api/v1/public/events/:eventId` | Anonymous; explicit public DTO, members-only detail is 404 |
| `GET /api/v1/events`, `GET /api/v1/events/:eventId` | Current `company.read`; both visibility classes |
| `GET /api/v1/me/upcoming-event` | Nearest scheduled accessible event, independent of RSVP, or null |
| `GET/PUT /api/v1/events/:eventId/my-response` | Current `events.respond`; own private reason only |
| `GET /api/v1/events/:eventId/participants` | Current member; participating members' safe summaries only |
| `POST /api/v1/admin/events` | Director/deputy `events.manage`; 201 |
| `PATCH /api/v1/admin/events/:eventId` | Full EventInput replacement under definition ETag |
| `POST /api/v1/admin/events/:eventId/cancellation` | Private nonblank reason, immutable cancellation |
| `GET/PUT /api/v1/admin/events/:eventId/attendance` | Director/deputy; collection ETag, private RSVP reasons and latest staff notes |

Browser mutations require the existing authenticated Origin/CSRF policy, JSON content type and UUID idempotency key. Commands except creation require strong `If-Match: "vN"`; omitted precondition is 428, malformed input 422, stale version 412, conflicting idempotency input 409. Dispatcher alone cannot manage events or read others' reasons. Public serializers exclude participants, attendance, member visibility, load prescriptions and private notes. Public event existence is filtered before detail serialization; list pagination never includes private rows.

Event input includes game, server, organizer display text, description, route and meeting location text, canonical city IDs, meeting/start/end instants, visibility and optional prescribed cargo/mass/trailer IDs. Display text never becomes identity. UTC dates must be canonical millisecond `Z` instants, calendar-valid, with meeting <= start and supplied end >= start. Technical string/batch/page limits are transport/storage bounds, not company business policy. Exact nonnegative mass fits DECIMAL(38,18) and canonical decimal wire form. The event's command actor is server-derived and distinct from organizer display text.

Lists have bounded chronological keyset pages, start-time/UUID tie breaking and `period=upcoming|past` (default upcoming). Signed cursors bind visibility, period, actor/session/access epoch and a fixed UTC period boundary, preventing a moving clock from changing the next page's period. Participant and attendance pages bind event and their own scope; attendance pages also bind collection version. Tampered/cross-scope cursors fail 409. Current access is rechecked even with a valid old cursor. Rescheduling can change live list ordering; cursors are not a frozen snapshot of all event content. All instants remain UTC across DST; VTC-035 renders user timezone labels.

## Transactions, versions and immutable history

Every command locks company, sorted actor/target members and current session through Identity's owning `eventContextInTransaction` facade, then event/current child state and its durable command identity. No Events query reads Identity tables directly. The company lock serializes current access and commands; this favors correctness for the single-VTC MVP over independent per-event write throughput. Authoritative time is sampled after those locks. The shared bounded transaction retry retries only classified MySQL deadlock/lock-wait errors after explicit rollback. An uncertain COMMIT remains uncertain and is never automatically retried; a later caller retry with the same key consults the durable receipt and current authority.

Definition version, each member's response version, and attendance collection version are independent. The unanswered initial response is version 1; its first change is version 2. A response never changes the definition ETag, another member's response ETag, or attendance ETag. Attendance GET/PUT share a collection namespace beginning at 1. A repeated equivalent response produces no extra response history, audit or outbox effect. Repeated explicit attendance decisions are retained as new staff decisions. Every effective mutation advances a separate per-event change sequence, used for ordered history and later consumers.

RSVP accepts unanswered, participating, or declined with a nonblank private reason. At `now == revised startsAt`, RSVP closes and actual attendance opens. A later start reopens response editing and preserves prior answers; an earlier start closes it using the revised value. Cancellation closes response/attendance mutation and excludes the nearest-event result. Unanswered or non-attending members receive no automatic penalty. Staff actual attendance is separate from RSVP, accepts 1–100 distinct known members atomically after start, and retains actor, time and private note.

Migration `0011_tearful_infant_terrible` adds eight owned tables: current Events/Responses/Attendances, immutable definition/response/attendance revisions, immutable catalog pins and permanent command references. Published `0000`–`0010` bytes stay unchanged. UTC datetime(3), binary application IDs, exact mass and restrictive event/member/catalog foreign keys preserve history on account departure. Current revision pointers and response aggregate IDs are validated by the transactional service rather than cyclic foreign keys: definitions, response and attendance revisions must belong to their current event/member, and current pointers are assigned in the same transaction. There is no deletion API or history cleanup. Treat direct runtime history writes/deletes as outside this facade's contract.

Creation uses a server-generated UUID. Durable command uniqueness is actor + route + target discriminator + key; creation's target discriminator is the client key, other routes use the event ID. Independent administrators can reuse a key without sharing event IDs. A keyed canonical fingerprint covers precondition and input without storing private reasons in ordinary command results. Exact replay reconstructs the original DTO from immutable definition/own-response/own-attendance references and returns its original version. Current permission/session checks still precede replay. Receipts contain safe IDs/versions only; private reasons/notes remain exclusively in owned history. Domain, history, safe audit, receipt and outbox share one caller transaction and roll back together.

## Catalog and integration facades

`Catalogs.eventReferencesInTransaction` validates at most four same-game selections against the current complete published catalog, with exact kind and non-retired fact checks. Events stores immutable fact/entity/catalog-revision foreign-key pins and original safe labels; later publication or translation changes do not rewrite them. Unknown kinds/games/IDs fail 422, and non-null selections without an adapter fail 503. No production catalog coverage or source licensing claim follows from synthetic fixtures.

The service exports these bounded owning seams:

- `history(actor,eventId,afterSequence,limit)` requires current event management and returns immutable private definition/response/attendance streams plus `nextAfterSequence` for each stream. `afterSequence` is exclusive (initially 0); `limit` is 1–100 definitions, responses or complete attendance decision batches per stream (default 25). Each stream selects one extra entry/batch only to detect continuation; lookahead rows are not returned or consumed. A non-null stream continuation is the last emitted sequence: pass it as `afterSequence` for that stream's next page; null means that stream is exhausted at this read. Paginate streams independently rather than taking the maximum sequence across streams. Attendance first selects bounded distinct sequences, then returns every revision for those sequences, ordered by sequence/revision ID; the command's 100-member batch bound limits each page to `100*limit` attendance rows. History reads retain current authorization and the event lock across selection and fetch. No public browser history endpoint is introduced here.
- `definitionInTransaction(tx,revisionId)` returns safe immutable identity/version/start/status/change-order facts. `generationInTransaction(tx,eventId)` separately locks and reads only the current safe definition identity/version/start/status/visibility/change sequence so a later consumer can fence cancelled or superseded generations; it exposes no private content.
- `recipientsInTransaction(tx,eventId,changeSequence,afterMemberId,limit)` uses a latest-prior-revision SQL anti-join and member keyset to reconstruct participating recipients immediately before a definition change. It returns only member IDs, at most 100. Future consumers must recheck current membership/resource access at effect creation/delivery/read.
- `associateInTransaction(tx,actor,{eventId,memberId,game,eventRevisionId?,attendanceRevisionId?})` participates in a caller transaction and permits the owner or current trip reviewer/event manager. It validates access, same game, event revision membership and attendance ownership. Coordinators acquire Identity/company/member locks before trip locks and retain that same transaction. It returns immutable references and conservative attendance mapping: actual attended -> rule `confirmed`, not_attended -> `declined`, missing -> `unconfirmed`. RSVP alone never yields `ConfirmedEventContext`. Invalid/mismatched references fail safely; cancelled events cannot authorize an exception. Superseded definition/attendance references retain identity with `reviewRequired=true` and no usable confirmed context. Accepted decisions keep their stored references for staff review rather than being silently rewritten.

Only a current actual-attended decision tied to the current definition returns a usable `ConfirmedEventContext`; prescribed load matching remains the existing pure qualification matcher. The coordinator still checks prescribed cargo/mass/trailer against the trip and owns actual acceptance/contribution replacement. Events does not accept a trip, count progress or emit a reminder.

## Safe events and recovery

Closed schema-v1 `event.changed`, `event.response_changed` and `event.attendance_changed` contain only safe event/definition/revision/member IDs, category and change sequence. Definition categories are created/updated/cancelled. Response and attendance use their own monotonic aggregate/version namespaces. Attendance batch history is recovered through event/change sequence, not by assuming its representative last revision describes every member. These events remain visibly unbound until VTC-036 installs reviewed consumers; they signal later reminder generation invalidation and accepted-trip review, with no delivery claim. See [event registry](../contracts/dashboard/events.md).

Apply the additive migration through the locked runner and [partial-DDL recovery procedure](persistence.md#partial-ddl-recovery-runbook). Startup never migrates or seeds. MySQL DDL implicit commits remain relevant; never rewrite the published prefix or clear a sticky applying marker to replay blindly. The fixed synthetic reset drops Events children before catalog/identity parents. The persistence suite rehearses exact eleven-migration prefix upgrade with sentinel/checksum preservation; recovery retains its distinct partial-DDL and lost-receipt cases with thirteen current migrations. No live migration, grants, production retention deletion or deployment is performed by this card.

## Verification scope

Unit tests cover signed scope/session/epoch cursors, fixed UTC/DST boundary, key configuration and safe event schema rejection. Contract tests cover closed public DTOs and explicit server/meeting/organizer/route/attendance facts. Real MySQL tests cover roles/privacy, independent versions, cutoff/reschedule/cancellation, duplicate/conflicting keys, competing responses, current authority on replay, attendance/exception references, rollback after durable effect append, lock-time cutoff, ordered recipients, server IDs, restrictive history and immutable published catalog pins. Receipt-loss injection checks no automatic command retry; lower-level persistence protocol/recovery tests own actual wire receipt-loss evidence. Aggregate, browser regression, exact-candidate generation/CI/review remain separate delivery gates recorded with their candidate SHA.

Immutable receipt lookups use `FOR SHARE` under the already-held company command lock, matching SELECT+INSERT-only receipt privileges. MySQL distinguishes [locking-read privilege requirements](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html); no history mutation grant is needed. The deployment rehearsal's owned local acceptance fixture exercises real Events commands/replays with these restricted grants, separately from ordinary broad synthetic integration accounts. Exact-candidate execution is recorded by delivery verification.
