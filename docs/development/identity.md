Steam remains separate from email/password login; actual telemetry-token consumers remain VTC-023.

## Auth engine and persistence

`apps/api/src/modules/identity/service.ts` is the public module facade. Better Auth and its Drizzle adapter are both pinned to **1.7.10**. `engine.ts` owns their configuration and schema coupling. No generic library handler, admin plugin, standalone signup, native reset or native credential-change route is mounted. Passwords are 12–128 characters under the configured technical policy and use the library's configured scrypt hash/verify functions. Input policy does not claim a company membership rule.

The adapter/core's required peers are explicit production dependencies at the versions already resolved by Better Auth. Strict `pnpm deploy --prod --legacy` requires those peers at the deployment root even when workspace installation finds nested copies. Kysely is an auth-engine dependency; domain persistence remains the existing Drizzle/mysql2 path. No peer/release-age policy is disabled.

Login takes a nonlocking credential/security snapshot in a short transaction, releases its connection, then runs the pinned native scrypt verifier (or equivalent native dummy hashing for an absent credential). A successful verification creates an opaque in-memory capability validated by a private WeakMap; arbitrary objects/booleans cannot bypass verification. A short final transaction locks company/member/current user/account state and rechecks the exact account/hash, email/verification state, all security epochs, active membership and company version. Native Better Auth still issues the session on that caller transaction; its configured verifier only accepts the captured hash/password pair, without repeating expensive work under SQL locks. Stale proof fails generically. Passwords/proof are never persisted or logged. Short exclusive authoritative locks retain the existing company/member/session ordering because native getSession may delete expired/invalid sessions; it is not uniformly a pure read. The existing five-slot fail-fast pool remains intentional; bursts may receive controlled 503 rather than an unbounded queue or a throughput guarantee.

Installed-source inspection establishes the integration assumptions exercised by real MySQL tests:

- Native email sign-in lowercases the submitted email and reads the `credential` account's `password` field. Provisioning applies the same lowercase-only normalization; it never rewrites provider-specific dots/aliases or trims an invalid address. Email keys have exact UTF-8 binary collation, separate from display names.
- MySQL adapter `withReturning` performs an insert/update and a follow-up ID-based select. Even with adapter transactions disabled, it invokes `db.transaction` for that follow-up select. The private bridge joins that callback to the already active `TxContext`; it never starts or commits an autonomous transaction. The transaction host continues guarding execution after context expiry. A real rollback test creates user/account/member and a native library session, then fails the outer callback and proves all those rows absent.
- Engine dates use Drizzle `datetime(3, mode: date)`. Better Auth passes/receives `Date`; the existing `utcColumn` instead accepts canonical ISO strings and must not be substituted. The mysql2 session remains UTC with exact milliseconds. Application IDs use the existing exact `BINARY(36)` UUIDv4 representation and the engine's configured UUID generator.
- Library cookie construction prefixes even custom names when `useSecureCookies` is true. The bridge disables that automatic prefix and explicitly sets Secure/HttpOnly/SameSite=Lax/Path=/ attributes, preserving exact `__Host-vtc_session` / `__Host-vtc_csrf` names for every configured HTTPS origin, including unset or nonproduction NODE_ENV. Issuance and clearing share this origin policy. Local HTTP uses `vtc_dev_session` / `vtc_dev_csrf`. There is no Domain attribute or cookie authorization cache.

`packages/db/src/schema/identity/` owns auth users/accounts/sessions/verifications, memberships/epochs/preferences, additive role rows, the singleton company pointer, bound challenges, abuse counters and safe command results. Its package subpath is an internal owning-module convention, not a general account mutation API or SQL security boundary. Historical references use restrictive FKs. The additive migration follows the published audit migration without changing its bytes. Startup/install never migrates or seeds; use the explicit [migration/recovery commands](persistence.md#migration-ownership-and-commands).

## Transaction and authorization contract

`prepareCredential` runs before invitation/bootstrap locks. `insertWithCredential(tx, input)` inserts on the exact caller transaction and creates no session and no email verification. Admissions must additionally consume its invitation, assign initial per-game qualifications and append its audit/events in that same transaction. It must reject an unrelated existing identity rather than adopting it by email. No password is queued or stored in command results.

Bootstrap is an explicit operator call to `identity.bootstrap` before enabling member traffic, using an approved transactional access-event adapter. Supply operator input from private stdin or an ignored configuration file, never command arguments, committed fixtures or logs. There is no public bootstrap endpoint or startup seed. The initial member and singleton pointer are inserted together without circular required FKs. A repeat/concurrent second bootstrap fails, rolling back its candidate identity. Bootstrap starts with unverified email and Driver membership; the normal verification flow must establish the current email channel before protected changes/succession.

The singleton pointer is the only Director grant. Generic assignments accept only Trainee/Driver/Dispatcher/Deputy Director and reject protected director targets. `permissions.ts` implements the architecture's capability vocabulary; every active member can read their own pending/rejected reports and evidence, including administrative-only actors. Submission and event responses require a Trainee/Driver role; administration alone does not grant those actions. Every authenticated operation reads active membership and session/access/credential epochs from MySQL. Privileged commands lock the company, actor/target members in sorted order, then session/challenge state and recheck current capabilities. This deliberately serializes the small company's identity commands. Cross-module callers must acquire company/member locks before later qualification/trip locks; `authorizeInTransaction` rechecks an actor on the caller's exact transaction. `guardManualReview` must run again under the owning report/revision locks for decisions, corrections and reconciliation; Director and Deputy have no self-review exception.

Departure deletes current sessions, consumes challenges, increments access/credential/identity epochs and removes assignments. Reinstatement retains the same identity and requires explicit replacement roles; previous sessions/challenges remain invalid. Requested qualification assignments fail unavailable until an owning qualification coordinator exists. `accessState(tx, userId)` exposes the authoritative active/epoch seam for future telemetry and identity consumers. This does not claim that absent telemetry-token tables were mutated or that historical qualifications were reset. Those owners must bind credentials/assignments to the access lifecycle and join the same command transaction.

Succession requires the serving director, their currently verified email/epochs, another active member and a cryptographically generated successor-bound code. It expires **exactly ten minutes** after creation, is replaced by the next generation, allows five attempts, and is consumed atomically with the pointer update and audit/events. The former director retains Driver, history and separately assigned additive roles. An explicit Deputy/Dispatcher assignment is not a derived Director grant and is removable through normal authorized role administration; only the current singleton pointer grants Director and leadership transfer, including after two successive transfers. Credential/reset challenges bind purpose, actor, email/access/credential/identity epochs and proposed email where applicable. Changing credentials revokes all sessions, including the current one; further authenticated requests require a fresh sign-in. No administrator recovery bypass is provided.

Email replacement preserves the current verified login address through two durable stages. `POST /me/credential-challenges` with `purpose=email_change` delivers only to the current channel. Its confirmation through `/me/credential-changes` returns **202 pending**, leaves identity/epochs/sessions unchanged and transactionally enqueues a separate proposed-address proof with a fresh ID/hash and ten-minute expiry. Only `/me/email-change-confirmations` can consume that proposed proof and return 200 after atomically swapping the address, marking it verified by that proof, revoking sessions/challenges, advancing email/access/credential epochs and appending audit/access events. A taken proposed address or the current address returns the same generic 401 as an invalid challenge, retaining the bounded attempt/consumption and failed idempotent result without identity/session/event effects. Missing delivery or required final events fail closed; adapter failure rolls back the stage/effects.

`GET /me/email-change` exposes the caller's current pending ID, proposed address, stage and expiry, or null when absent, expired, exhausted, consumed or invalidated. A fresh credential-challenge request replaces either stage, so an unreachable/mistyped proposal never traps the old verified channel: login, recovery, another replacement and serving-director succession remain available. Each stage allows five attempts; an old-channel code cannot prove the proposed channel. Inputs are bounded to 254 characters in the canonical contract and facade. VTC-017 owns the account UI using these explicit states; no UI or mail delivery is claimed here.

### Email replacement rollout

The additive `0002` migration adds the stage and identity epoch without rewriting published migrations. Existing outstanding challenges default to epoch zero and must be reissued; existing identities and their verified email remain intact. Apply the migration explicitly and drain old identity processes before activating the revised two-proof routes. Do not run old and new credential-change implementations concurrently. Startup remains disabled by default and never migrates; this is a rollout gate, not a claim of a live migration or zero-downtime compatibility.

## Delivery seams and fail-closed rollout

`IdentityPorts.delivery.enqueue(tx, privateChallenge)` must persist a private mail intent on the supplied transaction, with encrypted/private payload handling owned by VTC-014/021. It must not send network mail inside database locks. Its ordinary result is `pending`, never a claim of sent/delivered mail. Email-change intents include `emailChangeStage` (`current_email` or `proposed_email`) so the future delivery adapter can select the correct confirmation flow without reading identity-owned tables. Codes are HMAC-protected in identity storage, absent from ordinary audit/events/results, and only available to the private delivery port.

`IdentityPorts.accessEvents.append(tx, event)` must durably append the safe `member.access_changed` event on that same transaction. There is no default no-op or in-memory runtime queue. VTC-021 installs the real transaction-backed access-event adapter in the default server composition; access-only administration can use it after the explicit identity migration/activation gates below are satisfied. Events remain retained unbound until an owning consumer is installed. With MAIL_MODE disabled, bootstrap, recovery and protected changes requiring mail reject with 503 before claiming effects; VTC-014 supplies the opt-in delivery composition below. Synthetic delivery ports prove transactional rollback in tests and do not establish a production mail adapter or downstream consumer effects.

Existing environments continue starting with identity disabled. Explicitly apply the new migration and approved operator/bootstrap integration before enabling `IDENTITY_ENABLED=true`, with a separately managed random `IDENTITY_SECRET` of at least 32 characters and an exact `IDENTITY_ORIGIN`. Production requires an HTTPS origin. HTTP is accepted only for exact canonical localhost, 127.0.0.1 or [::1] origins outside production; other loopback addresses, lookalike hostnames and nonlocal HTTP are rejected. HTTPS cookies are secure independently of NODE_ENV; local HTTP has distinct cookies. Invalid enabled configuration fails startup with field names only. `.env.example` contains placeholders; local setup generates an ignored random secret without printing it. This change performs no live migration, environment update or deployment. Proxy trust is disabled by default. The optional strictly validated `API_TRUSTED_PROXY_IPV4` enables only one exact ingress peer at hop zero, including its dotted IPv4-mapped socket form. The [development activation package](../operations/identity-mail-activation.md) supplies dedicated ingress addresses, explicit Caddy forwarding overwrite, narrow runtime grants and measured client-IP/rate-bucket acceptance. Activation still requires that reviewed configuration and operational proof. VTC-039 owns security hardening; the VTC-011/VTC-041 activation owner must satisfy that gate for the actual environment. A shared proxy socket otherwise puts clients in the same conservative slot; no unverified forwarding header is trusted to improve fairness.

## Browser security and technical bounds

All writes require the exact configured Origin and a signed expiring CSRF token from `/api/v1/auth/csrf`. Pre-login tokens bind an HttpOnly signed 30-minute nonce; authenticated tokens bind the current session ID. Login/logout clear the old pre-session binding, and stale/cross-session tokens fail. Fastify enforces the existing strict request and response schemas; errors/logs omit raw driver/library exceptions, identities, inputs and cookies. Set-Cookie remains an array of distinct headers.

Abuse counters live in MySQL. Each of five source-admission categories (CSRF, login, challenge, command, read) retains its own 200/minute global ceiling. The read category admits up to 40 requests per keyed source slot per fixed minute; CSRF, login, challenge and command source slots remain at 20/minute. Actor/private-binding slots, including an actor-scoped read if called, remain at 20/minute. VTC-035 measured a legitimate account/event-header workflow reaching the previous 20-read source boundary (21 charged reads, including cancelled requests); the bounded read allowance provides headroom without changing authentication or command admission. Fixed-window allowances can burst and do not imply per-second pacing or throughput. Source slots are checked first: an already denied slot cannot charge the global row, and anonymous CSRF traffic cannot consume login/command capacity. Every owned auth/me route admits once in an early request hook before parsing, actor/optional-actor resolution or password work, including reads and invalid cookies. Challenge facade send controls additionally use a separate actor/private-binding namespace at 20/minute, without charging the HTTP global budget again. For anonymous resets this binding is mintable and is not a per-account limiter. These are technical ceilings, not guaranteed allowances or company policy. Each namespace/category has 256 fixed keyed slots, plus the five source-global rows (at most 2,565 possible keys); attacker-selected addresses/actors cannot create unbounded rows. Collisions conservatively share limits. Updates lock slot then category-global row, persist denied-slot saturation, survive recreation and reset by minute window; dependency failure denies admission. `Retry-After` is 60 seconds. Untrusted forwarded addresses cannot select a bucket; the verified ingress policy above is a hosted activation gate.

Anonymous reset requests additionally coalesce under the authoritative company/member/challenge locks: an existing unconsumed, unexpired code below its attempt bound and matching every current security epoch keeps its original ID/hash/expiry/attempts, with no further mail intent. Fresh anonymous bindings/keys cannot supersede it or extend its lifetime. Only an unusable code permits renewal; the same generic received acknowledgement covers known, unknown, unverified and inactive accounts. Coalescing survives process recreation and concurrent requests through MySQL, without additional cooldown policy or attacker-controlled rows. Missing required delivery still fails closed; a failed renewal enqueue rolls back. Authenticated credential/email/succession requests retain their explicit replacement semantics.

These finite ceilings bound work and state; they do not prevent distributed denial of service. Distinct sources can still exhaust a category global budget, and fixed-slot collisions can deny unrelated clients. Per-account login backoff is not implemented: it could reduce distributed guessing but introduces attacker-triggered account lockout and requires enumeration/timing review. VTC-039 owns that hardening before pilot activation, including residual reset abuse after expiry/attempt exhaustion, delivery reliability and enumeration/lockout tradeoffs, alongside measured ingress and capacity evidence; no production throughput is inferred from these synthetic limits.

Declared browser command results retain a keyed fingerprint and only safe IDs/versions/preferences for 24 hours. Scope includes actor or signed private pre-session binding, route and target as appropriate. Company locking serializes identical key reservation; changed input conflicts. Passwords/codes are only inputs to HMAC, never plaintext result-store fields. Each command deletes up to 100 expired result rows; login likewise deletes up to 100 expired sessions through the expiry index. Per-category admission bounds result/session creation by the corresponding fixed ceilings above; VTC-021/039 own periodic retention/operations beyond opportunistic cleanup. Authenticated result replay still requires a current valid session; credential changes require signing in again before a same-key replay. An unknown COMMIT outcome is never automatically retried: use a durable same-key result lookup/recovery. Invalid challenge attempts commit their bounded counter before returning generic 401. Internal failure diagnostics contain only fixed allowlisted categories, with no raw error/SQL/input.

Recognized mysql2 connection/acquisition/query and InnoDB lock-wait timeouts, transport loss/refusal, temporary DNS resolution/network reachability and pool/server capacity failures return retryable 503. Temporary DNS resolution uses Node's `EAI_AGAIN`; permanent `ENOTFOUND` and arbitrary SQL/application errors are not availability failures. The pinned driver's two uncoded pool-acquisition errors use exact full-message matching; arbitrary SQL/application error text is never classified or exposed. Availability failures, including lock-wait timeout, are not automatically retried. Native auth-engine 5xx responses also return 503; invalid credentials remain generic 401, while unexpected uncoded application failures remain nonretryable 500. The unknown-COMMIT class takes precedence over availability classification even through a repository cause wrapper, preserving its uncertain outcome and preventing an automatic retry.

Identity uses the shared [transaction receipt bounds](persistence.md#transaction-participation): COMMIT acknowledgement is bounded at five seconds; START/ROLLBACK remain one second. Focused MySQL workload measurements motivated the COMMIT-only headroom, without establishing the storage cause or a production-latency guarantee. A failed or late COMMIT remains unknown and nonretryable, with immediate connection disposal. Test fixture diagnostics retain only fixed phases, allowlisted driver/status categories and numeric timings; first-unknown loop/status capture does not serialize errors, SQL or credential inputs.

## Verification and remaining evidence

Logout deletes the checked current session through the owned repository on the caller transaction. Better Auth 1.7.10's sign-out suppresses database errors, so it is used only for native cookie expiry with its session-token cookie removed from the internal request; other cookies remain available for cache-chunk cleanup. This avoids swallowed database failures and further statements after a server-side transaction rollback. Persistence failure returns a safe error without reporting revocation or emitting success cookies; an uncertain COMMIT retains its distinct nonretryable outcome.

Focused real MySQL tests cover owned provisioning/native sign-in and rollback, bootstrap/duplicate races, additive roles/current authority, forbidden self-review/protected director targets, deactivation/reinstatement, challenge binding/expiry/replacement/attempts, concurrent reset/succession, failure rollback, durable rate state and API cookies/CSRF/strict schemas. The built-server Playwright API-context journey enables identity against its isolated allocated MySQL, signs in a synthetic provisioned account, reads `/me` and logs out. Auth traces are disabled to keep generated passwords/cookies out of uploaded artifacts. Production-cookie checks use the actual engine configuration. Existing persistence/recovery suites include the additive migration and preserve their synthetic guards and unknown-COMMIT regressions.

Run `pnpm check`, `pnpm build`, `pnpm test:local integration`, `pnpm test:local e2e`, and the final isolated suite through the delivery workflow; startup/packaging changes also require `node deploy/development/test.mjs`. The delivery report records actual results and exact candidate, independently from these implementation requirements. Real mail, downstream token/qualification integration, independent review, green exact-head CI and hosted acceptance remain distinct gates.

## Admissions integration

VTC-015 implements the [admissions coordinator](admissions.md) using identity-owned current-company/authority, normalized-email-existence, prepared-credential, same-transaction provisioning and access-event facades. No admissions repository reaches through identity tables. Invitation redemption supplies the same transaction for account, active Trainee membership and selected-game initial assignments, never issues an automatic session and retains unverified email. Existing active/inactive identities are rejected rather than adopted; former-member reinstatement remains the identity workflow. Identity defaults and protected director flows remain unchanged. See the admissions guide for current generation/mail fencing, opt-in key handling and exact-candidate verification gates.

[VTC-017 account screens](account.md) now consume these existing routes, including current-email verification, protected password change and reloadable two-proof email replacement. This browser integration does not change identity policy or activate a hosted service.

[VTC-023 telemetry](telemetry.md) adds an optional transaction-scoped credential invalidation callback for membership/security changes and `externalChanged`. Composition supplies it only when telemetry is explicitly enabled; failure rolls back the identity/audit/access event. Captured epochs still prevent revival if a credential was stale while the module was disabled. Identity imports no telemetry repository.


VTC-038 [administration](administration.md) mounts current-authority staff member reads/commands and verified-email leadership HTTP. It adds the existing company reporting-timezone primitive and resolves the successor from the stored challenge for the challenge/code-only confirmation wire shape. Explicit reinstatement uses the injected caller-transaction qualification lifecycle; old credentials remain invalid.
