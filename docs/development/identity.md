# VTC-013 identity foundation

[VTC-013](https://trello.com/c/dkwyHN2B) implements the project-owned identity facade and the existing auth/me browser contract. Product policy remains in [CONCEPT.MD](../../CONCEPT.MD), wire shapes in the [browser contract](../contracts/dashboard/README.md). This is backend identity infrastructure; account screens (VTC-017), admissions (VTC-015), mail (VTC-014), durable job delivery (VTC-021), Steam (VTC-018), personal telemetry credentials (VTC-023), qualifications (VTC-028) and administration HTTP/UI composition (VTC-038) keep their own integration gates.

## Auth engine and persistence

`apps/api/src/modules/identity/service.ts` is the public module facade. Better Auth and its Drizzle adapter are both pinned to **1.7.10**. `engine.ts` owns their configuration and schema coupling. No generic library handler, admin plugin, standalone signup, native reset or native credential-change route is mounted. Passwords are 12–128 characters under the configured technical policy and use the library's configured scrypt hash/verify functions. Input policy does not claim a company membership rule.

The adapter/core's required peers are explicit production dependencies at the versions already resolved by Better Auth. Strict `pnpm deploy --prod --legacy` requires those peers at the deployment root even when workspace installation finds nested copies. Kysely is an auth-engine dependency; domain persistence remains the existing Drizzle/mysql2 path. No peer/release-age policy is disabled.

Installed-source inspection establishes the integration assumptions exercised by real MySQL tests:

- Native email sign-in lowercases the submitted email and reads the `credential` account's `password` field. Provisioning applies the same lowercase-only normalization; it never rewrites provider-specific dots/aliases or trims an invalid address. Email keys have exact UTF-8 binary collation, separate from display names.
- MySQL adapter `withReturning` performs an insert/update and a follow-up ID-based select. Even with adapter transactions disabled, it invokes `db.transaction` for that follow-up select. The private bridge joins that callback to the already active `TxContext`; it never starts or commits an autonomous transaction. The transaction host continues guarding execution after context expiry. A real rollback test creates user/account/member and a native library session, then fails the outer callback and proves all those rows absent.
- Engine dates use Drizzle `datetime(3, mode: date)`. Better Auth passes/receives `Date`; the existing `utcColumn` instead accepts canonical ISO strings and must not be substituted. The mysql2 session remains UTC with exact milliseconds. Application IDs use the existing exact `BINARY(36)` UUIDv4 representation and the engine's configured UUID generator.
- Library cookie construction prefixes even custom names when `useSecureCookies` is true. The bridge disables that automatic prefix and explicitly sets Secure/HttpOnly/SameSite=Lax/Path=/ attributes, preserving the exact production name `__Host-vtc_session`. Local HTTP uses `vtc_dev_session`. There is no Domain attribute or cookie authorization cache.

`packages/db/src/schema/identity/` owns auth users/accounts/sessions/verifications, memberships/epochs/preferences, additive role rows, the singleton company pointer, bound challenges, abuse counters and safe command results. Its package subpath is an internal owning-module convention, not a general account mutation API or SQL security boundary. Historical references use restrictive FKs. The additive migration follows the published audit migration without changing its bytes. Startup/install never migrates or seeds; use the explicit [migration/recovery commands](persistence.md#migration-ownership-and-commands).

## Transaction and authorization contract

`prepareCredential` runs before invitation/bootstrap locks. `insertWithCredential(tx, input)` inserts on the exact caller transaction and creates no session and no email verification. Admissions must additionally consume its invitation, assign initial per-game qualifications and append its audit/events in that same transaction. It must reject an unrelated existing identity rather than adopting it by email. No password is queued or stored in command results.

Bootstrap is an explicit operator call to `identity.bootstrap` before enabling member traffic, using an approved transactional access-event adapter. Supply operator input from private stdin or an ignored configuration file, never command arguments, committed fixtures or logs. There is no public bootstrap endpoint or startup seed. The initial member and singleton pointer are inserted together without circular required FKs. A repeat/concurrent second bootstrap fails, rolling back its candidate identity. Bootstrap starts with unverified email and Driver membership; the normal verification flow must establish the current email channel before protected changes/succession.

The singleton pointer is the only Director grant. Generic assignments accept only Trainee/Driver/Dispatcher/Deputy Director and reject protected director targets. `permissions.ts` implements the architecture's capability vocabulary; administration alone does not grant driving capabilities. Every authenticated operation reads active membership and session/access/credential epochs from MySQL. Privileged commands lock the company, actor/target members in sorted order, then session/challenge state and recheck current capabilities. This deliberately serializes the small company's identity commands. Cross-module callers must acquire company/member locks before later qualification/trip locks; `authorizeInTransaction` rechecks an actor on the caller's exact transaction. `guardManualReview` must run again under the owning report/revision locks for decisions, corrections and reconciliation; Director and Deputy have no self-review exception.

Departure deletes current sessions, consumes challenges, increments access/credential/identity epochs and removes assignments. Reinstatement retains the same identity and requires explicit replacement roles; previous sessions/challenges remain invalid. Requested qualification assignments fail unavailable until an owning qualification coordinator exists. `accessState(tx, userId)` exposes the authoritative active/epoch seam for future telemetry and identity consumers. This does not claim that absent telemetry-token tables were mutated or that historical qualifications were reset. Those owners must bind credentials/assignments to the access lifecycle and join the same command transaction.

Succession requires the serving director, their currently verified email/epochs, another active member and a cryptographically generated successor-bound code. It expires **exactly ten minutes** after creation, is replaced by the next generation, allows five attempts, and is consumed atomically with the pointer update and audit/events. The former director retains Driver and history. Credential/reset challenges bind purpose, actor, email/access/credential epochs and proposed email where applicable. Confirmation at the old address does not verify the new address. Changing credentials revokes all sessions, including the current one; further authenticated requests require a fresh sign-in. No administrator recovery bypass is provided.

## Delivery seams and fail-closed rollout

`IdentityPorts.delivery.enqueue(tx, privateChallenge)` must persist a private mail intent on the supplied transaction, with encrypted/private payload handling owned by VTC-014/021. It must not send network mail inside database locks. Its ordinary result is `pending`, never a claim of sent/delivered mail. Codes are HMAC-protected in identity storage, absent from ordinary audit/events/results, and only available to the private delivery port.

`IdentityPorts.accessEvents.append(tx, event)` must durably append the safe `member.access_changed` event on that same transaction. There is no default no-op or in-memory runtime queue. Missing adapters reject required challenge/event-producing commands with 503 before claiming effects. Synthetic tests supply transaction-backed fixture ports and prove rollback; they do not establish a production mail/job adapter. The default server composition supplies neither until the owning cards implement them. Thus existing provisioned accounts can sign in/read/logout when identity is enabled, while bootstrap, recovery, protected changes and administration remain unavailable until their required ports are composed.

Existing environments continue starting with identity disabled. Explicitly apply the new migration and approved operator/bootstrap integration before enabling `IDENTITY_ENABLED=true`, with a separately managed random `IDENTITY_SECRET` of at least 32 characters and an exact `IDENTITY_ORIGIN`. Production requires an HTTPS origin; local HTTP has distinct cookies. Invalid enabled configuration fails startup with field names only. `.env.example` contains placeholders; local setup generates an ignored random secret without printing it. This change performs no live migration, environment update or deployment. The server ignores forwarding headers (`trustProxy=false`); a future trusted-proxy change needs exact deployment configuration and verification.

## Browser security and technical bounds

All writes require the exact configured Origin and a signed expiring CSRF token from `/api/v1/auth/csrf`. Pre-login tokens bind an HttpOnly signed 30-minute nonce; authenticated tokens bind the current session ID. Login/logout clear the old pre-session binding, and stale/cross-session tokens fail. Fastify enforces the existing strict request and response schemas; errors/logs omit raw driver/library exceptions, identities, inputs and cookies. Set-Cookie remains an array of distinct headers.

Abuse counters live in MySQL: a shared global budget of 200 checks/minute and 20 checks/minute per category/hash slot. There are four categories and 256 keyed slots each plus the global row, so attacker-selected addresses/keys cannot create unbounded counter rows. Slot collisions conservatively share limits. Challenge facade calls also charge send limits; HTTP may charge additional checks, so these are ceilings rather than guaranteed request allowances. Counters survive process recreation and serialize concurrent updates; dependency failure denies the operation. `Retry-After` is 60 seconds. Deployment proxy/address policy remains relevant to fairness; untrusted forwarded addresses cannot choose the bucket.

Declared browser command results retain a keyed fingerprint and only safe IDs/versions/preferences for 24 hours. Scope includes actor or signed private pre-session binding, route and target as appropriate. Company locking serializes identical key reservation; changed input conflicts. Passwords/codes are only inputs to HMAC, never plaintext result-store fields. Each command deletes up to 100 expired result rows; login likewise deletes up to 100 expired sessions through the expiry index. Rate-limited admission bounds new rows to at most the shared global budget per minute; VTC-021/039 own periodic retention/operations beyond opportunistic cleanup. Authenticated result replay still requires a current valid session; credential changes require signing in again before a same-key replay. An unknown COMMIT outcome is never automatically retried: use a durable same-key result lookup/recovery. Invalid challenge attempts commit their bounded counter before returning generic 401. Internal failure diagnostics contain only fixed allowlisted categories, with no raw error/SQL/input.

Recognized mysql2 connection/acquisition/query timeouts, transport loss/refusal and pool/server capacity failures return retryable 503. The pinned driver's two uncoded pool-acquisition errors use exact full-message matching; arbitrary SQL/application error text is never classified or exposed. Availability failures are not automatically retried. Native auth-engine 5xx responses also return 503; invalid credentials remain generic 401, while unexpected uncoded application failures remain nonretryable 500. The unknown-COMMIT class takes precedence over availability classification even through a repository cause wrapper, preserving its uncertain outcome and preventing an automatic retry.

## Verification and remaining evidence

Focused real MySQL tests cover owned provisioning/native sign-in and rollback, bootstrap/duplicate races, additive roles/current authority, forbidden self-review/protected director targets, deactivation/reinstatement, challenge binding/expiry/replacement/attempts, concurrent reset/succession, failure rollback, durable rate state and API cookies/CSRF/strict schemas. The built-server Playwright API-context journey enables identity against its isolated allocated MySQL, signs in a synthetic provisioned account, reads `/me` and logs out. Auth traces are disabled to keep generated passwords/cookies out of uploaded artifacts. Production-cookie checks use the actual engine configuration. Existing persistence/recovery suites include the additive migration and preserve their synthetic guards and unknown-COMMIT regressions.

Run `pnpm check`, `pnpm build`, `pnpm test:local integration`, `pnpm test:local e2e`, and the final isolated suite through the delivery workflow; startup/packaging changes also require `node deploy/development/test.mjs`. The delivery report records actual results and exact candidate, independently from these implementation requirements. Real mail, downstream token/qualification integration, independent review, green exact-head CI and hosted acceptance remain distinct gates.
