# Trip reporting and review workspace

VTC-030 connects the protected RU/EN trip workflows to the existing server commands. Runtime activation remains separately controlled by the [trip](trips.md), [manual report](manual-reports.md), [decision](trip-decisions.md), [catalog](catalogs.md), [event](events.md) and [reconciliation](reconciliation.md) configuration. No production qualification thresholds, reporting timezone, storage capacity or hosted activation is supplied by this UI.

## Member workflows

- `/account/trips` offers own and accepted company scopes with the server's game/decision filters and bounded cursor pages. Lifecycle, company decision, source kinds and recording completeness are separate. Pagination is bound to the effective validated filters, including browser Back/Forward navigation; recovery returns to the first page. Catalog labels visibly identify an English fallback in the current locale. Unknown quantities remain unavailable; known zero is displayed. Actual driven distance and planned distance are separate.
- The list (VTC-049) uses underline tabs for the two scopes, a one-row toolbar with compact game/decision selects, and a dense table (route with game chip, cargo, driven distance, sources, company decision, reporting time) that becomes labeled cards at 760px and below. There is no source filter because `listTrips` has no such parameter; filtering one page in the browser would break pagination. From 1200px a row link selects the trip through a validated `?trip=<uuidv4>` search parameter, which is never sent to the list API, survives paging, is cleared by scope/filter changes and pushes history entries. The non-modal side panel reads `/trips/:tripId`, so the server still decides between the summary and private views; summaries state that decision history is not included. A plain click or Enter moves focus to the panel heading; Close or Escape returns it to the row link, or the main content when the row is not listed, and so does removing the panel while it holds focus; Back/Forward and deep links do not otherwise move focus. While the panel is open the table hides its Sources column, which the panel shows. Narrower screens ignore `?trip=` and link rows to the full detail page. The dispatch review queue reuses this list and side-panel pattern at the same 1200px breakpoint.
- `/account/trips/:tripId` renders the server's summary/private discriminated union. Other members' accepted summaries never cause private evidence/history requests. Private detail includes normalized effective facts, original immutable manual revisions, comparison against the prior revision, decision reasons and historical evaluation references. Comparisons require a proven same-report predecessor with the preceding report-local revision number. Interleaved reports are never compared; legacy or missing lineage is explicitly unavailable. History pages remain bounded.
- `/account/reports` discovers durable drafts. `/account/reports/new`, `/account/reports/drafts/:draftId` and `/account/reports/:reportId/edit` save partial drafts or submit complete immutable revisions. Reports never collect a gameplay date. Original canonical entity/publication IDs survive locale changes; explicitly unresolved selections retain diagnostic labels without inventing an ID.
- The compact report form (VTC-060) keeps one page frame (the heading) for the editor and every loading, error, forbidden and submitted-draft state; the no-date note shows with the editor. The form card holds, in order: game and catalog publication (a publication read failure offers Refresh; a game without a published catalog shows a plain note), a field grid that has two columns once the form is at least 520px wide (origin, destination, cargo, trailer type, cargo mass, actual distance, event, comment), the screenshot picker with visible native file input and its uploaded items, the telemetry target, and the footer. Mass, distance and event hints are accessible descriptions: actual shipment mass rather than catalog unit mass, results-screen driven distance rather than planned length, and the existing RSVP/attendance note. While Submit is disabled because the submission is incomplete, a passive list (no live region) names the missing or inexact fields and a ready screenshot; it is derived from the same generated `ManualSubmissionFields` schema and evidence readiness as the submit guard. Save draft is secondary and Submit is the primary action; draft/save/submit semantics, idempotency, telemetry-target intent and the confirmation dialog are unchanged. A "What happens next" aside explains different-reviewer review, pending reports outside company totals, revision history and resubmission on the same trip. The aside sits beside the form when there is room and below it otherwise; Russian text wraps only between words. Autocomplete catalog pickers, tonnes/kilometres input, client-side limit checks, drag-and-drop or multi-file upload and thumbnails are not offered because the contract and policies do not support them.
- Upload controls read the configured policy and show processing, ready, rejected, expired and unavailable states. A ready completion screenshot is required before submission. Private downloads use the authorized binary route. Upload completion and removal update the latest attachment state, so a removed attachment cannot return when another upload settles. Files and object URLs are transient; report bodies, reasons and evidence are never persisted in browser storage. Retention remains at least one calendar year after the latest decision and throughout review.
- An explicit own same-game telemetry target carries its canonical version. Reloading targets is an explicit version refresh. A saved draft must successfully save a changed or refreshed target/version before submission can be confirmed, because the submission command uses the persisted draft target. Draft, report and canonical trip versions remain distinct. Accepted records offer a correction request, preserving the effective result until staff commits a replacement.
- Own trip detail exposes event association. Selection and RSVP do not prove attendance. The server either applies an authoritative result or creates a pending proposal; immutable event/attendance references are displayed during review.

## Staff workflows

`/account/review` (VTC-059) is a compact dispatch queue with two tabs: Awaiting decision lists held trips (`hold=true`) oldest first by default, and Decided lists released trips newest first with a company-decision filter. Game and order filters, the tab and the selected trip live in validated search parameters; filter changes restart paging, and an expired cursor returns to the first page. Rows show driver (own reports marked), route, queue type (manual report, new revision, late telemetry or telemetry), revision number, a rules flag and the filing time; at 760px and below each row becomes a three-line card. From 1200px a row opens a non-modal decision panel beside the queue; narrower screens open `/account/review/:tripId`, whose back link keeps the queue filters. Both read the trip through `getTripReview` (trip, effective facts, qualification check, acceptance and decision history), the report's `listManualRevisions` page when a manual revision exists, catalog entity labels for pinned IDs, and evidence content only when a screenshot is opened; below the panel the full page also reads the private history (revisions, report, correction requests) and reconciliation history, and proposals once the corrections disclosure opens. The header names the driver, queue type and revision and states why the trip is held (its stored review reasons, localized where known and shown as the code otherwise). The panel then shows the revision diff against the proven same-report predecessor (changed fields marked in text) and the trip's effective facts (route, cargo, mass, trailers, driven and planned distance, start and completion; unknown values read as unavailable, never zero) whenever the read includes them, because telemetry or an approved staff resolution can change them without a new revision; trips with a telemetry source list the facts first, and a trip with neither facts nor a manual revision says its facts are unavailable. It continues with evidence opened on demand in a dialog, the qualification check (pass, fail, unknown or bypassed by an event), a merged revision/decision history with reviewer nicknames and the "Accepted over limits" marker, and the decision form. Staff choose Accept or Reject before the submit button is named; a reason is always required. An over-limit acceptance lists every exceeded limit and requires an explicit confirmation, which resets whenever the review ETag changes and is sent as `confirmOverLimits: true` only then; when the server reports acceptance as unavailable, Accept stays focusable and explains why while Reject remains. Own reports stay listed but show a note without decision controls. Escape closes the side panel and returns focus to the row, except on a decision control (choice, reason, confirmation, submit) or during text composition, so a draft is never discarded by Escape. Proposals and resolutions remain on the full page under a "Corrections and resolution" disclosure that opens while a proposal is pending. A decision binds the current review ETag and the exact immutable reviewed revision and fact. All manual authors in a merged group remain barred from their own review, resolution and reconciliation, including directors.

Direct decisions require an explanation. Resolution proposals contain only supported changed fields, ready evidence, optional exact pending correction request and optional historical assignment. Supported UTC corrections are offered only for telemetry facts; manual dates remain absent. Proposal decisions bind the exact proposal revision and current canonical ETag. The proposal-decision response union distinguishes a rejected proposal from a rejected effective trip.

`/account/review/reconciliation` shows bounded candidates, side-by-side authorized facts and explicit primary selection. Candidate reads retain current root/owner/game/matcher guards. When assessment alone changes a version, an advisory pair remains visible only after complete bounded owning evidence proves exactly the stored immutable source fact-ID set and each current effective pointer belongs to its own source set. Matching reasons and accepted-state warnings are recomputed; changed, incomplete or unprovable evidence is excluded. This read never updates candidates, searches, credits or decisions, and always returns `review_required`. It preserves the source reconciliation-before-assessment guard. The merge command still independently validates both current versions; a derived effective fact outside the original source set waits for renewed discovery rather than receiving this read-only exception. Confirmation carries both current versions. Merge retains evidence/sources, produces one canonical contribution and never adds the distances or independently accepts a trip. Trip detail contains reloadable applied/reversed reconciliation history. If a later canonical version invalidates a history cursor, Refresh restarts at its authoritative first page and clears the old page stack. Reversal reloads the operation and current original primary/secondary versions through the owning DTO; aliases still resolve to the canonical detail. Later decisions/dependencies can prevent reversal.

## Transport and recovery

Private query keys bind member, session generation, identity epoch, current capabilities, locale and effective path/filters/cursor. Cancellation reaches transport. Session loss clears private caches; permission failures remove private data and refresh current capabilities. HTTP failures are mapped without rendering private error bodies.

Writes carry current CSRF, actor-scoped UUID idempotency keys and exact ETags where required. Identical uncertain retries reuse their key; changed input, target or version receives a new key. Upload identity includes a SHA-256 checksum of the actual bytes, filename and MIME. Pending commands cannot duplicate. Retry-After is honored. A 409/428 preserves input, refreshes server state and closes the obsolete confirmation; the user must review the current state before confirming again. A background version change cannot rebind an open confirmation to a new command.

The frontend consumes generated browser types and schemas. The installed Zod JSON Schema importer lacks conditionals, so the two existing `ResolutionInput`/`TripProposal` conditions are expanded into equivalent exclusive object branches before import. Positive and negative contract fixtures cover omitted/null/exact correction links and non-null resolution changes.

## Verification

The normal contributor baseline is `pnpm contracts:check`, `pnpm check`, `pnpm build`, `pnpm test:local`, and the full `node deploy/development/test.mjs` rehearsal. Focused lanes are feedback only. The browser harness composes the built API's owning modules, independent synthetic keys and an allocation-owned private Linux evidence directory. It retains the normal five-slot pools and settles its worker before shutdown. Real trip browser journeys disable traces/video/screenshots; controlled synthetic RU/EN captures use ignored output at 390×844, 768×1024 and 1280×800.

Coverage is in `test/unit/trip-ui.test.ts`, `test/unit/manual-report-ui.test.ts` and `test/unit/review-ui.test.ts`, the existing real MySQL trip/decision/reconciliation suites, controlled `test/e2e/trips.spec.ts`, `test/e2e/trips-list.spec.ts`, `test/e2e/manual-report-layout.spec.ts` and `test/e2e/review-layout.spec.ts`, and real `test/e2e/trips-real.spec.ts`. Mocked success establishes UI behavior only. Exact-candidate independent verification/review, current-head advisory review, Required CI, merge and operational activation remain separate evidence gates.

Measured synthetic desktop upload feedback reduced one action from five GET reads plus one POST to two GET reads plus one POST: CSRF, upload and its new metadata. Unrelated events, upload policy and trip-list reads were removed. This is a request-count measurement on controlled fixture data, not throughput/capacity evidence. Paired live editing also exposed API pool admission failures; browser account/catalog/trip reads now share a cancellable FIFO scheduler with two active reads per tab, retaining each transport deadline. Queued cancellation never fetches, active cancellation/rejection releases capacity, and session/query cancellation cannot revive an obsolete queued read. It does not promise unlimited multi-client capacity or change server authority.
