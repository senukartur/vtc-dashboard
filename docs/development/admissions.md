# VTC-015 admissions and onboarding

The admissions module implements the [approved application/invitation policy](../../CONCEPT.MD#membership-application-fields) through the [browser API](../contracts/dashboard/README.md). VTC-016/017 own the public/member UI, VTC-018 owns verified Steam identity, and VTC-028 owns full qualifications. Submitted Steam URLs are unverified applicant evidence; validation performs no provider request or ownership inference.

## Activation and owning boundaries

Admissions is explicitly disabled by default. After applying reviewed migrations and bootstrapping identity, set `ADMISSIONS_ENABLED=true` and a separate `ADMISSIONS_ENCRYPTION_KEY`: 32 random bytes encoded as canonical unpadded base64url. Identity must be enabled. The key must differ from identity/mail keys. Local setup generates a private key while retaining the disabled default. No startup migration, seed, account purchase, provider activation or deployment occurs through this change.

The API and minute jobs process must use the same identity origin and admissions key. The shared private activation file accepts these two fields through the existing explicit activation controls. Preserve the key throughout outstanding seven-day generations and the 24-hour command-result window. There is one active key, no automatic key rotation/key ring. Changing it prematurely makes outstanding encrypted links and keyed fingerprints unreadable; operators must plan rotation after outstanding generations/results expire or retain the previous configuration through recovery. Never print/export keys, passwords, invitation links or authenticated applicant responses as diagnostics.

Admissions owns application facts, immutable committed decisions, invitation generations, bounded command results and rate slots. Identity exposes current company/authority, normalized email existence, prepared Better Auth credentials, same-transaction account/member creation and access events. Admissions never reads identity tables. The qualifications owner supplies `initialize(tx, userId, selectedGames, assignedAt)`, creating exactly one initial Trainee assignment per selected game on the caller transaction. This contains no company numeric limits, rule evaluator, progress, promotion or later assignment API.

## Public submission and strict validation

`POST /api/v1/public/applications` requires nickname, email, Steam profile URL and one or both unique games. Discord and introduction may be omitted or null; staff DTOs normalize them to null. Unknown fields/types, blank strings, malformed mailbox, oversized bodies and unsupported games fail. Nickname/optional text and email use identity/mail-compatible technical bounds. Supported Steam URL syntax is HTTPS `steamcommunity.com/profiles/<17 digits>` or `/id/<ASCII letters, digits, underscore or hyphen>`, optionally followed by one slash, with a 512-character total bound. Credentials, alternate origins, query/fragment and extra path components fail. These are supported technical URL shapes, not provider ownership checks or claims about Steam's business limits. A leading Russian `Accept-Language` range selects RU mail; otherwise EN is retained as transport metadata.

Every submission returns the same 201 ordinary `{id, version}` receipt shape. A receipt is scoped to the caller's signed pre-session/session binding and is deliberately different from the staff application ID. Duplicate normalized emails, including existing active/inactive identities, do not disclose existing IDs, status or private fields. A different request cannot replace pending evidence. Database uniqueness on nullable exact `open_email` allows one submitted/approved-awaiting-redemption application per lowercase email. Rejection clears the guard and creates no deletion; reapplication creates a new application.

## Staff review and history

Current active Director/Deputy `applications.manage` authority is required for every list/detail/history/decision/invitation/copy/reissue operation. Authorization is rechecked under locks, including command replay. Driver, Trainee, Dispatcher, inactive and stale sessions cannot use these operations. A missing private resource after current authorization returns 404. `If-Match` uses the application version for decisions and generation version for copy/reissue.

A submitted application has one committed terminal decision: reviewer, exact reviewed application version, UTC millisecond time, outcome and rejection reason. Rejecting requires a nonblank reason and the durable mail adapter. Missing adapter or enqueue failure rolls back the decision and every related effect. Provider failure after commit retains the decision/history. Approval can succeed with mail disabled and still supplies staff manual copy.

List/history use default 25/max 100 keyset pages sorted by `(submitted_at,id)` descending. `GET /admin/applications/{applicationId}/history` pages all retained applications for the same normalized email. Decision lookup is batched per page. Signed opaque cursors bind current actor/session/access epoch, resource/filter and visibility; the private binding is keyed before encoding. Every page rechecks current authority.

## Generations, delivery and redemption

Approval issues a high-entropy seven-day token. Its lookup hash and AES-256-GCM encrypted generation are separate from encrypted mail payloads; authenticated data binds module/version, origin, application and generation IDs. The current approved generation must be active, unconsumed and strictly before its expiry. `now >= expiresAt` is unavailable. Authorized bodyless POST copy decrypts only that generation, audits the action and returns no-store data. Copy never creates a session or stores its reply in an ordinary result cache.

Reissue creates a new generation ID, atomically removes the prior hash/ciphertext, suppresses its pending private mail, and updates the application pointer/version. Old links fail after this commit. Expired unconsumed invitations may be reissued; consumed/replaced ones cannot. The indexed bounded jobs sweep clears expired hash/ciphertext/eligibility while retaining structured application/decision/generation history.

Enabled approval/rejection intents, safe jobs, audit/outbox and domain changes share the exact transaction. Valid new state is written before the mail adapter validates its owner generation. Network I/O occurs after commit. `Invitation.emailDelivery` reads the messaging owner's current safe state; `not_requested` means disabled mail, `unavailable` means the mail adapter is currently absent. `deliveryId` points to existing permission-filtered mail inspection/retry APIs. `accepted` means provider acceptance and `simulated` means local simulation; neither claims inbox delivery. Required rejection email is durably requested, not falsely acknowledged as delivered.

Redemption validates/password-hashes with the pinned Better Auth hasher before database locks. One transaction checks current generation/email, inserts the auth user/credential and active Trainee membership, initializes selected-game assignments, consumes the invitation, clears private material, invalidates mail, appends audit/outbox/access events and persists a safe ordinary result. Existing identities, including former members, are never adopted or recredentialed. Rollback leaves no orphan account/member/assignment and leaves the original invitation usable. A 201 returns no session/cookie and does not mark email verified; the member signs in normally afterward.

## Concurrency, replay and bounds

Admissions writers serialize through identity's singleton company lock, then current actor/session, application, generation and participating identity/qualification/audit/outbox/mail rows. This deliberately simple choice suits one small VTC and prevents duplicate email/decision/redemption races. Worker validity takes shared company/application/generation locks before the delivery row. Inspect/resend establish the same owner order. An already started provider request cannot be recalled by reissue; current-generation redemption remains authoritative, and earlier invalidation suppresses requests that have not passed the worker's fence.

UUID idempotency keys are HMAC-scoped to actor or signed private pre-auth binding, route and target. Keyed validated-input fingerprints detect changed input. The company guard serializes first use, and the database primary key retains durable uniqueness. Results expire after 24 hours with indexed cleanup limited to 100 rows per pass/command. Public submission/redemption store only safe ID/version. Decision replay stores original version/invitation ID and reconstructs the exact response from immutable application/decision facts; reissue stores only ordinary safe invitation metadata. No password, token, copy reply or ciphertext enters these results, audit, events or jobs. Replays still require current authority; a new key does not bypass domain uniqueness. Unknown COMMIT is nonretryable/uncertain and is never blindly replayed; the same key can discover a committed ordinary result. Only classified deadlock/lock-wait failures retry the complete transaction after explicit rollback, within the existing bounded platform budget.

Public `submit` and `redeem` each retain at most 256 source rows keyed by an eight-byte HMAC plus one category global row. Each minute admits at most 20 per source and 200 per public category. A denied source saturates at 21 without charging the global category, so one unspoofed source cannot exhaust the 200-request allowance. The category global row is locked first, followed by source cleanup/allocation/charge; this path takes no company or identity lock. Global saturation rejects before unknown-source allocation. Otherwise each admission deletes at most 100 older-window rows in its source category, then atomically checks the 256-source cap before insertion. Public admission precedes parsing, authentication and credential work, and restart preserves allowances. These bounded aggregate ceilings protect resources; they do not promise public availability during distributed abuse.

Staff requests authenticate before parsing and require current `applications.manage` authority before changing any staff quota. Missing cookies return 401 without authentication work; invalid cookies can still require identity database work within the existing bounded pool and transaction deadlines. Anonymous, inactive, stale and authenticated unauthorized requests cannot spend privileged quotas. The request caches the authenticated actor, while each handler independently rechecks current authority under its normal transaction locks. `staff_read` and `staff_command` admit 20 per authorized user per minute, using an eight-byte keyed actor digest; sessions cannot multiply the allowance. They have no shared staff global ceiling. Each staff category retains at most 256 actor rows: company locking serializes count/cap/insertion, and each authorized admission deletes at most 100 older-window rows in its own category before allocation. An existing actor can continue at the allocation cap. At most 1,026 rate rows persist across the four categories, and restart does not reset allowances. Runtime needs narrowly scoped DELETE on `admissions_limits` for this cleanup; jobs receive no additional rate privileges. These are technical controls, not company business rules or a claim of distributed denial-of-service immunity. The 64 KiB HTTP body limit, strict JSON, exact origin, signed CSRF binding, UUID keys, If-Match and no-store remain enforced.

## Migration and verification

Migration `0005_admissions` adds admissions/initial-assignment tables and extends audit subject values. Published 0000–0004 bytes are preserved. Exact binary IDs/hashes, exact lowercase email keys, restrictive foreign keys, nullable unique open-email guard, history/expiry indexes and UTC millisecond timestamps follow the persistence baseline. MySQL DDL implicitly commits; use the existing explicit locked migrator and dirty-state recovery/runbook, never claim transactional DDL rollback. Runtime/jobs grants are prepared in the activation matrix, with worker reads plus narrowly scoped expiry cleanup writes. Runtime decisions are immutable after their creation transaction; the internal update privilege completes their mail reference before commit and exposes no mutation API.

Meaningful evidence lives in the unit, actual MySQL integration, persistence/recovery and built-server Playwright lanes. Tests use fictional identities and local adapters only, including duplicates, current permissions, terminal decisions, RU/EN intents, copy with disabled/rejected/ambiguous mail, seven-day boundaries, reissue/redemption races, rollback failure injection, native sign-in, unknown COMMIT and bounded cleanup/rate state. Safe `admissions_query_plan` events expose query-shape label, access/index and numeric row estimate only. Candidate-specific results and independent review remain in the delivery report/PR; this guide is not a claim of deployed admissions, real email delivery, full qualifications or completed future UI/Steam cards.

Private mail invalidation is keyless and always composed, independently of optional enqueue/status. Switching mail from enabled to disabled cannot retain a replaced/consumed invitation payload: reissue and redemption still clear it on their domain transaction. The jobs CLI also runs keyless admissions expiry/result cleanup while the feature is disabled; only classified missing-table/table-grant errors report configuration_pending, and network, unexpected SQL or unknown-COMMIT failures remain failures. Cleanup takes result rows before invitation rows, matching command order.
