# Company Dashboard and Driver Profiles

VTC-033 delivers the company overview dashboard, driver directory, and individual driver profiles in VTCDashboard.

## Architecture and Endpoints

### Identity Module Endpoints (VTC-033 Owned)

- `GET /api/v1/members`:
  - Returns paginated list of company members (`EnvelopeListMemberSummary`).
  - Supports `limit` (default 50, bounded 1..100) and signed cursor pagination (`nextCursor`).
  - Each item contains `id`, `nickname`, `roles`, and `formerMember` boolean flag.
  - Requires `company.read` capability.
- `GET /api/v1/members/:memberId`:
  - Returns driver profile envelope (`EnvelopeMemberProfile`).
  - Contains `member` summary and active qualification `qualifications` assignments per game.
  - Requires `company.read` capability.

### Consumed APIs

- `GET /api/v1/me/workspace-summary` (VTC-114, VTC-119): one private, language-independent snapshot for the signed-in shell, overview actions and review header. The cache is scoped by member, session generation, identity epoch and capabilities. The shell refreshes on visible online focus or reconnect. Confirmed trip, event and admission writes cancel obsolete reads and refresh the summary.
- `GET /api/v1/analytics/company`: Company aggregate distance and accepted trips with day/month buckets.
- `GET /api/v1/analytics/leaderboard`: Top drivers ranked by accepted distance and trips.
- `GET /api/v1/public/company-stats`: only `currentMonth.reportingTimezone`, the zone of the overview period anchors (VTC-056) and of the driver profile's 12-month window (VTC-078); shared cache with the landing stats band.
- `GET /api/v1/members/:memberId/analytics`: Individual driver monthly distance and trips.
- `GET /api/v1/me/upcoming-event`: Next upcoming convoy or company event (the nearest `scheduled` event not yet started; the API has no event type, so the overview calls it the nearest convoy).
- `GET /api/v1/events/:id/my-response` and `PUT /api/v1/events/:id/my-response`: the overview's quick response (VTC-055), through the events feature's `useEventQuery`/`useEventCommand` with the event detail page's paths: `If-Match` only from the my-response ETag (a missing ETag blocks the command), `Idempotency-Key` reused for an unchanged retry, CSRF per command, one command in flight, 15 s abort and the Retry-After wait.
- `GET /api/v1/events/:id/response-counts`: participants count of the nearest convoy, refreshed after a committed response.
- `GET /api/v1/me/qualification-progress` and `/members/:memberId/qualification-progress`: Current qualification levels and progress.
- `GET /api/v1/trips`: Confirmed trip history (accepted trips only on driver profiles). The overview's recent company trips read `scope=company&limit=5&order=completion_desc` plus `game=` for a selected game (key `dashboard-recent-trips` with member, generation, identity epoch, capabilities, language and path; a 403 clears inactive private queries and refreshes the session, a 401 confirms session loss). Company scope is accepted-only. The block shows the latest trips across all time for the selected game.

## Privacy Safeguards

- **Strict isolation of private account data**: Member summaries, profiles, and directory listings never expose emails, passwords, password hashes, credentials, or session tokens.
- **Privacy tests**: Integration and end-to-end tests assert that no `@example.invalid` address, password hash, or credential token is present in serialized responses or client storage/DOM.
- **Privacy footnote**: the driver profile states under its trips that pending and rejected reports, their reasons and screenshots are not shown and that account details never appear on profiles. The profile requests only accepted trips, public qualification progress (`ProgressPublic`, no review flags) and no `/admin/*` or `scope=review` data.

## UI Components and Features

- **Company Overview (`/account/dashboard`)**: a compact layout (VTC-048) that keeps the key numbers, qualification progress and the leaderboard on the first 1280×800 screen.
  - Header: title, subtitle and filters on one row. The game filter is a segmented control (All games, ETS2, ATS) and the period is a labelled native select (This month, Last month, Last 30 days, Last 7 days). Filters are local page state.
  - Period anchors (VTC-056): the periods are calendar dates around today's date in the company reporting timezone (`computePeriodDates(period, now, timeZone)` in `features/dashboard/model.ts`, `Intl.DateTimeFormat` plus calendar arithmetic), because the API reads `fromDate`/`toDateExclusive` in that timezone. The zone comes from `currentMonth.reportingTimezone` of the anonymous public company stats, read with the landing stats band's query key, reader and cache times (`useReportingTimezoneSource`, only with `company.read`). Analytics, the leaderboard and the overview's other reads (qualification progress, nearest convoy, review queue, recent trips) wait for that read. Meanwhile every block shows its loading state, never cached data or a cached error of the fallback keys, so no alert appears before the zone is known. They enable in one render, analytics and the leaderboard first, so their first request has the right dates and, on a cold load, enters the two-slot read queue before the other blocks; a filter change still sends one request per endpoint. The shell's nearest-event chip keeps its own observer. A failed read that is being reread (remount, Retry) also waits. UTC is the fallback when the read fails without data, the month is `unavailable` (no reporting timezone; analytics then answers 409 as before) or the browser does not know the zone; retained data keeps its zone after a failed refresh, and a browser reconnect does not reread a failed read (the UTC fallback lasts until Retry or a remount). The page Retry first rereads a pending, failed or `unavailable` stats read, reusing a read in flight; a changed zone fetches the new period keys on its own, otherwise Retry refetches the period reads, and nothing is refetched once the page is gone. The subtitle and the timezone definition say that periods follow the reporting timezone. Dates are recomputed on render, not at midnight.
  - KPI strip (`Key metrics` region, `<dl>`): actual distance, accepted trips and active drivers. Active drivers is the number of leaderboard entries for the filters; the leaderboard is requested with `limit=100` (contract maximum) and shows `100+` when a next cursor exists. A failed leaderboard shows `Unavailable`, never `0`.
  - Distance card: Interval (Daily/Monthly) and View (Chart/Table) segmented controls; the reporting timezone and computation time stay visible. Chart view pairs the decorative bar chart with a visible peak summary. Table view shows the exact per-bucket table (caption with the reporting timezone, sticky header, peak badge) in a focusable scroll region named by its caption. The card body keeps one height across views and states.
  - My Qualification: per game (ETS2, ATS) the level badge, an eligibility badge and exact `trips` / `distance` values against the requirement with a decorative bar. Each game shows its own loading or `Progress unavailable` state; `No qualification assigned` appears only when the response has no assignment or the member cannot submit own trips.
  - Driver Leaderboard: top ten rows with rank badges for the top three, driver profile links, trips and distance, plus an `All drivers` link. Loading, failure (with Retry) and empty states are separate.
  - Side column: Review Queue for `trips.review` (count from the five-item queue request, `5+` when more exist) and the nearest convoy (`Upcoming Event` region).
  - Needs attention appears first in the side column and remains available when analytics fails. It shows server totals and ordered previews for returned trips, editing drafts and unanswered events, plus direct links to the awaiting review queue and submitted applications. Omitted sections are unavailable, and available zeros do not create navigation badges. The dispatch header shows the overall count and snapshot age independently of queue filters. Admin Members and Applications show the status counts returned by their respective lists. Usable invitations are a separate member metric.
  - Nearest convoy (VTC-055): title, start time with the viewer's display timezone, route, `Going: N` (`Count unavailable`, never 0, when the counts fail), a Details link and a compact countdown chip (`in 3 d 4 h`, `in 2 h 30 min`, `in 5 min`, `starting soon`). The countdown is plain text, never a live region; one timer wakes only when its text changes and also closes responses at the start, where the overview refetches the nearest event once and shows the next one. Members with `events.respond` get `Going` / `Can't go` toggles (`aria-pressed` from the server-confirmed response, `aria-disabled` while blocked, never `disabled`), the confirmed state line and a decline form with the required private reason (at most 2048 characters, a translated inline error for a blank reason). A conditional `Response saved.` status confirms success, and the events failure view shows conflicts, unknown results and rate limits. A conflict also rereads the nearest event, because the event may have been cancelled or rescheduled. Others see the count without controls and no own-response read. After the start the area links to the events list; if focus was inside the response area when it closes, it moves to the block heading.
  - Recent company trips (VTC-055): a full-width third row with at most five accepted company trips (game chip, `Origin → Destination` link to `/account/trips/:id` with the English-fallback marker, then driver · distance · counted time in the display timezone; `Unknown` places and `Unavailable` values, never 0) and an `All company trips` link to `/account/trips?scope=company`. It follows the game filter. On desktop it sits below the first 1280×800 screen: beside the leaderboard it would either halve the leaderboard or push its first row towards the fold.
  - Block states: each new block shows its own loading (decorative placeholders; the trips list is `aria-busy`), empty, error with Retry and forbidden (no Retry) state, and a block failure never triggers the page analytics alert. A failed Retry (recent trips, the nearest convoy and the own response) keeps the error and focus on Retry; a successful one moves focus to the block heading. The retained error ends at the next outcome, so another game or a later failure shows its own state.
  - Collapsible "How Metrics Are Calculated" card (`aria-expanded` / `aria-controls`).
  - States: a visually hidden status announces loading while analytics or the leaderboard is pending, static placeholders per block show it without shifting the layout, and the header controls stay usable. Every block renders its latest data when present and shows its own error only when it has none, so a failed background refresh keeps current values. An analytics failure without data replaces the KPIs and grid with an alert and Retry; Retry moves focus to the page title (or, for the leaderboard, its heading) because the button unmounts; members without `company.read` see an access notice and no dashboard query runs; an empty company shows a notice above the KPIs only when both analytics and the leaderboard answered with zero.
  - Layout: from 1051px a two-column grid (distance | qualification, then leaderboard | side column, then recent trips across both columns); below that one column in DOM order. Visual order matches DOM and keyboard order. Styles live in `features/dashboard/dashboard.css`, scoped to `.dashboard-page` and built from shared tokens; touch screens get the shared 40px targets.
  - Follow-ups: a deep link to the wide trip side panel (`?trip=`) once the trips list panel lands; clearing a response back to unanswered and the decliner count on the overview (the event detail page has both); leaderboard role chips, the qualification `Rules` link and the mockup placement of rows 1–2; an `events` area in the dashboard test selection. No data source: KPI deltas, member totals, review-age KPIs, next qualification level, a trips date filter and an event type.
- **Driver Directory (`/account/drivers`)**:
  - Filter by driver nickname.
  - Role badges: Director, Deputy Director, Dispatcher, Driver, Trainee.
  - Active vs Former Member indicators.
  - Links to individual driver profiles.
- **Driver Profile (`/account/drivers/:memberId`)**: a compact layout (VTC-061, board R11) built only from existing endpoints.
  - Header: decorative initial avatar, nickname as the page heading, role badges, `Active` / `Former member`, `You` on one's own profile, one chip per assigned game with the level name (`ETS2 · Driver II`; `Loading level…` / `Level unavailable`, never the level ID) and the game segmented control (All games, ETS2, ATS). A small `All drivers` link sits above. The breadcrumb is unchanged.
  - KPI strip (`Driver statistics, last 12 months`, `<dl>`): accepted trips, actual distance and this month (last bucket: distance plus trips and month). The window is a rolling twelve calendar months: from the first day of the month eleven months back to the first day of next month (`granularity=month`), within the 732-day API limit. Since VTC-078 the month is today's calendar month in the company reporting timezone, like the overview periods (`twelveMonthWindow(now, timeZone)` in `features/drivers/model.ts` on the VTC-056 `calendarToday`/`isoDate` helpers); the instant is fixed when the page mounts, so a midnight rollover never changes the window. Analytics waits for the shared stats read (`useReportingTimezoneSource`), so its first request already has the zone's dates; meanwhile the KPIs and the chart show their loading state (`untilAnchored`), never cached data or a cached error of the fallback key. The profile, trips, progress and level reads have no date window and do not wait, so the header and layout appear as before. UTC is the fallback when the stats read fails without data, the month is `unavailable` or the browser does not know the zone; retained data keeps its zone after a failed refresh. Zero shows as `0` / `0 km`; a failure shows an error with Retry, which first rereads a pending, failed or `unavailable` stats read (reusing a read in flight) and refetches analytics only when the zone did not change, because a new zone fetches its own key. 409 (no reporting timezone) shows the setup message without Retry. Without `company.read` no stats read runs.
  - Accepted trips: one completion-ordered page of at most ten. The request uses `scope=mine&decision=accepted` for self or `scope=company&ownerId=<id>` for another driver, with the selected game when applicable. The history link opens the corresponding filtered trip list. All-game lifetime accepted trips and exact actual distance come from `MemberProfile.lifetimeTotals` when available. Rows link to trip details and show the saved display timezone, actual completion, staff confirmation or other reporting time, cargo, source and actual distance. Phones (≤760px) show labeled cards with the same table semantics.
  - Qualification card per game (follows the game filter): level name heading, `Next: …` or `Top level`, the level ladder as a static progression (`<ol>`, decorative arrows, current step highlighted with `aria-current="step"`), exact trips and distance against the thresholds with decorative bars, `Promotion thresholds are not configured.` for null thresholds, the eligibility text with a ✓, and `Progress since` in the display timezone. No assignment shows `No qualification assigned` without a progress request; progress and level names load and fail per game.
  - Distance by month: Chart/Table toggle, reporting timezone from the response, peak summary under the chart, and an exact month table in a focusable scroll region named by its caption; the body keeps one height across states.
  - Requests and keys: `driver-profile`, `driver-analytics`, `driver-progress` (`EnvelopeProgressPublic`, only for assigned games after the profile loads) and `driver-accepted-trips`, keyed by member, viewer, session generation, identity epoch, capabilities, language and path; level names reuse the overview's `/qualification-levels?game=<g>&limit=25` read (only assigned games). The reporting timezone comes from the public `public-company-stats` read shared with the overview and the landing band; it is the first hook, so on a cold load it enters the read queue alongside the profile read. Switching the game refetches only analytics and trips. A 403 clears inactive private queries and refreshes the session, a 401 confirms session loss.
  - States: without `company.read` the page shows an access notice and mounts no query; profile loading keeps the heading and a hidden status line; 400/404/422 show `Driver not found` with a link back; 403 shows the access notice; other failures show an alert whose Retry keeps focus on the stable page heading.
  - Layout: one column below 1200px; from 1200px trips beside a 300px side column (340px from 1360px), which keeps whole Russian words in the trips table with the sidebar expanded. Trip and month tables override the shared break-anywhere wrapping with whole-word wrapping and automatic column widths. Styles live in `features/drivers/drivers.css`, scoped to `.driver-profile-page`, from shared tokens; touch screens get the 40px targets.
  - Omitted, with no data source in the API or policies (follow-ups): member-since date, Steam/TruckersMP indicators (privacy decision), average trip, convoy count, period select and pagination within the recent trips block, cargo mass and event marker, and the assigning person.
