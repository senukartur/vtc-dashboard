# Company Dashboard and Driver Profiles

VTC-033 delivers the company overview dashboard, driver directory, and individual driver profiles in VTCDashboard.

## Architecture and Endpoints

### Identity Module Endpoints (VTC-033 Owned)

- `GET /api/v1/members` (VTC-140 directory, `MemberStage4DirectoryListEnvelope`):
  - Requires `company.read`. Lists active and former members; `limit` is 1..100 (default 25; the directory and the event organizer picker ask for 25).
  - Filters apply before paging and combine with AND. `search` is the `listAdminMembers` nickname rule: trimmed, case-insensitive, literal `%` and `_`, blank or over 128 characters is 422. `role` is a current role; `director` matches only the serving director pointer. `status` is `active` or `former` (membership status `active` or `inactive`); omitting it lists both, and any other value is 422.
  - `ets2Level` and `atsLevel` accept a level that `listQualificationLevels` returns to the reader for that game, which is any active level of the game. Archived, other-game and unknown IDs return 422, as does any level filter without the Qualifications module. A member matches when its current qualification in that game is the level, so former members never match. The lookups are the swappable exports in `apps/api/src/modules/qualifications/directory-level-filter.ts`; the qualification model change (VTC-157) replaces only that file.
  - `sort` is `nickname`, `distance30d`, `trips30d` or `lastTrip`. `order` defaults to `asc` for `nickname` and `desc` otherwise; `order` without `sort` returns 422. Omitting `sort` keeps ascending member ID order. Every sort breaks ties by ascending member ID, and `nickname` compares with the column's case-insensitive collation. Members without an accepted trip sort last for `lastTrip` in both orders.
  - With Trips configured each row has `last30Days` (accepted unique canonical trips and exact distance with `reportingAt` in `[windowEndsAt - 30 days, windowEndsAt]`, zeros included) and `lastAcceptedTripAt` (null without any accepted trip, not capped by the window), and the page has `windowEndsAt`. Without Trips these fields are absent, never zero, and the three activity sorts return 422.
  - The first page takes `windowEndsAt` from the server clock. The signed cursor binds the actor, session, access epoch, normalized filters, sort and effective order, and carries the keyset position and `windowEndsAt`, so later pages keep the first page's window. `status` joins the binding only when present, so cursors minted without it stay valid; changing it either way is 409. Any mismatch or tampering returns 409 `VERSION_CONFLICT`. Activity comes from correlated subqueries over the `trip_owner_accepted_reporting` index; trip rows are not locked.
  - Every page has `statusCounts`: company-wide `active` and `former` totals that ignore search, role, level and status filters and the cursor. With Trips it adds `droveLast30Days`, the active members with at least one accepted trip under the `last30Days` rule and window (the cursor's `windowEndsAt` on later pages); without Trips it is absent, never zero.
  - With Qualifications every row has `levels` with `ets2` and `ats`, each the current level `{ id, name, position }` as `listQualificationLevels` returns it. A game is null without a current assignment, for every former member and when the level left the active ladder, so an archived name is never returned (the level filter still rejects such a level with 422). Without Qualifications `levels` is absent. One batched read covers the page's active rows; it and the lookup filter are the two exports of `directory-level-filter.ts` that VTC-157 replaces.
  - Lock order: company `FOR UPDATE`, actor check, level-filter row `FOR SHARE`, directory rows `FOR SHARE`, roles `FOR SHARE`, then the current levels and the counts as plain reads of the same transaction snapshot, which take no locks.
- `GET /api/v1/members/:memberId`:
  - Returns driver profile envelope (`EnvelopeMemberProfile`).
  - Contains `member` summary and active qualification `qualifications` assignments per game.
  - `memberSince` is the latest join or return (`identity_memberships.joined_at`). Registration writes it with the account creation instant and every reinstatement moves it to the return instant, the same instant as the reinstatement assignment and its audit entry; role and membership changes, deactivation and failed commands leave it. The first join stays in membership history. With Trips, `lastAcceptedTripAt` is the latest accepted trip time, or null.
  - Requires `company.read` capability.

### Consumed APIs

- `GET /api/v1/me/workspace-summary` (VTC-114, VTC-119): one private, language-independent snapshot for the signed-in shell, overview actions and review header. The cache is scoped by member, session generation, identity epoch and capabilities. The shell refreshes on visible online focus or reconnect. Confirmed trip, event and admission writes cancel obsolete reads and refresh the summary.
- `GET /api/v1/analytics/company`: Company aggregate distance and accepted trips with day/month buckets, plus the Stage 4 `activeDrivers`, `activeMembers` and `byGame` (VTC-143); an absent field is unavailable, never zero. All time sends `period=all_time&granularity=month` and no dates.
- `GET /api/v1/analytics/leaderboard`: Top drivers ranked by accepted distance and trips. The overview asks for `limit=10` (or `period=all_time&limit=10`) and reads the per-item `position`, `rankedMembers` and the viewer's own `viewer` row (null: not ranked; absent: unavailable).
- `GET /api/v1/analytics/company/breakdown` (VTC-112): one read per card, `dimension=route|cargo|source` with the period (dates or `period=all_time`), the selected `game` and `locale` (interface language); `limit=5` for route and cargo only, because the source split rejects it. Key `dashboard-company-breakdown` with member, generation, identity epoch, capabilities, language and path; a body for another dimension is a payload error. 403 and 401 are handled like the other overview reads.
- `GET /api/v1/public/company-stats`: only `currentMonth.reportingTimezone`, the zone of the overview period anchors (VTC-056) and of the driver profile's 12-month window (VTC-078); shared cache with the landing stats band.
- `GET /api/v1/members/:memberId/analytics`: Individual driver monthly distance and trips.
- `GET /api/v1/me/upcoming-event`: Next upcoming convoy or company event (the nearest `scheduled` event not yet started; the API has no event type, so the overview calls it the nearest convoy).
- `GET /api/v1/events/:id/my-response` and `PUT /api/v1/events/:id/my-response`: the overview's quick response (VTC-055), through the events feature's `useEventQuery`/`useEventCommand` with the event detail page's paths: `If-Match` only from the my-response ETag (a missing ETag blocks the command), `Idempotency-Key` reused for an unchanged retry, CSRF per command, one command in flight, 15 s abort and the Retry-After wait.
- `GET /api/v1/events/:id/response-counts`: participants count of the nearest convoy, refreshed after a committed response.
- `GET /api/v1/me/qualifications` and `/members/:memberId/qualifications`: Current qualification levels, progress and conditions.
- `GET /api/v1/trips`: Confirmed trip history (accepted trips only on driver profiles). The overview's recent company trips read `scope=company&limit=5&order=completion_desc` plus `game=` for a selected game (key `dashboard-recent-trips` with member, generation, identity epoch, capabilities, language and path; a 403 clears inactive private queries and refreshes the session, a 401 confirms session loss). Company scope is accepted-only. The block shows the latest trips across all time for the selected game.

## Privacy Safeguards

- **Strict isolation of private account data**: Member summaries, profiles, and directory listings never expose emails, passwords, password hashes, credentials, or session tokens.
- **Privacy tests**: Integration and end-to-end tests assert that no `@example.invalid` address, password hash, or credential token is present in serialized responses or client storage/DOM.
- **Privacy footnote**: the driver profile states under its trips that pending and rejected reports, their reasons and screenshots are not shown and that account details never appear on profiles. The profile requests only accepted trips, public qualification progress (`ProgressPublic`, no review flags) and no `/admin/*` or `scope=review` data.

## UI Components and Features

- **Company Overview (`/account/dashboard`)**: a compact layout (VTC-048) that keeps the key numbers, qualification progress and the leaderboard on the first 1280×800 screen.
  - Header: title, subtitle and filters on one row. The game filter is a segmented control (All games, ETS2, ATS) and the period is a labelled native select (This month, Last month, Last 30 days, Last 7 days, All time). Filters are local page state. All time (VTC-148) exists only on the overview (`overviewPeriods`, `periodQuery` and `effectiveGranularity` in `model.ts`; the trip list keeps `periods`): the reads send no dates and the distance card hides its Interval control and shows month buckets, keeping the chosen interval for the next dated period.
  - Period anchors (VTC-056): the periods are calendar dates around today's date in the company reporting timezone (`computePeriodDates(period, now, timeZone)` in `features/dashboard/model.ts`, `Intl.DateTimeFormat` plus calendar arithmetic), because the API reads `fromDate`/`toDateExclusive` in that timezone. The zone comes from `currentMonth.reportingTimezone` of the anonymous public company stats, read with the landing stats band's query key, reader and cache times (`useReportingTimezoneSource`, only with `company.read`). Analytics, the leaderboard and the overview's other reads (qualification progress, nearest convoy, review queue, recent trips, then the trip breakdowns) wait for that read. Meanwhile every block shows its loading state, never cached data or a cached error of the fallback keys, so no alert appears before the zone is known. They enable in one render, analytics and the leaderboard first, so their first request has the right dates and, on a cold load, enters the two-slot read queue before the other blocks; a filter change still sends one request per endpoint. The shell's nearest-event chip keeps its own observer. A failed read that is being reread (remount, Retry) also waits. UTC is the fallback when the read fails without data, the month is `unavailable` (no reporting timezone; analytics then answers 409 as before) or the browser does not know the zone; retained data keeps its zone after a failed refresh, and a browser reconnect does not reread a failed read (the UTC fallback lasts until Retry or a remount). The page Retry first rereads a pending, failed or `unavailable` stats read, reusing a read in flight; a changed zone fetches the new period keys on its own, otherwise Retry refetches the period reads and the breakdowns, and nothing is refetched once the page is gone. All-time keys have no dates, so Retry refetches them even when the zone changed. The subtitle and the timezone definition say that periods follow the reporting timezone. Dates are recomputed on render, not at midnight.
  - KPI strip (`Key metrics` region, `<dl>`, VTC-148): actual distance and accepted trips, each with an `ETS2 … · ATS …` sub-line when `byGame` has both games; active drivers from analytics (`activeDrivers`, which counts former members with accepted trips and can exceed the members count) with an `Active members: N` sub-line; and `My place` from the leaderboard: `N of M` (`position` of `rankedMembers`) with the viewer's distance and trips, `Not ranked` with `No accepted trips for the period` for a null viewer, or `Unavailable` for an absent viewer or a failed leaderboard. An absent Stage 4 value is `Unavailable`, never `0`. A sub-line is a second `<dd>` that wraps only between the games; while loading the tile reserves it (two lines in a strip narrower than 900px), so the strip keeps its height.
  - Distance card: Interval (Daily/Monthly) and View (Chart/Table) segmented controls; the reporting timezone and computation time stay visible. Chart view pairs the decorative bar chart with a visible peak summary. Table view shows the exact per-bucket table (caption with the reporting timezone, sticky header, peak badge) in a focusable scroll region named by its caption. The card body keeps one height across views and states.
  - My Qualification: per game (ETS2, ATS) the level badge and exact `trips` / `distance` values against the conditions with a decorative bar. Each game shows its own loading or `Progress unavailable` state; `No qualification assigned` appears only when the response has no assignment or the member cannot submit own trips.
  - Driver Leaderboard: top ten rows (rank from the server `position`, else the list order) with rank badges for the top three, driver profile links, trips and distance, plus an `All drivers` link. The viewer's own row carries a visible ` · you`; a ranked viewer below the top ten follows in a separate row (its own `<tbody>` with a separator) with the position, a link to the own profile, trips and distance. Loading, failure (with Retry) and empty states are separate.
  - Trip breakdowns (VTC-148, `features/dashboard/breakdowns.tsx`): Popular routes, Frequent cargo and How trips arrived for the page game and period. Routes and cargo are a ranked list (no table) of the top five: the labels in the interface language with the canonical city name and the English-fallback marker, a game chip under All games, the exact count (`12 trips`, Russian plural forms chosen with `Intl.PluralRules` in `tripsKey`) and a decorative single-series bar (one hue, no legend) relative to the largest item; the remainder (`Other routes`) and unrecognized trips (`City not recognized`) follow as muted rows only when above zero; with only unrecognized trips the card shows just that row, without an empty list. Labels wrap at whole words and IDs never show. The source split is a thin segmented bar (a zero part draws nothing) with legend rows that carry the swatch, the name, the exact count and the share (rounded per part), plus the note that manual reports count after review in Dispatch. Telemetry (`#3987e5`) and manual (`#d95926`) are dashboard-scoped categorical hues validated against `--surface` with the dataviz palette check (about 4.8:1 and 4.5:1). `--dashboard-source-undetermined` (`#64748b`) is an intentional neutral for `Source not recognized`, shown only when that count is above zero, not a third category: it fails only the check's chroma floor, by design, and its legend row always carries the text name. Only the route and cargo bar colour (`--chart`, about 2.2:1) is below 3:1; those bars are decorative, because the exact count is printed beside each. Each card is a region named by its heading with its own loading (`aria-busy`), empty (only for a computed zero total), error with Retry and forbidden state; a 503 without catalogs is the card's error.
  - Side column: Review Queue for `trips.review` and the nearest convoy (`Upcoming Event` region). The queue card shows the workspace summary's exact `reviewQueue.count`, the trips the viewer can decide without their own, so it agrees with the dispatch header and the menu; it is hidden when the summary omits the queue and shows its error only when the summary read fails.
  - Needs attention appears first in the side column and remains available when analytics fails. It shows server totals and ordered previews for returned trips, editing drafts and unanswered events, plus direct links to the awaiting review queue and submitted applications. An omitted section is simply not shown, never called partial or unavailable; "unavailable" is only the failed-load state with Retry. Available zeros do not create navigation badges. The dispatch header shows the overall count and snapshot age independently of queue filters; when the awaiting page lists the viewer's own trips, which the count excludes, it says that another reviewer decides them. Admin Members and Applications show the status counts returned by their respective lists. Usable invitations are a separate member metric.
  - Nearest convoy (VTC-055): title, start time with the viewer's display timezone, route, `Going: N` (`Count unavailable`, never 0, when the counts fail), a Details link and a compact countdown chip (`in 3 d 4 h`, `in 2 h 30 min`, `in 5 min`, `starting soon`). The countdown is plain text, never a live region; one timer wakes only when its text changes and also closes responses at the start, where the overview refetches the nearest event once and shows the next one. Members with `events.respond` get `Going` / `Can't go` toggles (`aria-pressed` from the server-confirmed response, `aria-disabled` while blocked, never `disabled`), the confirmed state line and a decline form with the required private reason (at most 2048 characters, a translated inline error for a blank reason). A conditional `Response saved.` status confirms success, and the events failure view shows conflicts, unknown results and rate limits. A conflict also rereads the nearest event, because the event may have been cancelled or rescheduled. Others see the count without controls and no own-response read. After the start the area links to the events list; if focus was inside the response area when it closes, it moves to the block heading.
  - Recent company trips (VTC-055): a full-width third row with at most five accepted company trips, labelled in the interface language (`locale` on the request) (game chip, `Origin → Destination` link to `/account/trips/:id` with the English-fallback marker, then driver · distance · counted time in the display timezone; `Unknown` places and `Unavailable` values, never 0) and an `All company trips` link to `/account/trips?scope=company`. It follows the game filter. On desktop it sits below the first 1280×800 screen: beside the leaderboard it would either halve the leaderboard or push its first row towards the fold.
  - Block states: each new block (also each breakdown card) shows its own loading (decorative placeholders; the trips list is `aria-busy`), empty, error with Retry and forbidden (no Retry) state, and a block failure never triggers the page analytics alert. A failed Retry (recent trips, the nearest convoy and the own response) keeps the error and focus on Retry; a successful one moves focus to the block heading. The retained error ends at the next outcome, so another game or a later failure shows its own state.
  - Collapsible "How Metrics Are Calculated" card (`aria-expanded` / `aria-controls`).
  - States: a visually hidden status announces loading while analytics or the leaderboard is pending, static placeholders per block show it without shifting the layout, and the header controls stay usable. Every block renders its latest data when present and shows its own error only when it has none, so a failed background refresh keeps current values. An analytics failure without data replaces the KPIs and grid with an alert and Retry; Retry moves focus to the page title (or, for the leaderboard, its heading) because the button unmounts; members without `company.read` see an access notice and no dashboard query runs; an empty company shows a notice above the KPIs only when both analytics and the leaderboard answered with zero.
  - Layout: from 1051px a two-column grid (distance | qualification, then leaderboard | side column, then the three breakdown cards and the recent trips, each row across both columns); below that one column in DOM order. Visual order matches DOM and keyboard order. Styles live in `features/dashboard/dashboard.css`, scoped to `.dashboard-page` and built from shared tokens; touch screens get the shared 40px targets.
  - Follow-ups: a deep link to the wide trip side panel (`?trip=`) once the trips list panel lands; clearing a response back to unanswered and the decliner count on the overview (the event detail page has both); leaderboard role chips, the qualification `Rules` link and the mockup placement of rows 1–2; an `events` area in the dashboard test selection. No data source: KPI deltas, the average trip, a personal daily chart and recent trips, review-age KPIs, next qualification level, a trips date filter and an event type.
- **Driver Directory (`/account/drivers`, VTC-145)**: a server-paged `DataTable` over `listMembers` (`features/drivers/DriversPage.tsx`, pure state in `directory-model.ts`, styles in `drivers-directory.css`).
  - Heading line `18 in the company · 15 drove in the last 30 days` from `statusCounts` (company-wide, ignoring filters); the second part is omitted without `droveLast30Days` (Trips off), the whole line without `statusCounts`. An ⓘ popover explains the 30-day rule with `windowEndsAt`. No plurals.

  - URL filters: `search` (300 ms debounce, replace navigation, Back/Forward restore the draft; the `listAdminMembers` normalization), `role` and `ets2Level`/`atsLevel` (In company only, hidden elsewhere; switching to another tab drops them, and `status=former` is never sent with them because deactivation clears access roles), a tab switch keeps `search` and an explicit sort, `sort`/`order` (written only when they differ from the tab default), `state` (Invited).
