# Transactional email

[VTC-014](https://trello.com/c/sRU44ZRa) supplies durable RU/EN account mail, a replaceable provider port, a synthetic local sink and a concrete Resend HTTPS adapter. Ordinary trip notifications do not use email. Provider acceptance, simulated delivery and receipt in a real inbox are separate facts. The owner selected preparation of Resend plus local verification on 2026-10-19; no provider account, verified sender, DNS change or real recipient is configured or claimed.

## Configuration and activation

`MAIL_MODE=disabled` is the default. Required identity delivery fails closed when disabled. `local` performs no network I/O and returns `simulated`; production configuration rejects it. It deliberately emits no body, address, code or inbox file. The focused integration fixture inspects the private decrypted request inside its isolated synthetic database to verify the actual recipient/template path. It does not establish real mail delivery.

For an explicitly authorized environment, configure these values through private environment/secret storage:

| Field | Meaning |
| --- | --- |
| `IDENTITY_ENABLED`, `IDENTITY_ORIGIN`, `IDENTITY_SECRET` | Existing [identity activation](../development/identity.md) and exact HTTPS production origin |
| `MAIL_MODE` | `disabled`, `local` or `resend` |
| `MAIL_ENCRYPTION_KEY` | Separately managed random 32-byte key as 64 lowercase hex characters; never reuse the identity/provider secret |
| `MAIL_SENDER` | One verified plain sender mailbox, without a display-name/header expression |
| `MAIL_API_KEY` | Private Resend credential, required for `resend` |
| `MAIL_TRACKING_DISABLED=true` | Operator attestation that open/click tracking has been disabled on the sending domain; the send API has no per-message tracking override |

Keep the encryption key available until every encrypted pending/ambiguous intent has been resolved or expired. There is no automatic key rotation/re-encryption tool. A missing/wrong key fails closed; do not regenerate the key to repair delivery. Run API and jobs with consistent mode, key, origin and provider account. Changing sender/templates/configuration does not mutate existing encrypted requests. Credential changes are conservatively treated as a different provider scope; this is an application safety inference, since public documentation provides no cross-credential/account deduplication guarantee. A keyed private binding freezes the original provider credential scope. Any credential change fails closed for existing intents, because a new key could belong to a different team with a different idempotency namespace. Rotation/recovery of pending work needs an independently reviewed reconciliation procedure.

Apply additive migration `0004_windy_ravenous` explicitly with the [migration runner](../development/persistence.md), using migration credentials. Startup never migrates. The existing published 0000–0003 bytes remain immutable. The runtime needs SELECT/INSERT/UPDATE on `mail_deliveries`, SELECT/INSERT/DELETE on `mail_commands`, and the existing queue producer grants. The worker needs SELECT/UPDATE on `mail_deliveries`, SELECT/DELETE on `mail_commands`, SELECT on identity company/membership/user/challenges and existing jobs grants. The prepared development grant command includes these narrow table grants; running that command or enabling mail on a host needs separate operational authorization. Merge does not apply these new grants or enable mail. Existing automatic development delivery is tracked separately; no manual host application was performed for this package.

## Producers, privacy and validity

`createMessaging(...).enqueue(tx, intent)` writes on the producer's exact UnitOfWork connection. Domain/generation changes, encrypted mail and the common `{deliveryId}` job either commit together or roll back together. No outbox subscription is installed, so the first-subscription routing measurement gate remains untriggered. Uniqueness is `(owner,generationId,kind)`; a keyed input fingerprint rejects changed reuse. Identical replay retains the delivery, job, frozen request and durable provider key. Security delivery IDs equal the identity challenge ID returned by the existing owner request; admissions producers receive the delivery ID directly.

AES-256-GCM uses a fresh nonce and delivery/version-bound authenticated data. Recipient, code/link, rejection reason and rendered request are encrypted in a MEDIUMTEXT column, separate from common jobs/events/audit/results. The technical rejection input ceiling is 8,000 UTF-16 code units, not an approved admissions business limit. The real MySQL fixture covers escaped characters and four-byte Unicode at that boundary. Only safe IDs, kind, state, attempts, times, version and fixed recovery categories leave the status serializer. Logs never include payloads, provider messages, receipts, SQL or exceptions.

Identity owns validity: current challenge ID/purpose/stage, ten-minute expiry, bounded attempts/consumption, active membership, all security epochs, serving director and bound active successor. Locale is captured from membership preferences. Identity replacement, consumption, exhaustion and account invalidation remove unnecessary ciphertext on the same transaction. The worker checks authoritative validity immediately before provider I/O outside locks. Replacement can race an already in-flight message; redemption still rejects the obsolete code. Network delivery and challenge replacement are not atomic.

Admissions VTC-015 owns application decisions, reasons/history, seven-day invitation generations, reissue and redemption. This card provides invitation/rejection producer and authoritative validity interfaces, with no production admissions adapter. Missing validity fails closed. Admissions must perform its checks on the supplied transaction, invalidate obsolete private delivery material, and retain its structured decision history independently. Failed email must never prevent a valid invitation's authorized copy-link action. Messaging never issues/reissues/redeems an invitation.

Accepted/simulated and definitively unusable private payloads are removed immediately. Ambiguous request material is retained only while it can support authorized reconciliation, then removed by the original expiry. Disabling mail pauses mail claims while preserving pending jobs; CLI output includes the configured mail mode. A preexisting missing-handler/invalid-version or exhausted queue failure is exposed as worker_configuration or attempts_exhausted rather than perpetually queued. It needs the owning workflow/configuration recovery, never a blind generic reopen. Every normal jobs pass attempts a keyless indexed bounded expiry sweep, including terminal jobs, and removes command-idempotency rows older than 24 hours. Paused delivery therefore needs no decryption/provider key for cleanup. On a pre-activation disabled installation, only precisely allowlisted missing-table/table-privilege errors produce an explicit configuration_pending cleanup result and fixed mail_cleanup_pending notice; this is never reported as completed cleanup. Other failures, including network errors and unknown COMMIT, still fail the pass. Enabled mail fails closed on every cleanup failure. Identity invalidation also clears obsolete material before expiry. Safe delivery/job evidence remains retained; this does not shorten admissions/report history or image retention.

## Retry, ambiguity and recovery

The first attempt marker commits before network I/O. The provider request, template version, recipient, sender and key are frozen at enqueue. Resend receives the same `messaging.mail:<delivery UUID>` key and byte-identical request on every retry. Requests/response consumption have a four-second upper cancellation bound and an 8 KiB response ceiling, with process/lease ceilings retained from [jobs](../development/jobs.md). The actual request budget also subtracts elapsed pre-fence COMMIT/preparation time from the authoritative MySQL lease and reserves six seconds each for the private receipt and queue completion. Exhausted budget or slow preflight prevents provider I/O. Durable acceptance is saved separately from queue completion, so later lease/completion failure cannot erase a known receipt.

Known rejections use allowlisted categories: rate limit (at least 60 seconds), daily quota (next midnight UTC), monthly quota (terminal until authorized recovery), authentication, validation, changed idempotent payload, concurrent matching request and temporary provider failure. At most five claims are permitted. Retry is allowed only if the original expiry and a conservative 23-hour provider idempotency window both cover the next attempt. A quota wait cannot burn claims in an immediate loop. Monthly/authentication failures may be retried by an authorized user after configuration/quota recovery within the original bounds. No caller may change target, payload, code, successor, expiry or key.

Transport loss, malformed/oversized provider responses, unknown acceptance and abandoned external claims remain ambiguous. They are never reopened by the resend endpoint. Unknown database COMMIT and lost-lease outcomes retain precedence over retryable-looking causes. A crash after the attempt marker can leave `attempting`; after 15 seconds status conservatively shows `ambiguous`, even if no request was actually sent. Reconcile privately with durable/provider evidence; do not assume failure, extend expiry, recreate a provider key or blindly resend after retention. No generic reconciliation mutation is shipped. The owning security workflow may issue an explicitly authorized replacement generation, retaining its current protection/coalescing rules.

`GET /api/v1/mail-deliveries/{deliveryId}` returns safe evidence and ETag. `POST /api/v1/mail-deliveries/{deliveryId}/resends` has no body and requires current session, exact Origin, signed session-bound CSRF, UUID Idempotency-Key and If-Match. Permissions are rechecked on the command transaction. Security mail is visible/retryable only by its account owner, including the serving director; general staff/deputies cannot inspect or resend that account's codes. Admissions requires `applications.manage`; inaccessible resources return 404. Accepted/simulated/ambiguous/obsolete/exhausted deliveries cannot be generically resent. Expired/replaced security work requires the owning flow. Command replay remains actor-scoped and authorized, with no secrets in its retained result.
