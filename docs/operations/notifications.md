## Hosted domain acceptance record

Create dedicated fictional owner, observer, dispatcher and director/deputy accounts through the reviewed staging admission/operator fixture workflow. Existing accounts and schema are never adopted solely because a fixture name matches. Record fixture ownership and cleanup/deactivation instructions privately before mutation. Prepare a mode-0600 private JSON configuration for `deploy/development/notifications-probe.mjs`: `origin`, `syntheticOnly:true`, and 1–4 `actors`, each with fictional `email`, private `password`, and `forbiddenCategories`. A timing actor may additionally supply `expected:{category,occurredAt,subjectId}`; the occurrence is the known synthetic source/domain instant, never a recent worker receipt substituted for old evidence. No configuration example contains actual credentials or host identifiers. With `VTC_NOTIFICATIONS_PROBE=synthetic-only` and `NOTIFICATIONS_PROBE_CONFIG` pointing to that private file, the commands are:

```sh
node deploy/development/notifications-probe.mjs exercise
node deploy/development/notifications-probe.mjs poll
```

`exercise` logs in through the real CSRF/session API, checks history, all preference/read operations and idempotent replay, then logs out and verifies 401. It increments only the dedicated fixture's preference version (same values) and reads its messages. `poll` takes twelve bounded 30-second cycles, uses recipient catch-up checkpoints without overlapping requests, records fixed count/status/duration fields and observed occurrence-to-poll timing, then revokes its own session. It prints neither credentials, IDs, messages nor response bodies. A successful probe alone does not establish the following wider scenarios; retain a sanitized pass/fail/duration record for each:

## Pause, rollback and partial application

For a normal feature pause, set `NOTIFICATIONS_ENABLED=false` in **both** API and worker private configurations and recreate those owned processes through the reviewed root operation. Delivery/reminder jobs pause; immutable events and producer-created intents remain. Event/RSVP writes retain current pending markers through their own schema without notification-table privileges. On re-enable the Events-owned current definition/response predicate filters both rows and unread counts before maintenance; enabled commands additionally invalidate obsolete saved reminders. Before re-enabling inspect failure/backlog counts and current event generations; expired reminder windows are skipped.

An application rollback keeps all additive `0016` tables and grants. Older producers may omit intents; the repeating primary-ID sweep discovers them after re-enable, including late commits after an earlier lap passed them. That recovery latency scales with retained history and must be measured separately from current producer delivery. Earlier application code does not expose the new routes. Re-enable only with matching reviewed API/worker code and keys, inspect cursor progress and allow a complete recovery lap before claiming complete historical delivery. Do not drop tables as a code rollback. Saved history remains subject to current permissions.

For interrupted migration/grants/configuration, preserve the exact image/revision, complete private grant/configuration hashes, fixed failure category and fence state. Use the [persistence recovery runbook](../development/persistence.md#partial-ddl-recovery-runbook) and [development recovery workflow](development.md), obtain a reviewed concrete repair/consistent restore, and read back actual schema/ledger/effective grants before resuming. A configuration rollback does not reverse DDL or erase prior effects. This prepared package has not been applied and contains no hosted acceptance claim.
