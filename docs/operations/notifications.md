This is an **unapplied** VTC-036 package for the existing VTC-011 development environment. It authorizes no deployment, account/resource setup, paid change, production operation or real mail. Apply only after separate owner authorization covers the reviewed revision, private configuration, restricted grants, schema changes and synthetic acceptance window. VTC-041 owns Hostland proof. Preserve the [development operations lock/fence](development.md), existing backup/restore procedures and current review/CI gates.

The fixed [window operator](../../deploy/development/notifications_acceptance.py), [isolated role manifest](../../deploy/development/notifications-acceptance-grants.json), [service template](../../deploy/development/notifications.acceptance.compose.yaml) and packaged [fixture](../../apps/api/src/notifications-acceptance.ts) prepare an executable acceptance window on existing infrastructure. They do not activate notifications in the normal shared application. Local execution results, exact-candidate review and actual hosted execution are separate evidence. Delivery reports record completed checks and failures; this source document establishes no hosted result.

Before approving application, privately inspect the currently accepted release/image, installed controls, exact MySQL baseline, actual minute cron and recent executions, operations/recovery state, absence of another window, and available memory/connections/disk. Do not assume an empty company. The window uses the **current ordinary CI-approved immutable image**, validated through the existing release path. If it lacks this fixture, separately approve the normal release/migration first; there is no alternate image-import path. Capacity failure does not authorize a paid upgrade.

These modes accept no caller SQL, paths, commands, image tags or feature overrides. `prepare` verifies fresh schema/account/network/container absence, binds the UUID/current release/controls/private configuration, records allocation intent before CREATE and acknowledged authority afterward, and creates an owned schema sentinel/account metadata. The combined normal jobs composition legitimately needs other modules' rights; the separate strict notification-worker rehearsal proves its narrower read dependencies.

The fixture generates independent keys and fictional identities/configuration. Production `readConfig` validates the real prerequisite chain with mail disabled and normal catalog checks. Provider credentials and egress attachments are absent. Owned source/admission/event/qualification/decision setup uses the owning module facades. Rule/threshold/timezone values are explicitly fictional, not company launch defaults.

The isolated source path calls Trips → Reconciliation refresh → rule snapshot/search advancement, and the normal jobs composition executes its bounded search continuation. Both isolated roles therefore receive SELECT/INSERT on immutable `reconciliation_rules`, SELECT/INSERT plus UPDATE(active) on `reconciliation_candidates`, and SELECT/INSERT plus the explicitly listed search-state upsert columns on `reconciliation_searches`. The upsert includes its unchanged `trip_id`, so that column is listed too. There is no table-wide reconciliation UPDATE, history/rule mutation, DELETE or grant for unexercised manual merge/reversal command/history writes. Runtime negative probes verify those denials and always roll back if unexpectedly permitted; exact effective table/column readback covers both roles. All four optional reconciliation tolerances remain omitted: the owning callback persists its documented immutable `rule:null` identity, without inventing matching defaults. These grants complete the fixed window's real source/search composition; they are not a shared activation profile or proof of manual reconciliation administration.

The combined isolated jobs role also includes the existing unconditionally enabled Catalogs maintenance: expiring command deletion, state/failure-only operation updates, byte/expiry-only artifact updates, state/pruned-only revision updates and deletion of rejected incomplete normalized rows. The owning cleanup selects only incomplete rejected revisions and preserves publication, revision metadata and reference locks. Its SQL role can delete normalized rows; this is not a universal SQL sandbox or a claim that SQL privileges alone prevent deletion of published rows. Separate guarded job-role probes permit only the required no-op maintenance statements and reject publication updates, revision-completion/artifact-identity/fact updates and immutable domain-history mutations. Runtime catalog read rights and shared profiles are unchanged. Existing Admissions/Mail cleanup rights remain; mail stays disabled. Optional manual storage is unconfigured in this fixed window, so normal manual maintenance explicitly reports `configuration_pending`; uploads/storage maintenance are **not run or proved** by this package.

Unknown CREATE acknowledgement, dirty/uncertain DDL/DCL or a mismatched schema/account/container receipt is a recovery blocker. Names, labels and CID files alone cannot establish ownership. Interrupted prepare is cleanup-only; never replay partial DDL, stamp migration receipts, adopt a matching name, or reset a shared schema/volume.

### HTTPS, scheduling and measurements

`start` creates an owned API and pinned internal Caddy proxy, with no published port, DNS or shared proxy change. Its internal subnet excludes Docker and host/VPN routes. API/worker/probe drop all capabilities; the proxy mirrors the existing proxy's sole `NET_BIND_SERVICE` addition, retaining read-only/no-new-privileges restrictions. Caddy uses `tls internal` and `skip_install_trust`; its private CA key remains in owned storage. Only its root certificate reaches the fixture through `NODE_EXTRA_CA_CERTS` **at Node process launch**. Normal SAN/hostname/chain/origin verification stays enabled; no system trust is installed or TLS check disabled. See [Caddy TLS](https://caddyserver.com/docs/caddyfile/directives/tls) and [Node process certificate loading](https://nodejs.org/api/cli.html#node_extra_ca_certsfile).

`exercise` starts the guarded asynchronous HTTP/domain fixture. Authentication, CSRF/session cookies, polling, history, preferences, read and read-through use actual HTTPS routes. It does not invoke workers. Leave the existing **real minute tick** installed: the active window retains heartbeat and directs only its jobs step to the owned schema's normal `dist/jobs.js run`. Normal shared jobs and conflicting release/activation windows stay fenced. No temporary accelerated cron or clock is used. Preserve the 40-second pass, 50-second hard watchdog, 100-job ceiling, route/lease/retry limits. A repeated invocation in the same UTC minute records a skip; it cannot accelerate work.

`pause`/`resume` change only owned scheduling; `overlap` runs two receipt-owned normal workers. The fixture may request its fixed pause/interruption/overlap stages through an owner-validated private exchange file inaccessible to API/HTTP callers. Interruption requires a real claimed job and recovery waits for natural leases; no lease/attempt reset is permitted. Inspect the window after each stage and keep all nine scenario results, including negative cases. A 7,200-second bound from prepare is an operator expiry safeguard, not a company policy or delivery guarantee. Expiry disables scheduling/stops owned processes and retains the fence until explicit safe cleanup.

The interruption fixture separates cold startup from the armed claim. Its producer transaction holds Identity's owning company writer fence while the normal worker reaches the positively bound pre-catch-up stage. Startup has a 30-second operator observation and 40-second fixture wait. A second pool connection must confirm the existing owner's recipient row is exclusively locked before the producer commits; only a known COMMIT receipt permits the bound armed signal. The original 10-second claim observation and 20-second recipient acknowledgement start after arming, and all worker observation operations share one absolute 55-second deadline. These are synthetic fault-injection coordination bounds; normal pass, hard watchdog, SQL, routing, retry and lease policies are unchanged. Failure cleanup keeps its existing bounded safe-stop path and cannot convert a timed-out observation into success.

Every startup, armed and stop acknowledgement binds the run, fresh request, exact worker CID and intended trip/source/outbox event. The job must match that immutable event and reference. After positive process absence, the captured job must still be running with an unexpired stored lease and attempt count. Recovery must increase that attempt count, retain exactly one effect per intended recipient, and have persisted `completed_at` at or after the captured old `lease_until`; poll wall time alone is insufficient. Application UUID columns retain their existing 36-byte ASCII representation (72 hex characters); Docker CIDs use 64 hex characters.

Private evidence includes source occurrence/receipt and indirect commit observation, poll/server times, every tick's real spacing/offset, work/backlog/oldest-due/scan cursor, bounded worker result and CPU sample. An unavailable CPU/due/scan sample remains null/uninitialized, never fabricated zero. Before generated files disappear, cleanup retains `state/notifications-acceptance-evidence.json`; the small terminal receipt binds its hash. Keep cursor/allocation/control/private inventory values private; publish only safe counts/ranges/durations/fixed categories, including cold/chained/backlog samples longer than the healthy approximately90-second target. Preserve the120-second freshness and one-hour reminder policy.

The retained bundle also projects the current allocation's parent tick receipt into closed validation/heartbeat/jobs statuses, categories, durations and timestamps. Missing, stale, mismatched or malformed receipts remain explicitly unavailable; a successful notification worker alone does not establish a successful aggregate tick. Scheduler failures retain a closed operation stage/code. Evidence or cleanup failures remain fatal and preserve an existing primary scheduler failure; failed cleanup retains its recovery fence.

Owned worker startup/failure diagnostics read both container stdout and stderr. Docker sends the latter to its CLI stderr, so the bounded root-private tail is captured immediately after the receipt-bound log command, before another control command can replace it. The private tail path is absent before that synchronous command and must be recreated as a root-owned private regular file; this binds the tail to the invocation without comparing filesystem timestamps with a userspace clock. Extra closed worker diagnostics activate only after the exact synthetic flag/run/schema/jobs account/build revision and root-created sentinel image/revision match. The runtime can update only sentinel `refs`, not ownership metadata. Ordinary workers perform no diagnostic lookup and retain their existing output. Matching owned workers expose only registered SQL operation/table/locking and stage categories, never SQL text, parameters, account/schema names or error bodies. The root collector filters these again against its packaged owned-schema table inventory and preserves the primary worker failure separately from a possibly collateral fixture HTTP teardown failure. Maintenance status, including explicit pending configuration, is retained with worker samples.

### Stop, cleanup and restoration

`stop` persists scheduling-disabled state and attempts every receipt-owned process stop/absence check. Any failed stop retains the fence. `cleanup` again verifies all stops, checks allocation acknowledgements/account metadata/schema sentinel, revokes owned sessions where available and confirms no active owned clients. It attempts independent safe account removals after a DCL failure and retains failed receipts. It removes only acknowledged owned accounts/schema/network/generated files, verifying absence before clearing the active marker. The shared application schema and unrelated company history are never adopted or deleted.

Account presence is explicit: a missing account row is an idempotent no-DROP case, while a present row with NULL, missing, empty, malformed or foreign ownership metadata retains the fence. A present account needs its exact typed run marker and acknowledged allocation, checked again immediately before its DROP. An earlier absent observation grants no authority to remove a later same-name replacement. The synthetic root rehearsal proves the distinction on its positively acknowledged disposable MySQL container and exact network/data-volume receipt; normal hosted cleanup does not require creating a fresh physical server.

Cleanup compares protected shared file hashes and actual pre/post privilege metadata digests. The baseline is captured before owned accounts exist and compared after all are absent; no name-derived account exclusion hides a collision. It reads no password/authentication material or routine bodies. A changed non-window grant preserves the fence and evidence; it never automatically reverts another administrator's rights. Reviewed inputs, private failure/evidence records and control backups remain retained separately from removed generated keys. Verify the sanitized terminal receipt, ordinary release/configuration/privileges and next normal minute behavior before declaring the window closed. Restore controls only after the owned window is fully cleaned.

## Pause, rollback and partial application

The isolated interruption proof preserves the original job lease and verifies that the acknowledged
worker is absent while its exact job is still running and unexpired. Its JSON projection explicitly
casts the SQL comparison to an unsigned integer, matching the strict numeric `unexpired:1` wire
contract. MySQL JSON functions encode an uncast boolean expression as a JSON boolean, which is a
different type ([MySQL 8.4 conversion implementation](https://github.com/mysql/mysql-server/blob/mysql-8.4.11/sql/item_json_func.cc#L1308)).
A closed observation of field types, state, attempt and relative lease time is retained
before strict validation, so an invalid proof remains diagnosable without exposing SQL values or
relaxing the lease checks. This does not change job leases, SQL deadlines or worker limits.

For a normal feature pause, set `NOTIFICATIONS_ENABLED=false` in **both** API and worker private configurations and recreate those owned processes through the reviewed root operation. Delivery/reminder jobs pause; immutable events and producer-created intents remain. Event/RSVP writes retain current pending markers through their own schema without notification-table privileges. On re-enable the Events-owned current definition/response predicate filters unread reminders and counts before maintenance; enabled commands additionally invalidate obsolete unread reminders. Already-read reminder history remains available under current access and never becomes live again. Before re-enabling inspect failure/backlog counts and current event generations; expired reminder windows are skipped.

An application rollback keeps all additive `0016` tables and grants. Older producers may omit intents; the repeating primary-ID sweep discovers them after re-enable, including late commits after an earlier lap passed them. That recovery latency scales with retained history and must be measured separately from current producer delivery. A recovered typed `event.changed` or `event.response_changed` first page also validates its immutable owning history and re-marks that Event for scheduling, on the same transaction as its consumer receipt. This repairs an acknowledged false marker preserved by a pre-0016 producer. Event marker ownership is acquired before shared Event history reads. The next bounded maintenance invocation seeds the current generation; this chained minute and history-dependent sweep delay are recovery latency, outside the healthy current-producer target. Earlier application code does not expose the new routes. Re-enable only with matching reviewed API/worker code and keys, inspect cursor progress and allow a complete recovery lap before claiming complete historical delivery. Do not drop tables as a code rollback. Saved history remains subject to current permissions.

For interrupted migration/grants/configuration, preserve the exact image/revision, complete private grant/configuration hashes, fixed failure category and fence state. Use the [persistence recovery runbook](../development/persistence.md#partial-ddl-recovery-runbook) and [development recovery workflow](development.md), obtain a reviewed concrete repair/consistent restore, and read back actual schema/ledger/effective grants before resuming. A configuration rollback does not reverse DDL or erase prior effects. This prepared package has not been applied and contains no hosted acceptance claim.
