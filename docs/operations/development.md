## Image-store compatibility before first release

Run image-store **steps 1–4 after steps 1–2 of [installation](#install-and-enable-the-single-path)**: Docker is installed, `install.sh` has created root-owned controls/private credentials/state, and its ephemeral setup container has exited and been removed. Keep deployment **disabled through image-store steps 1–4**. Then return to installation steps 3–6; perform image-store step 5 only after enablement as post-enable validation.

Prepared root-owned controls/state directories, private credentials, cached setup/dry-run images and diagnostics from a failed **pre-database** image-ID check are permitted empty-host preparation. Such a failed attempt does not itself make the host populated; the proof below still requires no accepted release/current metadata, database/evidence data, or running/stopped containers. Do not rerun `install.sh`, recreate credentials or drop data to satisfy that proof; populated or unowned resources require separate recovery review.

Fresh Docker Engine 29 installations default to the [containerd image store](https://docs.docker.com/engine/storage/containerd/), rather than the [classic storage drivers](https://docs.docker.com/engine/storage/drivers/). The selected pairing for this transport is the current classic CI artifact store and classic `overlay2` staging. This is an image-identity compatibility prerequisite, not a claim that the application cannot use containerd or a request to change local Docker Desktop/development storage.

The receiver requires the loaded image ID to equal the trusted CI manifest's ID exactly. An initial classic-to-containerd trial exposed different IDs despite matching revision labels/environment and was rejected before application/database creation. Those identifier semantics are an observation of that trial, not a universal cryptographic identity claim. Keep the mismatch guard unchanged: labels/tags are not a fallback, and homogeneous local rehearsal does not prove cross-store portability.

1. Keep deployment disabled and maintenance in place; wait for/acquire the operations lock. On **only the separately approved new VM**, privately prove there is no accepted release/current metadata, no database/evidence content in any volume or bind mount, and no running **or stopped** containers (`sudo docker ps -a`). Review the complete image/volume/network and on-disk store inventory; only approved new-VM resources may be present. If data, another workload or ownership is uncertain, stop for a reviewed backup/restore or migration decision and rehearsal. Do not apply this empty-host procedure to a populated host.
2. Preserve independent operator/console access and privately back up existing daemon configuration and service options. Merge the following feature into a **full private candidate** for `/etc/docker/daemon.json` (or the configured alternative); preserve every other setting and feature. This fragment is not a replacement configuration:

   ```json
   {
     "features": {
       "containerd-snapshotter": false
     }
   }
   ```

3. Independently review the concrete merged candidate and reconcile daemon command-line/service flags. Validate the full candidate without starting another daemon; a successful JSON parse alone is insufficient. See the [daemon configuration reference](https://docs.docker.com/reference/cli/dockerd/#daemon-configuration-file).

   ```sh
   sudo dockerd --validate --config-file PRIVATE_CANDIDATE_JSON
   ```

4. Only after the empty-host proof, review and validation, the root operator installs that reviewed candidate at the existing daemon configuration path and restarts Docker. Keep raw configuration/readbacks, actual IDs and host details private:

   ```sh
   sudo systemctl restart docker
   sudo docker info --format '{{.Driver}}'
   sudo docker info --format '{{json .DriverStatus}}'
   ```

   Require `Driver` = `overlay2`, no `io.containerd.snapshotter.v1` driver-type marker, and continued absence of containers/accepted state/data before delivery. On restart/readback failure, keep deployment disabled and restore the validated prior configuration through the independent operator channel. Switching stores can hide the other store's images/containers while retaining them on disk; reverting the configuration restores that view. Do not prune, delete volumes or remove either store's files as part of this operation.
5. After completing installation steps 3–6 and enabling protected deployment, revalidate the exact successful-CI artifact through the normal protected automatic delivery and then historical manual redeployment, followed by all persistence/recovery/isolated-restore and hosted acceptance cases below. The loaded-ID guard must pass unchanged; mismatch remains a failed deployment even when CI passed. Every Docker upgrade, CI runner/image-store change or transport change requires renewed source/target identity proof. Setup/readbacks alone do not complete VTC-011. Node/MySQL pins, encryption, grants and durability remain unchanged; no script purchases resources or changes host storage automatically.

## Install and enable the single path

1. Review the exact merged source and actual checkout total. Install maintained Docker/Compose and operator prerequisites on the approved new VM. Apply reviewed updates/firewall/swap and verify console recovery. No script creates or purchases a provider resource.
2. Run `sudo sh deploy/development/install.sh` from the reviewed checkout. It refuses an existing installation and creates root-owned `/opt/vtc-development`, random private credentials and the restricted deploy account. Keep receiver, Compose, private files and code root-owned and unwritable by deploy. Private configuration is mode 0600 in a 0700 directory, except the dedicated bootstrap directory/file, which grant only pinned MySQL gid 999 the read/traverse access needed inside its read-only mount. The enclosing host private directory stays root-only. Never run this on another development or production server. After its setup container is removed, complete [image-store steps 1–4](#image-store-compatibility-before-first-release) while deployment remains disabled, then continue with installation steps 3–6 and finish image-store step 5 after enabling.
3. Privately replace the `example.invalid` DNS/TLS placeholders in `private/proxy.env`. On an existing volume, editing bootstrap credentials does not change stored MySQL users. Never delete a volume to repair credentials.
4. Install the public deploy key using `authorized_keys.example` into a root-owned, mode 0644 authorized_keys file in the root-owned deploy home/.ssh. Prepare a private full candidate `sshd_config` by appending the complete `sshd.example` at EOF after the host's global configuration. Verify that this insertion point is still global: `PermitUserEnvironment no` must precede the first active `Match`. Reconcile any existing conditional blocks separately while preserving their policy, and any earlier global `PermitUserEnvironment` value so the effective value stays `no`. Use this reviewed EOF layout rather than an early `Include`/`sshd_config.d` placement or a `Match all` workaround. Include/scope behavior depends on the complete configuration and server version; a local parser accepting another layout does not establish its portability or actual target policy. The [OpenSSH configuration manual](https://man.openbsd.org/sshd_config#Match) lists permitted conditional directives.

   Before installing/reloading, run `sshd -t -f CANDIDATE_CONFIG` on the full candidate and `sshd -T -f CANDIDATE_CONFIG -C user=vtc-deploy,host=client.example.invalid,addr=192.0.2.2`, then inspect the independent operator's effective context as well. Require public-key-only deployment authentication and disabled password/keyboard-interactive authentication, TCP/agent/X11 forwarding, PTY/tunnel and user-environment processing; review existing `AcceptEnv`/`SetEnv` for unsafe environment injection. Preserve the independent operator's intended key access and console recovery, and validate the exact sudo entry with `visudo`. Keep a second authenticated operator session and console access through installation, reload and fresh operator/deploy access checks. Test arbitrary shell commands, forwarding, malformed/oversized/interrupted uploads are rejected. Parser/configuration checks do not prove effective authentication or forced-command enforcement. SQL/root/probe credentials never enter GitHub.
5. Configure GitHub environment `development` with **main-only** branch policy and read back that restriction. Store only `DEVELOPMENT_SSH_TARGET`, `DEVELOPMENT_SSH_KEY`, `DEVELOPMENT_KNOWN_HOSTS` as environment secrets. Pin the host key after independent console comparison; keyscan alone is insufficient. Keep the real hostname out of environment URLs, PRs and CI output.
6. Keep repository variable `DEVELOPMENT_DEPLOY_ENABLED` absent/false until the reviewed setup and actual costs/access are ready. Set it to `true` only during separately authorized provisioning. The new workflow must be merged onto main before its first workflow_run/dispatch. CI/review gates still apply to the bootstrap PR.

The workflow accepts only CI completion and manual dispatch. Both execute control code from main, use the same validator, and require canonical repository/workflow, successful completed main-push CI, full merged-main SHA, exact run/attempt and one unexpired artifact. Automatic candidates must still equal current main. Manual dispatch itself must use main and identifies a historical merged SHA; it cannot rebuild or consume PR artifacts. Missing/expired artifacts fail closed. Main Required CI includes quality, deployment rehearsal and artifact publication. PR publication is deliberately inapplicable; unknown/skipped main outcomes fail.

CI builds the production image with immutable revision metadata and uploads only `image.tar` and closed `release.json` for seven days. Strict zip layout, expansion bounds, lengths, hash and revision/run/attempt bind the archive. It contains no environment, backups, uploads or diagnostics. Eligibility and archive validation precede SSH-secret use. Strict pinned host-key SSH uses one receiver protocol; callers cannot supply paths, environment, Compose or shell. Public logs contain fixed result categories/revisions, never commands, target, raw SQL, expanded configuration or child errors.

The receiver compares the loaded revision tag's image ID with the manifest ID supplied by the validated transport, then selects that immutable ID explicitly through `VTC_IMAGE_ID`. Current/previous metadata and export manifests retain the exact image ID. Runtime, migrator, heartbeat, file helpers, recovery and isolated restore use those IDs; the mutable revision tag is never a recovery selector. A later successful rebuild for the same SHA may have a different ID and cannot replace the accepted recovery reference merely by retagging. Root control code is installed from the reviewed source independently of the image artifact. Later root control/configuration changes require a reviewed operator update preserving private configuration/state and recording source provenance; CI never overwrites its forced-command policy.

## Runtime, releases and failure recovery

Only the proxy exposes ports and it has no evidence mount. App/probe run non-root with read-only roots, dropped capabilities, bounded logs/resources and no Docker socket. SQL is on an internal network. The separate authenticated probe adds no domain API/authentication. Only root/operator can inspect Docker; deploy is not in its group.

Trial caps are MySQL 512 MiB, app 192 MiB, probe 64 MiB and proxy 64 MiB; short migration replaces stopped app/probe and minute heartbeat uses 64 MiB transiently. MySQL uses 128 MiB buffer pool, bounded temporary tables, 24 connections, performance schema, and dedicated-server auto tuning off. Durability (flush-on-commit and sync-binlog), strict SQL, UTC and exact baseline remain enabled. Headroom is limited and must be measured. Current lazy connections are five readiness slots, one probe, heartbeat and migrator each; future UnitOfWork/jobs/replicas require renewed capacity/grant review.

Runtime can read the schema but has no DDL/global/cross-schema or migration-ledger writes. Future table DML grants belong to their schema owners; the scaffold has no runtime domain commands. Migrator has schema DDL/DML, exporter reads the two schemas, probe reads only its synthetic heartbeat and heartbeat writer changes only that table. Root/bootstrap credentials stay private. Operations SQL is separate from the production Drizzle journal.

One host flock serializes release, migration, export/restore and cron. The receiver validates bounded upload/hash/tar members and disk space, loads the image, enables maintenance, stops writers, exports consistent pre-migration state, runs the packaged explicit migrator, starts app/probe and checks database readiness plus trusted HTTPS/revision through authenticated operator readiness. The operator readiness proxy can verify the candidate while public app traffic remains in maintenance. Current/previous metadata is promoted before that maintenance fence opens. GitHub concurrency never cancels an active release; an independent high-water mark prevents lower automatic run IDs after manual rollback too. Historical redeploy is explicit. No automatic image pruning removes current/previous or export-required images; review disk before retaining further releases.

Before migration, durable `state/recovery-required` intent fences even an uncatchable receiver death. Only complete promotion or verified zero-migration recovery clears it. Upload timeout applies only to receipt, and is cancelled before release. Caught migration interruptions stop the fixed migrator and SQL server; marker state blocks ordinary export/cron/seed/release. Migration failure preserves maintenance and sticky `applying` ledger. Disconnect alone does not prove server DDL stopped. Never clear a marker or replay blindly. Failed readiness can restore the previous image only when the CLI proved **zero** newly applied migrations; verify that recovery. New/uncertain schema work requires forward repair or a tested consistent restore. Image rollback does not undo DDL. After mail has actually been activated, a rollback must retain a mail-compatible worker or stop workers until an approved compatible image is restored. A pre-VTC-014 worker cannot pause mail.deliver and could terminalize retained pending mail as missing-handler failures. With a compatible worker, use MAIL_MODE=disabled consistently to pause delivery while retaining keyless expiry cleanup; preserve existing keys and frozen pending intents. Verify worker/image compatibility before clearing the maintenance fence.

## Export and isolated restore

```sh
sudo python3 /opt/vtc-development/operations.py export
sudo python3 /opt/vtc-development/operations.py restore EXPORT_ID
```

Export holds the same lock, maintains a write fence over app/probe and cron, dumps both InnoDB schemas in one consistent snapshot, archives evidence while stopped, and writes a revision/length/hash manifest. This includes migration history and synthetic references. Failure keeps maintenance. Success restarts/verifies the app. Provider snapshots supplement this coherence proof.

For the initial fictional reference proof, run root operator `python3 /opt/vtc-development/operations.py seed-synthetic` after the first accepted release. It fences writers, writes one fixed fictional evidence sentinel and its content hash into the separate operations schema, then resumes/verifies. Export and isolated restore compare that SQL reference to the evidence inventory. It creates no application identity, report, upload endpoint or domain migration.

Restore validates the full manifest and evidence archive **before** touching SQL. It fences/stops active writers and active MySQL to avoid assuming two databases fit in 1 GiB, then creates fresh private MySQL/evidence volumes. It imports SQL, checks the exact baseline and clean immutable migration replay, and compares file content/length inventory and synthetic SQL references. It leaves isolated volumes stopped for private inspection. Active volumes remain untouched; only a clean active state is resumed and verified afterward. Recovery-required state stays fenced for an explicit reviewed repair/cutover. Tar ordering/metadata is not used as content identity. Preserve independently recoverable image/configuration/tools as well as the export.

Stream a selected export tar into private owner-local storage and encrypt there with pinned Node and `recovery-copy.mjs`: `key KEY_FILE` creates a 32-byte key; `seal ENCRYPTED_FILE KEY_FILE` reads stdin; `open ENCRYPTED_FILE KEY_FILE RESTORED_TAR` authenticates/decrypts. AES-256-GCM, exclusive output acquisition before ownership-based cleanup, and authenticated publication protect the copy. Repeated seal/open output names fail without removing or changing an existing copy. Store the key separately; never print/commit it or use public CI artifacts for copies. Verify independent-copy checksums and perform isolated restore from that decrypted copy, retaining the manifest's immutable image as well. Verify destination ownership/access/free space and zero incremental cost before claiming it exists.

This initial manual synthetic exercise is not ongoing data protection. Before pilot/real data, approve sustained cadence, retention, independent destination ownership/capacity and scheduled restore proof consistent with the one-year/latest-decision and under-review screenshot policy.

## Durable jobs: existing-installation update and acceptance

VTC-021 prepares these controls; source merge/rehearsal does not apply them to staging. Actual hosted application, migration, grants, cron and acceptance need the scoped owner authorization recorded in the delivery report. Do not rerun fresh-host `install.sh`/`setup.mjs` on the existing installation or overwrite its private configuration. No paid resources or telemetry changes are needed.

After exact-candidate CI/independent review and authorization, an operator uses the reviewed source package and eligible immutable image through the established release path. Preserve the current accepted revision/image, private configuration and consistent recovery copy. The update sequence is:

1. Run the reviewed `deploy/development/update-controls.sh` as root from the reviewed package. It takes the existing operations lock, refuses recovery state, atomically installs fixed controls and creates only a missing private jobs credential. It preserves other secrets/settings/volumes and does not install cron. The Compose file needs `private/jobs.env` even before a tools command; that is why configuration precedes migration.
2. Apply the additive migration through the existing serialized eligible-image release/migration procedure, with maintenance and backup/restore fences. Published 0000–0002 checksums must remain intact; `applying` remains a recovery stop. Never use runtime jobs credentials for migration.
3. Run `python3 /opt/vtc-development/operations.py jobs-grants` under the fixed root controls. It is rerunnable and uses table-level SELECT/INSERT/UPDATE for jobs, SELECT/INSERT receipts, SELECT/INSERT/UPDATE/DELETE runner leases, SELECT/INSERT outbox, and append-only outbox/job producer INSERT grants. It grants no worker DDL, migration-ledger or identity writes. Verify both successful operations and denied CREATE, identity mutation, outbox UPDATE/DELETE and migration-history writes with the jobs credential; retain only categories/counts publicly. Existing credentials are preserved. A missing credential for an already-created differently configured account requires owner recovery rather than password replacement.
4. Verify accepted image ID/revision and the bounded jobs result, then explicitly install the reviewed `cron.example` as root cron. The single fixed `tick` minute command validates the accepted image, attempts heartbeat first with its existing 30-second client budget, then attempts jobs under the same nonblocking operations lock. A jobs failure therefore cannot suppress the preceding heartbeat attempt. An ordinary heartbeat client failure permits jobs only after successful cleanup and with both maintenance/recovery fences still clear. Cleanup/control failure prevents the later writer. A busy lock skips the whole tick immediately with nonzero status and leaves the previous tick record unchanged; ticks never queue. During an acceptance window, tick explicitly skips ordinary jobs while still attempting heartbeat. The private `tick-last.json` records fixed per-step status, attempted UTC seconds, duration milliseconds and allowlisted failure categories. A failed attempt records `finishedUtc`, returns nonzero and has no `completedUtc`; `completedUtc` means all required steps succeeded, with an acceptance-window skip explicit in the jobs step and overall status `completed_with_skips`. Maintenance/recovery fences prevent either writer from starting. The jobs service has no ports, Docker socket or evidence mount, uses the immutable accepted image, 96 MiB/0.25 CPU/32 PID ceilings and a five-slot UnitOfWork. The ordinary handler registry is empty; retained access events are honestly unbound.

The worker's independent 50-second supervisor and 55-second Docker client budget do not bound the full tick. The configured subprocess timeout totals below are conservative maxima along the full two-writer path; successful calls normally finish earlier. Process creation, scheduling, private file writes/fsync and timeout cleanup add overhead, so this is not a hard wall-clock guarantee. An overrun holds the shared lock and the following minute skips; unhealthy dependencies can therefore delay heartbeat cadence. Actual host measurements remain required, with no 60-second tick or 90-second freshness SLA claimed.

| Tick operation | Configured subprocess budget |
| --- | --- |
| Initial accepted-image inspection and jobs image reinspection | 10 seconds each, 20 total |
| Each owned-container cleanup | Inventory 10 + batched inspect 10 + batched remove 20 + absence check 10 = at most 50 seconds; no containers uses 20 |
| Heartbeat, including cleanup before and after its client | 30 + 2 × 50 = 130 seconds |
| Jobs, including cleanup before and after its client | 55 + 2 × 50 = 155 seconds, plus the image reinspection above |
| Full tick configured child-operation total | 20 + 130 + 155 = 305 seconds, plus local overhead |

Every release, migration, export and restore shares the root operations lock. `fenced()` removes and verifies absence of only the four fixed Compose-owned jobs/acceptance/heartbeat containers before stopping app/probe. Each cleanup inventories those exact names together and validates every returned container ID/name/project/service before any removal. Jobs and heartbeat completion/timeout do the same before relinquishing their writer fence. Cleanup failure persists maintenance/recovery state; do not clear it until owned container/SQL state is understood. A Docker client timeout does not establish container or server cancellation.

For actual acceptance, choose a new synthetic UUIDv4 run identity, never a real member ID. The following fixed commands accept only the validated UUID and closed modes; run them through the root operations tool, not a public API:

```sh
python3 /opt/vtc-development/operations.py jobs-acceptance prepare <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance seed <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance seed <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance contend <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance run <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance inspect <synthetic-run-uuid>
python3 /opt/vtc-development/operations.py jobs-acceptance cleanup <synthetic-run-uuid>
```

`prepare` installs the independent fixture counter and narrow INSERT/SELECT fixture privilege and persists an acceptance marker. Ordinary jobs refuses this window, avoiding accidental consumption by its empty registry. `contend` runs two direct consumers from the same immutable image; the single-runner path remains `run`. Deliberate retry availability may require a later minute/run. The expected completed result is ten stage-1 and ten stage-2 rows with each touch count one; duplicate seed never adds effects. The private bounded inspection file contains only fixture counts/stages, no raw payloads.

Use separate fresh run identities/windows for `crash-claim`, `crash-effect` and `hang`. Their nonzero exit is intentional: confirm claimed leases persist, wait for database expiry, resume and verify exactly one fixture effect at each stage. `crash-effect` exits after committed effect/chaining; `hang` is killed by the independent 50-second supervisor/55-second host ceiling. Exercise actual SIGTERM during a claim, later recovery, two simultaneous minute invocations, runner-token loss, a >100-job fixture backlog using `seed-backlog` (150 stage-1 jobs), and chained work across the remaining pass budget. Do not shorten the real lease/schedule to claim host proof.

For the no-visitors schedule window, leave the actual minute cron installed and invoke the explicit acceptance composition on minute boundaries through a temporary root-owned cron invoking the exact validated run/mode (same operations lock). Ordinary jobs remains blocked by the acceptance marker. Record scheduler timestamps, processed counts, due age/count, retry/chained-stage latency, duration, CPU, peak RSS/container memory, swap, OOM/restarts and MySQL connections. The potential pool arithmetic is 5 readiness + 5 API + 5 worker + 1 probe + 1 heartbeat = 17 before admin, versus max 24; this is not measured capacity. Test operations lock denial, maintenance and recovery fences with actual worker state. No automatic host upgrade is authorized by a capacity failure.

`cleanup` deletes only acceptance.counter receipts/jobs and counter rows for the exact run UUID, revokes the fixture privilege and removes its window marker. It never resets platform/domain tables or changes other fixture runs. Preserve receipts until verification has been recorded. Remove only the temporary acceptance schedule/credential controls, retain the ordinary approved jobs/heartbeat schedule and private runtime credential, and verify ordinary jobs reports retained unbound events honestly. The empty fixture table may be removed separately only after proving no other acceptance rows exist. Host results and cleanup evidence must be recorded before VTC-021 Done; local integration/rehearsal cannot replace that gate. Downstream notifications/trips/mail and Hostland compatibility remain separate.

## Prepared transactional mail package

VTC-014 adds encrypted mail migration/configuration and narrow runtime/worker table grants to the existing explicit jobs-grants operation. It does not run that operation on a host. Configure API and worker consistently only after the [email activation gates](email.md) are satisfied. Worker identity validity uses shared locking reads, so SELECT grants suffice without identity writes. Existing jobs uses the internal database network; real Resend activation additionally needs a separately reviewed outbound HTTPS/DNS network policy for the worker, while keeping inbound ports closed.
