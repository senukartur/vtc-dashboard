# Telemetry ingestion contract v1.0

**Status:** VTC-003 candidate for owner/telemetry-maintainer agreement, not an implemented API. **Date:** 2026-10-17. **Source baseline:** [telemetry discovery](../research/telemetry.md). **Card:** [VTC-003](https://trello.com/c/lQrxZ13N).

This contract bridges the local ETS2Telemetry recorder and this dashboard. Its HTTP version is independent of native Named Pipe protocol v1 and trip-export format v1. The [concept](../../CONCEPT.MD) governs qualifications, privacy, manual reports and analytics. The [request schema](telemetry-v1.schema.json), [examples](examples/README.md) and [acceptance matrix](telemetry-v1-acceptance.md) belong to this candidate.

## Scope and initial synchronization

Send lifecycle summaries, not one-second samples, positions, raw event streams, screenshots, process/window details or local filesystem paths. The owner requires **automatic upload of all retained local game trips on first connection**, then new trips and subsequent material changes. This includes open, delivered, cancelled, partial and interrupted records; appearing in the trip list does not imply company acceptance or inclusion in totals.

Initial enumeration takes a durable local high-water mark, walks bounded pages, and records its cursor and pending work. New recording continues through the normal change journal; overlapping pages/live changes use the same trip/revision identity. A restart resumes enumeration, not a new import. Upload every retained eligible record eventually, without a fixed age cutoff. The client cannot promise to upload history already deleted locally or records never captured while game recording was disabled.

Bind previously unbound records once to the first connected account; show that account and the initial synchronization scope before connection. No per-trip selection is required. Previously bound records remain with their owner; another token must not reassign or send them under a new owner. A restored/copied local database preserves trip IDs and ownership metadata. Unknown provenance is retained and evaluated under normal evidence rules; age or backfill mode alone does not force manual review or guarantee automatic acceptance. This first-binding trust boundary requires owner/maintainer acknowledgement: the current SDK cannot prove who drove legacy unbound history.

The owner confirmed that this is client-to-server synchronization. Dashboard manual-only trips are not downloaded into the local telemetry journal in MVP. Server-to-client history restoration remains VTC-110; it must not be confused with initial upload. Local and dashboard rows may show different acceptance/review metadata. The remote receipt below confirms delivery, not final company acceptance.

## Authentication, binding and token lifecycle

All routes require HTTPS and a personal bearer token in `Authorization`, never URL/query, body or logs. Dashboard browser sessions create/revoke/rotate tokens through authenticated member APIs; the telemetry token cannot administer users, approve reports, read other drivers or mint more tokens.

Use at least 256 random secret bits; display once, store a one-way hash plus a nonsecret lookup prefix server-side, compare safely and record last use without the secret. Keep the client secret in OS-protected main/service storage, outside renderer state, localStorage, exported JSON, SQLite trip rows and diagnostic output. Redact headers at application/proxy/error boundaries. Never forward credentials across redirects; use a fixed configured dashboard origin. No paid service or production endpoint is established by these route names.

The server authenticates an active linked member, checks token scope/revocation on every request, and derives user/company from that token. Payloads contain no writable `userId`, roles, Steam owner or company selector. A dashboard-verified Steam link is a separate identity check, not proof that SDK records were generated by that Steam account.

| Route | Request and durable result |
| --- | --- |
| `GET /api/telemetry/v1/connection` | Return supported contract versions/limits and authenticated `accountId`, `companyId`, `identityEpoch`; `Cache-Control: no-store`. These are local binding metadata, not client-selectable upload ownership |
| `POST /api/telemetry/v1/installations` | `{contract:{major:1,minor:0},clientInstallationId:<opaque UUID>}`. Register/reuse an installation for the authenticated owner and epoch, returning `installationId`, `bindingId`, `identityEpoch`. Persist before success; retries return the same registration. A different account uses a distinct registration and cannot adopt old queued work |
| `POST /api/telemetry/v1/events` | One schema-valid frozen lifecycle snapshot, at most 65,536 UTF-8 bytes. Returns a durable receipt or the error table below |

An owner binding includes the account, company, identity epoch and service origin. The epoch changes after Steam replacement/relink requiring re-verification; tokens are revoked as required by the concept. Ordinary rotation for the same account/epoch may resume old queued work with the new token. Deactivation blocks new ingestion. Reinstatement does not revive revoked tokens. Pending work from an older identity epoch is held for explicit reconciliation, not silently retried as the new identity. No expiration policy is invented here: a token is valid until revoked or otherwise made ineligible under account policy.

## Request envelope

All keys shown in the schema are required; explicit `null`/availability carries absence. Unknown keys and unsupported minor versions are rejected. Objects below are closed objects. The schema enforces structural shape; the semantic requirements in this document also apply.

| Field | Meaning |
| --- | --- |
| `contract` | Exact `{major:1,minor:0}`; use a new supported minor/schema to add fields |
| `producer` | `{application:"ets2telemetry",version:<bounded version text>}` |
| `eventId` | Lowercase UUID-shaped opaque ID, generated once and stored with the frozen event |
| `revision` | Positive safe integer, strictly increasing per source trip for material snapshots; gaps allowed |
| `installationId`, `bindingId` | Server-issued registration/binding IDs, validated against authentication |
| `source` | `{provider:"ets2telemetry",game,tripId,pluginSessionId,databaseUuid,origin:"game"}` |
| `delivery` | `{mode:"live"|"backfill",syncRunId:<UUID>}`. Original classification/run is frozen; retries do not rewrite it |
| `type` | One lifecycle event from the next table |
| `createdUtcMs` | Client time when this upload event was frozen, not source occurrence or server receipt time |
| `snapshot` | Full current trip summary including evidence; end-before-start delivery must not need an earlier HTTP request |

Existing `tripUuid` becomes `source.tripId`. Accept lowercase 8-4-4-4-12 hexadecimal IDs without imposing RFC UUID version bits. Decimal source sequence/clock values remain strings with uint64 range validation; never JSON numbers. Source trip identity is `(provider, game, pluginSessionId, tripId)` and must survive token rotation, reinstall/database-copy retries and initial/live enumeration overlap. `databaseUuid` is provenance, not an extra deduplication dimension. Never match or generate a trip ID from route/cargo/name/time alone.

## Lifecycle and revision semantics

| Type | Snapshot outcome | Behavior |
| --- | --- | --- |
| `trip.started` | `open` | Publish observed start; late attachment remains partial and does not fabricate the actual start |
| `trip.completed` | `delivered` | Delivered summary with actual source outcome evidence |
| `trip.cancelled` | `cancelled` | Actual observed cancellation, not a shutdown/gap inference |
| `trip.closed` | `none` | Closed without a reliable delivered/cancelled outcome; retains close reason and partial recording |
| `trip.corrected` | Terminal outcome | New complete snapshot of materially corrected terminal evidence; never overwrite an earlier source message |

An initially imported terminal trip can start at revision 1 without a synthetic start message. An imported open trip emits a backfill `trip.started`, then a later terminal snapshot at a higher revision. Network retries resend the exact same event ID, revision and content. New evidence uses a new event ID and a higher revision; a new network attempt is not new evidence.

While a trip remains open, material context/completeness changes may publish a higher-revision `trip.started` snapshot for that same opening; this is a snapshot refresh, not another start transition. Do not stream per-second distance/speed updates. The terminal snapshot carries final aggregate context and any changes that make it uncertain. A terminal correction uses `trip.corrected`. Consumers derive notifications from the canonical lifecycle transition, never merely from the message type or revision count.

Store any valid snapshot even if a lower revision/start has not arrived. Apply a higher consistent revision; retain a lower revision as historical evidence without regressing state. An old start cannot reopen a finished trip. Conflicting terminal outcomes, an attempted reopen, suspicious revision histories, uncertain source evidence or contradictory facts enter review. Do not automatically create multiple canonical trips, reject an older valid event as lost, or let an unconfirmed correction change an already confirmed decision/statistics/progress. The concept's staff-review and self-approval constraints still apply.

## Snapshot fields and normalization

`Available<T>` is exactly `{available:true,value:T}` or `{available:false,reason:"not-observed"|"not-supported"|"invalid"}`. Metric fields add their exact `unit`. Empty display names may be observed values; an empty source ID is unavailable for matching. No implicit zero, English label, known currency, full trailer list, actual timestamp or DLC inventory is inferred.

| Group | Fields and semantics |
| --- | --- |
| Status | `outcome`, `closeReason` (`null` only while open), `recordingCompleteness` complete/partial/unknown |
| Time | `start`, nullable `end`: `{utcMs:number|null,basis:event|checkpoint|last-known|receipt|unknown,eventSeq:string|null}`. Nonnegative UTC epoch ms; preserve provenance. EventSeq required for an event basis. Unknown basis has null UTC/sequence. Preserve raw source-event time if the local row was clamped |
| Opening | `openedBy:event|checkpoint`, nullable `openedEventSeq`, nullable `checkpointNextEventSeq`, nullable `outcomeEventSeq` |
| Context | Available `gameBuild`, `sourceLocale`, `mapId`, `dlcIds`; `versions` includes supported native protocol, SDK archive, telemetry API and game-telemetry API availability. A retail build is never derived from the API version |
| Mode | `gameMode:{mode:single-player|truckersmp|unknown,method:module-scan|process-scan|none,confidence:strong|weak|none,ambiguous:boolean}`; no module paths |
| Job | Origin/destination each have available city/company source IDs and names; available cargo ID/name, actual mass kg, unit mass kg/count, market, special-job and cargo-loaded flags |
| Trailer | `trailers:{complete:boolean,items:[{index,id,bodyType,chainType}]}` with availability on identifiers/types; at most 10 active slots. Any mid-trip rule-relevant configuration change, missed configuration or omitted history is reflected in evidence/review, not hidden by the latest snapshot |
| Distances | `plannedDistance` m, `observedDistance` m, `deliveredDistance` m are separate available metrics |
| Other outcome facts | Available fuel used L and cargo damage fraction; available expected income/revenue/penalty as exact raw monetary values, not display conversions |
| Quality | `evidence:{startObserved,endObserved,ruleContextComplete,clockAnomaly,reasons:[bounded codes]}`. Aggregate all relevant completeness causes; no arbitrary raw event/interval detail |

Money is `{raw:<canonical signed/unsigned integer string>,sdkType:"s64"|"u64",currency:{status:"unknown"}|{status:"sdk-documented",code,source}}`. Preserve exact 64-bit range; expected and earned amounts remain separate. Never combine currencies, infer one from the game/language, or treat revenue as a real financial amount.

The native protocol defensively accepts damage up to 1,000; a value above the ordinary fraction range 0–1 is anomalous evidence for review, not a valid 100,000% display or a value to clamp silently. Reason codes are bounded project-defined lowercase identifiers; unrecognized codes require review/compatibility handling and must not be discarded as proof of completeness.

Use exact game/source IDs for server-side catalog normalization. Labels and locale are display/provenance only. Unknown map/build/name-only ambiguities go through the catalog review path. Resolve regions/ADR from the applicable catalog version; do not pretend these fields are supplied by the current job payload. Catalog changes cannot silently change historical rules.

### Actual time, distance and qualification

Use actual observed start for qualification/rule/progress assignment and actual observed completion for analytics, even for old initial uploads. Preserve server `receivedAtUtcMs` separately. Receipt time, first synchronization, current qualifications and current rule versions are never substitutes for old trip facts.

The local reducer's stored times may be a checkpoint, inherited last label, receipt fallback or clock-regression clamp. Send that provenance; `startObserved/endObserved` can be true only for supported actual lifecycle observations, not merely because a trip row has numbers. Late attachment, missing start, uncertain time/ownership, configuration changes and incomplete distance require evidence review when relevant; never automatically treat an old incomplete recording as complete. Staff must resolve historical attribution explicitly; this does not convert telemetry into an undated manual report with invented confirmation-time attribution.

The owner explicitly confirmed that an imported trip with unknown historical qualification (including a trip before membership) remains visible but awaits staff review before statistics/progress credit. Known historical qualification and sufficient source facts follow normal automatic rules; being old is not by itself a review requirement.

Candidate distance rule: use observed odometer distance as actual driven distance only when whole-trip coverage is supported. Retain SDK delivered distance independently for corroboration; never substitute planned distance or sum the two. Incomplete observed distance is a measured segment, not necessarily the trip total. Conflicting totals require review; tolerance and real-game SDK semantics must be verified in VTC-024, not invented as company policy here. Missing exact build alone is recorded uncertainty; automatic evaluation requires the catalog/rule mappings actually used to be supported.

Ingestion never trusts a client-provided `accepted`, qualification, RSVP or exception flag. Delivered plus complete is still not company acceptance. Unknown required facts go to review; proven qualification violations may be rejected by the dashboard, while valid sufficient evidence can be accepted. Initial backfill follows those same rules.

## Durable receipt, identity conflicts and processing

Validate auth/binding/version/shape/limits before returning success. In one MySQL transaction, reserve/validate immutable source-trip ownership, insert the immutable inbox record with its server-computed content hash, and schedule durable processing/outbox work. Acknowledge only after commit. Domain processing may follow asynchronously; return `202` for new committed receipt and `200` for an exact duplicate, never "accepted by company".

```json
{"contract":{"major":1,"minor":0},"eventId":"10000000-0000-0000-0000-000000000001","receiptId":"90000000-0000-0000-0000-000000000001","status":"stored","firstReceivedAtUtcMs":1792231200000}
```

An exact replay returns the same event/receipt/first-received identities with `status:"duplicate"`. Both responses mean the client may mark that one event delivered after validating the response version, IDs and status. Lost/invalid/truncated responses mean retry, not success. Persist receipt state before queue cleanup. A crash after remote commit but before local receipt commit must yield an exact duplicate on replay.

Required database invariants, using non-null columns and exact comparison:

- Unique `(provider,eventId)` for immutable event identity; source-trip key maps to one local owner across installations, tokens and database copies.
- Unique `(provider,game,pluginSessionId,tripId,revision)`; the same revision cannot introduce a second logical snapshot under another event ID.
- Content comparison uses SHA-256 of validated JSON canonicalized with RFC 8785, including the entire envelope. It ignores object-key order/whitespace, preserves array order and does not normalize source-ID case or Unicode. Validate finite numbers and lossless integer strings before hashing.
- Same identity and equivalent content is a duplicate. Different content, or another ID reusing a revision, is `409 IDENTITY_CONFLICT`; no overwrite and no second notification. Never expose another owner's identity or payload in the response.
- Token rotation never changes uniqueness scope. An authenticated account/binding mismatch or a trip already owned elsewhere is rejected before revealing its receipt. Do not scope event uniqueness only by token or installation.
- A database copy/reinstall must preserve frozen queue envelopes and the original registration/binding references when retrying already materialized events; the same owner may use those original references while valid. Do not rewrite `installationId`, `databaseUuid`, delivery mode/run or event IDs in pending envelopes. If that metadata was lost, hold for source reconciliation rather than minting a new identity to conceal a conflict.
- Commit failures/duplicate-key races roll back correctly; no check-then-insert-only guard. Workers use idempotent domain effects and transactional outbox. Canonical trip totals, progression and notification effects are each applied once.

A revoked token is refused even for a known duplicate. Already stored evidence remains; revocation does not delete history or undo accepted trips. Later source corrections and manual/telemetry reconciliation retain one canonical trip and staff review where required. Native source event sequence is not an HTTP ACK cursor: unrelated events/gaps can create holes and summaries do not upload the whole stream.

## Errors, retries and operational bounds

Error body: `{error:{code:<fixed code>,retryable:<boolean>},requestId:<opaque safe ID>}`; no raw payload/token/other-owner data. `401` includes a bearer authentication challenge. These codes describe transport/authentication; a company rejection is a successfully stored source record with a separate domain result.

| HTTP | Code | Client action |
| --- | --- | --- |
| 400 | `INVALID_PAYLOAD` | Hold this event; show fixed diagnostic; do not recreate identity to bypass validation |
| 401 | `TOKEN_INVALID` | Pause this account queue until a valid same-owner/epoch token is connected |
| 403 | `INGESTION_FORBIDDEN` | Pause; membership/scope eligibility must be resolved |
| 409 | `BINDING_MISMATCH`, `IDENTITY_CONFLICT` | Hold for explicit reconciliation; do not rebind or overwrite |
| 413 | `PAYLOAD_TOO_LARGE` | Hold; repair bounded projection under a reviewed new event/revision, preserving evidence |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Require uncompressed `application/json` UTF-8; repair client |
| 422 | `UNSUPPORTED_CONTRACT` | Stop unsupported producer work; upgrade/negotiate a supported contract; no lossy downgrade |
| 429 | `RATE_LIMITED` | Retry after valid `Retry-After`, plus jitter; retain exact payload |
| 500/502/503/504 or network timeout | `TEMPORARILY_UNAVAILABLE` where a body is available | Retry exact payload; timeout may follow a committed transaction |

Other HTTP failures are retained/paused with a visible diagnostic, not silently discarded or treated as ACK. TLS/certificate/redirect failures pause until configuration is repaired; never disable validation. Bound automatic network retries per work cycle and use capped exponential full jitter (base 2 s, cap 5 min), persisted next-attempt state and validated `Retry-After` seconds/date. Invalid `Retry-After` uses backoff. Authentication/permanent errors are not hot-looped. No maximum trip age or automatic queue expiry removes unsent records.

Candidate v1 limits: one event/request; 65,536 raw bytes; JSON depth at most 16; ID strings 128 UTF-8 bytes, display labels 256; 10 trailer slots; 32 distinct quality reason codes; 256 DLC IDs. Reject invalid UTF-8, duplicate JSON keys, nonfinite/unsafe numbers, unknown keys, excessive nesting and compression. The schema's character lengths do not replace UTF-8 byte checks. Defensive maxima are protocol bounds, not qualification limits. Do not truncate a payload into falsely complete evidence.

One client upload request is in flight at a time; bounded initial/live scheduling prevents history from starving new terminal summaries. Start with a per-token limit of 60 event requests/minute, burst 10, plus deployment-configured IP/global limits that tolerate shared NAT and do not disable revocation checks. Validate these proposed limits in VTC-023/024 and target hosting; they are not observed server capacity. Bound pending serialized queue storage (candidate 10,000 events or 64 MiB); on pressure pause materialization/upload work, show unsynchronized backlog, retain its durable source/change cursor, and resume as space frees. Recording/overlay cannot wait for HTTP. Test that changes cannot be lost while the materialization queue is full; never garbage-collect pending source data to meet a bound.

Backfill and delayed/replayed starts must not generate "driver just started" activity. Persist historical notification entries only as authorized, without real-time toasts for imported trips. Candidate live freshness window: 120 s from supported source occurrence to receipt, not `createdUtcMs`; duplicate events produce no second notification. Fresh terminal-before-start suppresses any later obsolete start notification. Unknown clock/freshness yields history, not fabricated live presence. Timer/window choices need maintainer agreement and host verification.

## Versioning, acceptance and ownership

Only exact v1.0 is specified. Unsupported major/minor versions receive a clear error before any durable ACK. Future versions require supported-version advertisement, schemas/examples and compatibility tests; old stored versions remain readable under their original decoder. No blanket "ignore new fields" policy applies to identity/evidence.

VTC-022 owns canonical/source mapping; VTC-023 owns token/registration/inbox/ACK/limits with real MySQL race tests; VTC-024 owns desktop binding, automatic initial enumeration, immutable queue, source projection and real-client verification. VTC-026 owns reviewed reconciliation; VTC-029 owns company decisions; VTC-036 owns permission-filtered notifications. No external implementation or card status is changed by this document.

Before VTC-003 can close, the owner/telemetry maintainer must review the concrete first-binding implementation/trust boundary, time/distance projection and transport limits; independent review/merge remain separate gates. Product scope for synchronized lists and unknown historical qualification is confirmed above. Client recording enablement, exact build/locale collection, real-game measurement and server concurrency proof remain implementation gates, not claimed discovery successes. See the [acceptance matrix](telemetry-v1-acceptance.md).
