# Telemetry companion v1

VTC-164 adds the bearer-only [OpenAPI](telemetry-companion-v1.openapi.json), generated `companionComponents` types and `urn:vtc:companion:v1` runtime schemas. [Fictional fixtures](examples/telemetry-companion-v1.json) describe both games, current/next/terminal progress, unavailable assignments, provisional checks, receipt/review/decided/predecessor/legacy states and safe errors. This is a separate additive contract; the frozen connection, v1.0/v1.1/v1.2 event bodies and 202 stored/200 duplicate ACK remain unchanged. Receipt never grants company credit. ET-119 joint integration and real-game evidence remain required.

## Grant and scope

Issue a new personal ingest token with browser `TokenInput.companion: true` to grant `companion.own.v1`; omission or false preserves ingest-only behavior. Existing tokens never acquire this grant. The form discloses that previews additionally send cargo code/mass, the current and previous trailer chain with provenance, supported actual distance, Hard Mode finality, actual start and an optional event reference. These facts may leave the device before a trip upload. No raw samples, positions, profiles or diagnostics are accepted.

All four operations under `/api/telemetry/companion/v1` check the live member, Steam identity, captured access/identity/credential epochs, token and grant on every call, including conditional reads. Cookies and administrative status cannot impersonate a driver. `securityScope` is an opaque server-authenticated owner/company/epoch fence, independent of token rotation within that scope. A changed scope invalidates persisted snapshots, versions and in-flight replies. It is not a credential. Installation/binding validate upload admission but never add a source deduplication dimension.

## Qualification and preview

`GET /capabilities` discovers enabled modules, both enumerated games and budgets. `GET /qualification/{game}` supplies a consistent assignment/level/edit/limits/progress snapshot; every configured promotion condition must be met. Null conditions have null remaining amounts; a terminal level has no next level. Missing assignment and disabled/unavailable module states have no invented zero progress. Unsupported games fail validation. `asOf`, `progressRevision` and the five-minute `offlineUsableUntil` label cached display only; offline state cannot promise credit or current eligibility.

`POST /preview` requires explicit availability/value pairs, canonical nonnegative DECIMAL(38,18) quantities (20 integral and 18 fractional digits), maximum ten trailer observations and bounded codes. Unknown pairs must carry null values; known pairs must carry a value. Actual distance is never planned or remaining distance. Partial/unsupported distance cannot establish whole-trip compliance. A growing whole-trip distance below minimum remains unknown; proven maximum breaches fail. Required nonfinal Hard Mode remains unknown. Known disallowed trailer groups outrank an incomplete chain; confirmed non-ADR passes; missing classification stays unknown. Overall fail outranks unknown, which outranks pass. Unrestricted rules follow the common final evaluator.

Preview is always provisional. Supported actual start may select a historical assignment; otherwise `basis=current_projection` explicitly labels current limits. A client event reference or RSVP cannot grant exemption. Only current server-confirmed attendance for an eligible published same-game event exempts all five limits; unresolved references add `event_unresolved` and cannot promise final credit. Company acceptance and lifecycle uncertainty remain separate from this limit check.

Clients allocate `contextRevision` whenever cargo, trailer chain/provenance, job, start, game or event context changes, and `evidenceRevision` for growing observations. Echoed request/evidence revisions fence out-of-order replies. The server issues a five-second applicability envelope: require the same context/security scope, nondecreasing evidence revision, supported distance at least `minimumDistanceM` and at most `maximumDistanceM`, an unexpired lease and the most recently fetched `qualificationRevision`. A growing below-minimum reply remains unknown even if distance crosses minimum; refresh to obtain a newer result. Crossing maximum invalidates a delayed positive immediately. Null maximum means no distance ceiling. An already-proven maximum violation uses no upper guard while distance grows, preserving a red result; final distance uses equal lower/upper guards so a correction cannot reuse its old check. Cargo/trailer/job changes invalidate the envelope immediately. Promotions/level edits invalidate it on qualification refresh; `requiresQualificationRefresh` makes the bounded five-second uncertainty explicit. This envelope is a lease for provisional display, never a final pass or acceptance. Clients only compare the server-provided envelope; they must not implement qualification evaluation.

## Own-upload results and history

`POST /results` accepts 1–25 exact known identities: provider `ets2telemetry`, game, original `pluginSessionId`, original root `tripId`, requested immutable envelope revision and `eventId`. No history listing or arbitrary member ID exists. A nonexistent or foreign identity returns the same `not_received` projection. `requestedSourceMessageId` establishes receipt for that exact revision/event; `latestSourceRevision` and canonical mapping describe the currently retained source lineage. A receipt without a completed evaluation is `processing`; missing never means fail.

State, company decision, pending assessment/correction, retained qualification outcome and credited contribution are independent axes. The assessment identifies the exact immutable fact/material, source message/revision/event, assignment, decision identity/sequence/time and retained level/edit/limits/rules/exemption. It never returns reviewer prose. A current correction can retain an effective predecessor decision: `assessmentBasis=predecessor` must remain visibly older, even while company credit remains accepted. A null historical snapshot returns `historical_unavailable`; it is never reconstructed from current limits or promotion. Current projections are preview-only. Event invalidation/queued reevaluation must mark results pending before refresh, without read-side catch-up writes.

`resultRevision` is a durable monotonic owner revision maintained in the producer transactions, surviving restart and canonical merge/unmerge. Compare it only inside `securityScope`, never decision sequence across roots. The opaque per-item `version` binds that revision, scope and exact requested source/revision/event. A matching `ifVersion` returns an authorized `unchanged` item with assessment/credit omitted as null; keep the previously saved item. Other identity or epoch versions cannot authorize reuse. Ordering counters are canonical unsigned integer strings; do not convert them to floating-point numbers.

## Budgets, refresh and failures

Source revisions preserve the frozen protocol's exact integer range 1 through 9007199254740991. Decision sequences and local request/context/evidence counters retain their separately bounded integer ranges. `materialIdentity` is the immutable server fact UUID, including a derived fact UUID after a resolution; it is never a client digest. `assessedSource`, `sourceRevision` and `sourceEventId` correlate a retained assessment with the exact immutable local envelope. `assessmentBasis=current` requires that exact source message/fact applicability. A decision on a different canonical source is `predecessor`; merge membership alone does not certify equivalence.

Trailer codes in preview are exact SDK `trailers.items[0].bodyType` values for each distinct coupling/configuration, matching the frozen event projection. One preview item represents one coupling configuration, not one physical constituent trailer slot. Send the current coupling and every known previous distinct coupling in observation order; do not send display names, `chainType` or each physical leaf body as independently restricted types. Unknown coupling configurations keep an explicit null hole with `provenance=unknown`; `previous` means an observed earlier attachment configuration, not a guessed chain. `complete` is false when any relevant attachment history is unavailable. Any cargo/mass availability or value, trailer/provenance, job, start, event, actual-distance availability/support/finality or Hard Mode result availability/value/finality change advances `contextRevision` and immediately invalidates earlier leases. Growing nonfinal metres alone advance `evidenceRevision`; any change to a final distance advances `contextRevision`. The server-provided minimum prevents rollback reuse. `requiresQualificationRefresh=true` permits provisional display within the unexpired lease while refreshing qualification in the background; it does not require a refresh-before-display loop. A fetched promotion/edit revision invalidates the lease immediately. Expired, scope-mismatched or changed-context replies become neutral until a fresh check. No client rule evaluator is required.

Each returned rule has an allowlisted `reasons` array attached to that rule: unavailable catalog/trailer/evidence produces `fact_unavailable`, growing distance `below_minimum_growing`, unsupported distance `unsupported_distance`, nonfinal Hard Mode `hard_mode_not_final`, a proven violation `limit_mismatch`, server-confirmed exemption `event_attendance_exemption`, and ordinary pass `within_limits` or `unrestricted`. Rule observations and limits remain the exact server assessment. `trailerDisplay` supplies bounded RU/EN names and group/code metadata beside immutable selected and observed trailer IDs. Its `basis=current_catalog` and `asOf` explicitly mark presentational current labels, including on historical results; missing rows/names remain unavailable. These labels never reconstruct historical group membership or alter a retained check.

Successful responses are capped at 1048576 UTF-8 bytes, independently of schema bounds. A conditional result with no locally retained matching version cannot populate a cache; refetch that item without `ifVersion`. Requests with the same source identity but a different revision/event have different versions. Fixture names describe in-flight boundary, support-loss, rollback, context, promotion/edit, expiry, canonical remapping and large-counter scenarios; application behavior tests establish enforcement in addition to structural validation.

Within the same `securityScope`, compare `Preview.applicability.qualificationRevision` directly to the latest `Qualification.progressRevision`. Both use the same durable owner counter across ETS2 and ATS; a change in the other game may conservatively invalidate the lease. Game is still part of preview context. Keep these counters as exact strings (or exact integer values), never floats or locally generated qualification revisions.

`Qualification.ownerId` exactly equals the authenticated frozen connection's `accountId` (the token's local owner ID). Frozen `companyId` is the token's company ID; companion DTOs do not duplicate it, while `securityScope` authenticates owner, company and access/identity/credential epochs. Desktop cache scopes retain registration origin/account/company/identityEpoch together with `securityScope`. Clear preview leases on process restart and accept replies only for the current request/context; do not reinterpret a cached positive as a new request's response.

`predecessor` means the retained assessment is not certified for the requested immutable material. During correction it identifies the older effective assessment; after canonical reconciliation or a staff resolution it may instead describe different/derived material. Its decision identity/time remain authoritative. Do not infer chronology or material equivalence from the word alone or compare decision sequences across canonical roots.

Supported partial distance can prove a maximum breach because its measured lower bound already exceeds the maximum. It cannot establish whole-trip minimum compliance or a completed pass. Its server-issued lower guard still prevents reuse after rollback. Unknown distance support cannot prove a breach. Final supported whole-trip distances receive equal lower/upper guards; any correction creates a new context.

Requests are closed-schema JSON, uncompressed UTF-8, at most 16 KiB, depth 16, without duplicate decoded keys. Strings/codes are bounded; batches cap at 25 and trailer chains at ten. Unknown fields and noncanonical decimals fail 400. Unsupported game/path returns safe 400/404; 401 invalid token, 403 forbidden membership or missing capability, 413 body limit, 415 media, 429 admission and 503 unavailable expose no private details. Errors carry a request ID and retryable flag. Responses use `Cache-Control: no-store`; no remote restoration or raw/event/sample download exists.

A persistent companion token/IP/global lane is isolated from upload admission; polling cannot spend event credits. Minimum polling is five seconds, token burst ten and rate 60/minute; batch known uploads and honor `refreshAfterSeconds` and `Retry-After` (also on 503). Refresh after upload, startup and reconnect and continue bounded polling for later staff/event/reconciliation changes. Use a 10-second request timeout, cancel on shutdown/context changes, one in-flight request per operation, exponential retry with jitter capped at 60 seconds and stop retrying 400/401/403/404 until configuration/access changes. A timeout never implies missing receipt or failed qualification. Every response, including unchanged items, is freshly authorized. Security admission/last-use audit is the only permitted read mutation; reads/previews never assign, promote, decide, associate events or replace contributions.
