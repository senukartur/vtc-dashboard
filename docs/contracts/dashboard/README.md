# Dashboard browser API v1

**Status:** VTC-005 implementation contract; review/adoption is recorded in [PR #5](https://github.com/senukartur/vtc-dashboard/pull/5), not proof of an implemented API. [OpenAPI JSON](openapi.json) is the wire reference; [synthetic examples](examples.json), [UI coverage](ui-coverage.md), [domain events](events.md) and the [architecture](../../architecture/README.md) specify behavior that structural schemas cannot enforce. Product requirements remain [CONCEPT.MD](../../../CONCEPT.MD). The separate [telemetry v1.0 API](../telemetry-v1.md) is unchanged.

## Transport and security

- Browser routes use `/api/v1`, same-origin HTTPS and JSON, except private evidence upload/download. No CORS wildcard or bearer fallback for browser membership routes. Native telemetry bearer credentials cannot authenticate browser APIs.
- Application auth endpoints wrap private Better Auth server APIs and preserve all required cookie headers. Do not mount a public library catch-all. The frontend consumes this project's contract, not Better Auth's mutable native response DTOs. Disable public standalone signup and unguarded profile/admin mutations; invitations are the only normal creation path.
- Cookies are HttpOnly, Secure on HTTPS, host-only with Path `/`, and SameSite=Lax; the deployment config pins exact origins and trusted proxies. Proposed session name is `__Host-vtc_session`; verify Better Auth custom-cookie mapping in VTC-013. Local HTTP uses an explicitly separate development cookie, never weakened production flags.
- All browser writes, including login/public applications/invitation redemption, require same-origin checks and `X-CSRF-Token` from `GET /api/v1/auth/csrf`, bound to a signed pre-session nonce or current session. Rotate binding on login/logout. Validate CSRF on the application facade even if an internal library helper skips HTTP middleware. No wildcard return URL, GET mutation or state-changing identity callback is accepted without its bound state/nonce.
- Authorize from current active membership/access epoch/capabilities and resource ownership. Return 404 for inaccessible individual private resources to avoid disclosing their existence; missing route capability returns 403 before executing the query. No inactive member can access protected routes, regardless of a still-valid library cookie. Invitation identity/member creation is atomic and invisible until commit; it never issues a session automatically. Disable auth cookie-cache shortcuts for these decisions.
- Auth responses, invitation links, telemetry token issuance, private reports/evidence and personal notifications use `Cache-Control: no-store`. Never place passwords, codes, tokens or private request bodies in logs, metrics, exception traces or analytics. A shared frontend error page cannot print server internals.

## IDs, values and absence

Application/canonical catalog IDs are opaque UUIDv4 strings. External source IDs keep the provider contract. Browser dates are ISO UTC strings ending `Z`; game is `ets2|ats`; locale is `en|ru`. Base-unit quantities use canonical decimal strings (m/kg/L/fraction), counts/versions are bounded safe integers. Missing values are explicit `null` plus reason/provenance where relevant, never an invented zero. UI converts units/localises labels without altering identity or rule arithmetic.

`CatalogLabel` carries requested/rendered locale and an explicit English-fallback flag. An unresolved name is a diagnostic fact, not a selected catalog entity. Forms submit IDs plus catalog revision, not translated labels. Retired entities remain readable for history; new choices come from the applicable published revision.

The server derives trip owner, decision actor and company from the session. A manual form contains game, origin/destination IDs, cargo ID/mass, trailer type ID, actual distance, ready evidence IDs and optional event/comment. It never accepts a trip date, qualification, accepted flag or another owner. Validate every selected entity's game, kind and pinned catalog revision, and evidence ownership/readiness, on the server. Manual revisions resubmit the same canonical trip; accepted records require a correction request and staff decision. Reconciliation requires distinct canonical trips of the same verified owner, never a trip merged with itself.

Private read-back is part of the contract: bounded manual-revision and proposal lists plus individual reads are available only to the trip owner or currently authorized trip-review staff, never ordinary company readers. Historical revisions retain their original form/evidence references; `Decision.reason` preserves the staff explanation alongside reason codes (null is allowed only for an automated decision without free text). A decision's `reviewedRevisionId` identifies the immutable reviewed manual/source revision. `TripProposal` exposes its immutable `revisionId`, reason, evidence, proposed field changes, base trip/fact versions and review outcome. A correction request can have no field changes; a resolution proposal must contain supported changes. Proposal creation's returned ID is the proposal ID. A proposal detail GET returns the **current trip** ETag, and approval requires that trip ETag plus `reviewedRevisionId == proposal.revisionId`; the server also revalidates the base facts and current supporting versions. Stale proposals require a new reviewed proposal rather than applying obsolete values.

Private decision/review evaluation snapshots expose the pinned assignment, level, rule/catalog revision, attendance and attribution references needed to explain the outcome; missing historical context stays null/unknown. Published rule-version list/detail reads supply immutable rules and promotion thresholds without private audit comments. Owner/admin historical-assignment lists and trip-scoped staff reads expose actual half-open assignment intervals `[assignedAt, endedAt)` (null end means current); they do not create or infer past assignments. An empty history remains unresolved, never today's qualification copied backwards.

## Responses, errors and concurrency

Successful JSON responses use `{data,meta:{requestId}}`; list data uses `{items,nextCursor}`. Creation returns 201, committed commands 200, durable background operations 202. No asynchronous receipt means business acceptance. Evidence content returns a protected binary stream. The telemetry API retains its own ACK/envelope/status codes.

Errors use `{error:{code,messageKey,retryable,details?},meta:{requestId}}`. `details` is a schema-validated safe field/conflict hint, not raw input, SQL, private histories or another owner's identity. The client localises `messageKey` and known reason codes. Loading is a client request state, not a special successful API payload. Empty lists use `items:[]`; network failure leaves the last safe data visibly stale rather than showing false zero totals.

| HTTP | Codes / meaning |
| --- | --- |
| 400/415/422 | Malformed JSON, unsupported media type or schema/semantic validation; never echo passwords/tokens |
| 401 | No valid browser session / invalid login or verification; generic auth diagnostics |
| 403 | Capability, CSRF/origin or action guard denied; self-approval is `SELF_REVIEW_FORBIDDEN` |
| 404 | Unknown or inaccessible individual private resource |
| 409 | `VERSION_CONFLICT`, `STATE_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `SETUP_REQUIRED`, `INVITATION_UNAVAILABLE`, `SECRET_ALREADY_ISSUED` |
| 413/428 | Upload too large under configured limits / missing required `If-Match` |
| 429/503 | Rate-limited (`Retry-After`) / temporary dependency or database outage |

Mutable resource GETs return a strong `ETag` derived from the authoritative aggregate version. Commands editing/reviewing a versioned aggregate require `If-Match: "v7"` where declared; list items with an explicit authoritative `version` may supply that same header value. Revocations, read markers and one-time challenge consumption use their intrinsic state guards instead. The server compares under lock and returns 409 on a stale version; a reviewer must refetch and confirm the **actual immutable report/fact revision** reviewed. Return the updated ETag after commit. Multi-aggregate commands additionally validate all referenced fact versions; an ETag alone does not prove attendance or a qualification snapshot.

Domain creation/irreversible browser commands require a UUID-shaped `Idempotency-Key` where declared, scoped by actor or a private pre-auth nonce, route and target. Login/logout follow their session lifecycle guards. Atomically reserve the key and compare a server-computed keyed fingerprint of validated input; changed input is 409. Never persist plaintext passwords/codes/invitation secrets in the fingerprint/reply store. Concurrent requests return the same committed ordinary result or a durable pending operation; they do not apply a command twice. Persist domain uniqueness as well as the transport key. Retention/abuse bounds are configured/tested in VTC-013/015/023/039, not invented company limits here.

**One-show telemetry secrets are an exception to result replay:** issuance stores only a hash; exact retry cannot reconstruct the secret and returns `SECRET_ALREADY_ISSUED` plus the caller-owned token ID. If the first response was lost, revoke that token and issue another; do not mint a second token for the same key. Invitations are one-time **use**, not one-time display: administrators can copy a still-valid link from an encrypted-at-rest generation; redemption lookup uses a hash, and consumption/reissue removes encrypted material. Do not store those links in ordinary idempotency caches.

## Pagination, projections and notifications

Use bounded cursor/keyset pagination: default 25, maximum 100 as technical API limits, sorted `(createdAt,id)` descending unless the operation defines a chronological cursor. Opaque signed cursors bind actor, filter set, sort and visibility; they are not credentials and cannot bypass current authorization. Changing filters requires a fresh cursor. No offset pagination for a mutating notification feed.

Notification polling uses an ascending recipient-scoped durable sequence cursor, every 30 seconds while visible, paused hidden/offline and refreshed immediately on return. Return catch-up/history and current unread state without duplicating toasts. Recheck membership/session before every poll. Event/source timestamps determine live freshness; database delivery time does not turn old history into live activity. Approximate healthy 90-second delivery is measured later in VTC-021/036/037/040, not proven by early VTC-011 synthetic probes.

An initial poll without a cursor returns the latest bounded visible window in chronological order and a current non-null checkpoint, even when empty. Subsequent polls advance from that recipient-scoped checkpoint; bounded catch-up uses `hasMore`. Older history uses the separate descending `/notifications/history` cursor and never triggers toasts. Do not make a new login drain years of history before it can receive current activity.

Company start/finish activity carries only the safe actor nickname/game and transition message. It does not grant access to another member's pending report. `Notification.target` is null when the underlying trip is inaccessible, while private event/review notifications require their current recipient permissions and never include private reasons in display arguments. Members can therefore see the agreed live activity without fetching private trip evidence. Event RSVP uses its own `GET .../my-response` version/ETag; an event-detail ETag does not authorise overwriting a newer response.

Analytics/progress responses carry `computedAt`, `projectionVersion` and pending/stale indicators. Only accepted canonical trip contributions count. Telemetry periods use actual completion; undated manual periods use confirmation. If reporting timezone/configuration is missing, return setup-required with safe missing-setting codes. User display timezone never silently changes reporting boundaries.

Analytics includes day/month buckets for charts and a stable projection-bound leaderboard. Enforce a configured bounded date window and `fromDate < toDateExclusive`. Own status counts are separate; `activeTrips` and `correctionPending` overlap the decision partition and must not be added to produce a total. Public member progress excludes private correction-review flags; owner/admin projections expose them. Catalog publication validates both candidate ETag and `expectedPublicationVersion`; source mapping changes belong to a draft revision, never mutate published mappings.

Authenticated background import status uses `/operations/{id}` with creator **and current initiating capability** checks. Public invitation redemption is synchronous/atomic with a 201 safe result, not a password-bearing background job. Initial Steam linking returns a bound verification URL; VTC-018 owns the external signed-provider callback/state protocol outside this browser API. A generic callback may never directly assign a different user's identity.

Steam replacement read-back is separate from initial provider verification. `/me/identity.pendingReplacementId` discovers the latest pending request after reload; the owner can read its status. Director/deputy list/detail reads expose the target member, verified candidate profile, bound identity epoch, expiry and terminal state, never callback nonces/provider credentials. Only a fresh, verified, unexpired, unconsumed proof for that member's current epoch can be applied under the member ETag; the server obtains the candidate from the stored proof. Expiry, a newer identity epoch or consumption prevents replay, including after a browser reload.

Catalog administrators read a candidate review manifest plus bounded entity diff, per-pack coverage and mapping-issue lists before publishing. The manifest records game build, dated release inventory, comparison revision, counts and reviewed public provenance/permitted-use references. Field changes are allowlisted safe catalog values, not source archives, internal paths or raw import payloads. Coverage includes base-game and every official pack, including missing/failed/non-contributing entries; a completeness boolean cannot hide a missing DLC. Child lists require `reviewVersion` and bind cursors to that candidate version; a changed candidate returns 409 and requires a fresh review. Publication still checks both the reviewed candidate ETag and the separate publication pointer. This preserves VTC-019's open source-coverage/licensing gates rather than declaring them satisfied by the schema.

## Contract evolution and implementing gates

The JSON OpenAPI document declares each operation's capability, owner card, request/response schemas and special preconditions. It excludes raw telemetry/webhook payloads and library-internal auth DTOs. Additive response fields require reviewed schema/example changes before strict generated clients adopt them; required-field removal, changed meaning/enums or security changes require a new major or an explicit coordinated migration. Route/API version is independent of domain-event and telemetry versions.

VTC-006 generates/types the shared browser contracts without altering this wire baseline. VTC-008/009 validate examples and runtime serializers; VTC-013 proves the auth bridge and disabled bypass paths; feature cards prove semantic rules, real MySQL transactions and browser journeys. The [UI coverage matrix](ui-coverage.md) is the acceptance map for mocks/parallel frontend work. UI cards remain incomplete until their live integration gates pass.
