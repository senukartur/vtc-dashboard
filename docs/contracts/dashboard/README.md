# Dashboard browser API v1

**Status:** VTC-005 implementation contract; review/adoption is recorded in [PR #5](https://github.com/senukartur/vtc-dashboard/pull/5), not proof of an implemented API. [OpenAPI JSON](openapi.json) is the wire reference; [synthetic examples](examples.json), [UI coverage](ui-coverage.md), [domain events](events.md) and the [architecture](../../architecture/README.md) specify behavior that structural schemas cannot enforce. Product requirements remain [CONCEPT.MD](../../CONCEPT.MD). The separate [telemetry v1.0 API](../telemetry-v1.md) is unchanged.

## Stage 2 foundation (VTC-132 Step 1)

Operations marked `x-contract-stage: VTC-132 Step 1` describe new paths and methods. An existing method's `x-stage-2-operation` contains the staged parameters, request and response schemas. Named `EventStage2*` schemas generate browser types and runtime validators. [Synthetic examples](examples.json) select the extension explicitly when applicable. [The route inventory](routes.md#stage-2-events-vtc-132-step-1) gives the capability for each staged operation.

- **Route and catalog (VTC-124).** A new complete definition requires `truckersmp` or `haulmp`. Select origin and destination depots by their canonical company–city row IDs. Each depot must be visible for a new selection, in the selected city and in the event game. The origin depot provides the meeting point. City, cargo and trailer labels use the requested RU/EN locale and visible fallback policy. Company, depot and DLC names are canonical. Their options carry ID, name and code, without locale or fallback fields. A depot's name and code come from its company. Show the name on the left and code on the right. Use canonical IDs when fetching the same-game selected cities and depots for derived DLCs. Deduplicate DLCs by ID and retain both `from_city` and `manual` provenance when applicable. Manual IDs are unique. The optional exact decimal `distanceKm` distinguishes unavailable from zero. Public payloads contain no company logos, private load prescription or member identifiers.
- **Draft and publication (VTC-125).** `POST /admin/events` with `draft: true` saves an incomplete draft. Without it, creation validates a full definition and immediately publishes. Draft input validates supplied values. A manager can read, replace or discard an active draft and use `period=drafts` on the admin list. Publishing the saved draft validates the full definition and preserves its ID and existing media. Drafts stay in administration, outside member/public lists and detail, trip association, notification and reminder eligibility. Publication is the first notification-eligible change. Apply the draft ETag to editing, deletion and publication. After publication, the returned ETag versions the published definition. Exact idempotency retries preserve the original committed result and recheck current access.
- **Read projections (VTC-126).** Member list and upcoming reads expose the current member's response status. `unanswered` is an actual response state and `null` means unavailable. Member list and detail have participating and declined counts without other members' reasons. The member organizer link uses a canonical member ID when present. Public organizer is safe display text. Legacy organizer text remains the fallback, and old platform/depot/distance fields may be null. Description, route and meeting location may be absent in new definitions. Leadership-only attendance has totals across the page scope, row-level nullable canonical trip IDs from Trips, and a separate paged nonresponders read. RSVP never establishes actual attendance.
- **Media (VTC-127).** Managers upload one PNG or JPEG per multipart request, under the existing manual evidence file-byte and decoded-pixel policy, with at most ten media slots per event. Keep the same file, key and `If-Match` on an uncertain retry. Reserve slots transactionally across concurrent processing and ready uploads. Recheck access, enforce bounded full image decoding, and fence leases and generation cleanup before I/O. Media collection versions are independent of definition, RSVP and attendance versions. The edit command supports caption, zero-based position and cover selection atomically. Ready images expose member thumbnail/full content with current event access. Manager draft content stays private. Anonymous access is limited to the selected ready thumbnail of a public published event and rechecks visibility on every request. Media is retained with its event. Duplication starts with an empty gallery. Uploader identity, storage locations, hashes and generations stay private.

The feature lanes own the wire cutover. Live `EventInput` and `EventPublic` still require nonempty description, route and meeting text, and the old revision table has non-null text columns. Coordinate the legacy readers and serializers before persisting a newly published definition with omitted legacy fields. Empty storage text fails legacy response validation. Preserve existing definitions, historical ordinals, active clients and compatibility of public/member lists, RSVP, the upcoming header and trip report event selection through cutover.

VTC-151 owns the shared picker used by VTC-128. Its options expose `{id, label, code}`. The adapter maps the canonical staged `name` to `label`, keeps the depot row ID as the option value and uses the company code for the right-hand column. Search existing depot transport by `game` and `cityId`, with bounded `search`/`limit` and the applicable `locale` parameter. The picker uses no locale fallback badge for these canonical labels.

The staged browser transport and TanStack Query hooks are opt-in. Keep the prepared command for exact retry and build a new attempt for a changed file, body or precondition. The browser fixture helper can opt into the Stage 2 examples without switching the existing event journeys to the new wire.

## Stage 1 dashboard contracts (VTC-123)

The OpenAPI operations marked `x-contract-stage: VTC-123 Step 1` describe the staged wire behavior. The feature lanes own runtime activation and behavior tests. Current routes and request validators still follow their implemented contracts.

### Workspace and administration (VTC-114)

`GET /me/workspace-summary` requires a current session with `company.read` and returns a private `no-store` snapshot. Apply the source reads' availability, current permissions, visibility and ownership. Count all eligible rows before taking the first five in each preview's specified order.

- `tripsNeedingFixes` requires `trips.read_own_private`, Trips and Manual Reports reads, and the effective rejection data. Include one row per owned canonical trip in the effective rejected state whose current manual revision belongs to the caller and is eligible for author resubmission. Use the latest applicable authoritative staff rejection of that revision in its canonical group. Exclude alias rows, historical decisions without current effect, telemetry-only and proposal-only rejections, and accepted or pending revisions. A resubmitted revision leaves the list while pending and can re-enter if rejected. Sort by the applicable `decidedAt` descending, then canonical trip ID descending. Return the author-visible reason or null when there is no displayable text.
- `unfinishedManualDrafts` requires `trips.submit_own` and Manual Reports reads. Include only the caller's editing drafts, ordered by `createdAt` descending, then draft ID descending.
- `unansweredUpcomingEvents` requires `events.respond` and Events reads. Include scheduled events the caller can see and respond to whose `startsAt` is strictly after `computedAt`. Include both missing RSVPs and a current `unanswered` RSVP after clearing a response. Sort by `startsAt` ascending, then event ID ascending.
- `reviewQueue` requires `trips.review` and Trips reads. Apply current review visibility and the Awaiting decision predicate (`scope=review&hold=true`). Exclude the caller's own trips before computing both count and age. Measure `oldestAgeSeconds` at `computedAt` from the oldest eligible queue entry's `createdAt`, or return null when empty.
- `newApplicationsCount` requires `applications.manage` and Admissions reads. Count submitted applications.

Omit each workspace section and each source-dependent member counter independently when its source is configured off or read authority is missing. Return zero for an available empty count and an empty array for an available empty preview. Apply the standard error policy on transient read failures. Promotion counts belong to a later stage.

The application and member admin lists can add `statusCounts` before cursor and limit. Application buckets `submitted`, `approved`, and `rejected` use their own status predicate and retain other applicable filters within the authorized population. Application history retains its original envelope.

- `inCompany` and `left` retain the role and nickname search filters and use active and inactive status respectively. Both identity counts remain available when an optional source is off.
- `droveLast30Days` requires Trips activity reads and current authority to read that activity. Keep the supplied status, role and nickname search filters. If status is omitted, consider both statuses. Count distinct members with accepted canonical trip `reportingAt` from the count snapshot time minus 30 days through the snapshot time, inclusive.
- `invited` requires Admissions reads and `applications.manage`. Count each approved application's current usable, active and unused invitation generation when its expiry is after the count snapshot time. Apply the same trimmed case-insensitive substring search to the application nickname. The member status filter does not apply. With a role filter, return zero because unredeemed invitations have no current member role.

### Trip lists and lifetime totals (VTC-115)

`GET /trips` can filter by canonical `ownerId`, UTC `from` inclusive and `toExclusive` exclusive on `reportingAt`, or `q`. Either time bound can be supplied alone. If both are present, the lower bound must precede the upper bound. A time bound excludes trips with unknown reporting time. Use the authenticated viewer's saved locale unless `locale=en|ru` overrides it. Search trims surrounding whitespace and matches the localized origin city, destination city or cargo label. Matching and returned labels use the same effective locale, with English fallback per missing translation. An all-digit term with an optional leading `#` matches the exact canonical number independently of locale. Existing scope authorization applies, and another owner's matches are accepted trips only.

Sort options `asc` and `desc` use `createdAt` then `id` in every scope, with `desc` the default. `completion_asc` and `completion_desc` use known effective actual completion with missing completion last and a stable ID tie-breaker. `hold` is review-only. After VTC-115 activation, every successful mine or company page includes `total` for the authorized filtered set before cursor and limit, including with `ownerId`. Omitting `scope` selects company scope. An empty filtered set has `total: 0`. Review pages may omit `total`, and the shared schema keeps it optional for compatibility. Cursors bind the normalized filters, effective locale and sort, and a mismatch returns `409 VERSION_CONFLICT`.

`TripSummary` can add a positive safe canonical `number`, UTC `createdAt`, and UTC `submittedAt` from the current manual revision, or null when there is no current manual revision. Only authorized author and reviewer projections can include `event` (a visible event ID and title, or null) and `gameMode` (`single-player`, `truckersmp`, `haulmp`, or `unknown`). Company-scope summaries omit both fields. The own trip status summary and member profile can include `lifetimeTotals` from accepted canonical trips, with `acceptedTrips` and exact `actualDistanceM` as a decimal metre string. The own summary applies its optional game filter and the member profile covers all games.

### Manual drafts and reports (VTC-116 and VTC-117)

The [manual report contract](manual-reports.md#stage-1-drafts-and-reference-fields-vtc-116-and-vtc-117) describes editing counts, bodyless guarded draft deletion, and staged reference fields for manual writes and private readback.

### Catalog filters and counters (VTC-118)

The catalog and depot lists can filter `hidden=only` and `untranslated=true`. The companies list also accepts `logo=missing`. `hidden=only` selects by the row's own hidden flag and takes precedence over `includeHidden`. Default depot visibility still requires the depot, company and city to be visible. A row is untranslated when its Russian name is missing. A depot is untranslated when either linked name lacks Russian. Apply filters before paging and bind them into the cursor.

Keep the existing visible and hidden summary counters. Each list can add `untranslated`, and companies can add `missingLogo`, matching the corresponding default-visible filtered population for the selected game. A company row can include `depotCount` for its linked depots in the same game. Each of the six catalog row kinds and depots can include UTC `updatedAt` for the row's own last update.

### Qualification publication (VTC-094)

`publishQualificationRules` accepts `QualificationRulePublicationInput` with an optional nonempty `reason`. Both threshold keys remain required and nullable. A null threshold means no minimum for that measure. Preview remains a separate optional action. Publication authority, effective-time guards, and immutable history still apply. Reads exclude the private audit reason.

## Transport and security

- Browser routes use `/api/v1`, same-origin HTTPS and JSON, except private evidence upload/download. No CORS wildcard or bearer fallback for browser membership routes. Native telemetry bearer credentials cannot authenticate browser APIs.
- Application auth endpoints wrap private Better Auth server APIs and preserve all required cookie headers. Do not mount a public library catch-all. The frontend consumes this project's contract, not Better Auth's mutable native response DTOs. Disable public standalone signup and unguarded profile/admin mutations; invitations are the only normal creation path.
- Cookies are HttpOnly, Secure on HTTPS, host-only with Path `/`, and SameSite=Lax; the deployment config pins exact origins and trusted proxies. Proposed session name is `__Host-vtc_session`; verify Better Auth custom-cookie mapping in VTC-013. Local HTTP uses an explicitly separate development cookie, never weakened production flags.
- All browser writes, including login/public applications/invitation redemption, require same-origin checks and `X-CSRF-Token` from `GET /api/v1/auth/csrf`, bound to a signed pre-session nonce or current session. Rotate binding on login/logout. Validate CSRF on the application facade even if an internal library helper skips HTTP middleware. No wildcard return URL, GET mutation or state-changing identity callback is accepted without its bound state/nonce.
- Authorize from current active membership/access epoch/capabilities and resource ownership. Return 404 for inaccessible individual private resources to avoid disclosing their existence; missing route capability returns 403 before executing the query. No inactive member can access protected routes, regardless of a still-valid library cookie. Invitation identity/member creation is atomic and invisible until commit; it never issues a session automatically. Disable auth cookie-cache shortcuts for these decisions.
- Auth responses, invitation links, telemetry token issuance, private reports/evidence and personal notifications use `Cache-Control: no-store`. The only API exception is the anonymous `getPublicCompanyStats` aggregate: a successful 200 carries `Cache-Control: public, max-age=60`; its errors stay `no-store`. Never place passwords, codes, tokens or private request bodies in logs, metrics, exception traces or analytics. A shared frontend error page cannot print server internals.

## IDs, values and absence

Application/canonical catalog IDs are opaque UUIDv4 strings. External source IDs keep the provider contract. Browser dates are ISO UTC strings ending `Z`; game is `ets2|ats`; locale is `en|ru`. Base-unit quantities use canonical decimal strings (m/kg/L/fraction), counts/versions are bounded safe integers. Missing values are explicit `null` plus reason/provenance where relevant, never an invented zero. UI converts units/localises labels without altering identity or rule arithmetic.

`CatalogLabel` carries requested/rendered locale, an explicit English-fallback flag, `hidden` and, only for a city that has one, `nameNative`, the canonical name as the game map writes it; `label` stays the translation and the field is never an identity key. An unresolved name is a diagnostic fact, not a selected catalog entity. Forms submit catalog row IDs, not translated labels. Hidden rows remain readable on existing records and leave selectors; a hidden row can only be kept unchanged, never newly chosen.

The server derives trip owner, decision actor and company from the session. A manual form contains game, origin/destination selections, cargo/mass, trailer type, actual distance, ready evidence IDs and optional event/comment. The [VTC-025 manual contract evolution](manual-reports.md) preserves legacy resolved payloads and adds partial drafts, explicit unresolved diagnostics, telemetry targets, complete history and correction-request discovery. It explicitly coordinates the response union migration before runtime activation. The manual report form requires start and completion dates for new final submissions and revisions. The dates are for reference, and the confirmation time determines reporting and progress. Client-supplied qualification, acceptance and owner fields are forbidden. Validate every resolved entity's game and kind, and evidence ownership/readiness, on the server. Manual revisions resubmit the same canonical trip; accepted records require a correction request and staff decision. Reconciliation requires distinct canonical trips of the same verified owner, never a trip merged with itself.

Private read-back is part of the contract: bounded manual-revision and proposal lists plus individual reads are available only to the trip owner or currently authorized trip-review staff, never ordinary company readers. Historical revisions retain their original form/evidence references; legacy trip history includes extended unresolved revisions through `ManualRevisionRead`, never silent omissions. `Decision.reason` preserves the staff explanation alongside reason codes (null is allowed only for an automated decision without free text). A decision's `reviewedRevisionId` identifies the immutable reviewed manual/source revision. `TripProposal` exposes its immutable `revisionId`, reason, evidence, proposed field changes, base trip/fact versions and review outcome. A correction request is separately discoverable and can have no field changes; its command result ID identifies the request, never a proposal. A resolution proposal must contain supported changes and proposal creation returns that proposal's ID. A proposal detail GET returns the **current trip** ETag, and approval requires that trip ETag plus `reviewedRevisionId == proposal.revisionId`; the server also revalidates the base facts and current supporting versions. Stale proposals require a new reviewed proposal rather than applying obsolete values.

Private decision/review evaluation snapshots expose the pinned assignment, level, rule version, attendance and attribution references needed to explain the outcome; missing historical context stays null/unknown. Published rule-version list/detail reads supply immutable rules and promotion thresholds without private audit comments. Owner/admin historical-assignment lists and trip-scoped staff reads expose actual half-open assignment intervals `[assignedAt, endedAt)` (null end means current); they do not create or infer past assignments. An empty history remains unresolved, never today's qualification copied backwards.

## Responses, errors and concurrency

Successful JSON responses use `{data,meta:{requestId}}`; list data uses `{items,nextCursor}`. Creation returns 201, committed commands 200, durable background operations 202. No asynchronous receipt means business acceptance. Evidence content returns a protected binary stream. The telemetry API retains its own ACK/envelope/status codes.

Errors use `{error:{code,messageKey,retryable,details?},meta:{requestId}}`. `details` is a schema-validated safe field/conflict hint, not raw input, SQL, private histories or another owner's identity. The client localises `messageKey` and known reason codes. Loading is a client request state, not a special successful API payload. Empty lists use `items:[]`; network failure leaves the last safe data visibly stale rather than showing false zero totals.

| HTTP | Codes / meaning |
| --- | --- |
| 400/415/422 | Malformed JSON, unsupported media type or schema/semantic validation; never echo passwords/tokens |
| 401 | No valid browser session / invalid login or verification; generic auth diagnostics |
| 403 | Capability, CSRF/origin or action guard denied; self-approval is `SELF_REVIEW_FORBIDDEN` |
| 404 | Unknown or inaccessible individual private resource |
| 409 | `VERSION_CONFLICT`, `STATE_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `SETUP_REQUIRED`, `INVITATION_UNAVAILABLE`, `SECRET_ALREADY_ISSUED` |
| 413/428 | Upload too large under configured limits / missing required `If-Match` |
| 410 | `EVIDENCE_EXPIRED`: authorized metadata/history survives, expired content is unavailable |
| 429/503 | Rate-limited (`Retry-After`) / temporary dependency or database outage; `EVIDENCE_TRANSITION` is retryable with `Retry-After` while a committed deletion reservation settles |

Mutable resource GETs return a strong `ETag` derived from the authoritative aggregate version. Commands editing/reviewing a versioned aggregate require `If-Match: "v7"` where declared; list items with an explicit authoritative `version` may supply that same header value. Revocations, read markers and one-time challenge consumption use their intrinsic state guards instead. The server compares under lock and returns 409 on a stale version; a reviewer must refetch and confirm the **actual immutable report/fact revision** reviewed. Return the updated ETag after commit. Multi-aggregate commands additionally validate all referenced fact versions; an ETag alone does not prove attendance or a qualification snapshot.

Domain creation/irreversible browser commands require a UUID-shaped `Idempotency-Key` where declared, scoped by actor or a private pre-auth nonce, route and target. Login/logout follow their session lifecycle guards. Atomically reserve the key and compare a server-computed keyed fingerprint of validated input; changed input is 409. Never persist plaintext passwords/codes/invitation secrets in the fingerprint/reply store. Concurrent requests return the same committed ordinary result or a durable pending operation; they do not apply a command twice. Persist domain uniqueness as well as the transport key. Retention/abuse bounds are configured/tested in VTC-013/015/023/039, not invented company limits here.

**One-show telemetry secrets are an exception to result replay:** issuance stores only a hash; exact retry cannot reconstruct the secret and returns `SECRET_ALREADY_ISSUED` plus the caller-owned token ID. If the first response was lost, revoke that token and issue another; do not mint a second token for the same key. Invitations are one-time **use**, not one-time display: administrators can copy a still-valid link from an encrypted-at-rest generation; redemption lookup uses a hash, and consumption/reissue removes encrypted material. Do not store those links in ordinary idempotency caches.

## Pagination, projections and notifications

Use bounded cursor/keyset pagination: default 25, maximum 100 as technical API limits, sorted `(createdAt,id)` descending unless the operation defines a chronological cursor. Opaque signed cursors bind actor, filter set, sort and visibility; they are not credentials and cannot bypass current authorization. Changing filters requires a fresh cursor. No offset pagination for a mutating notification feed.

Notification polling uses an ascending recipient-scoped durable sequence cursor, every 30 seconds while visible, paused hidden/offline and refreshed immediately on return. Return catch-up/history and current unread state without duplicating toasts. Recheck membership/session before every poll. Event/source timestamps determine live freshness; database delivery time does not turn old history into live activity. Approximate healthy 90-second delivery is measured later in VTC-021/036/037/040, not proven by early VTC-011 synthetic probes.

An initial poll without a cursor returns the latest bounded visible window in chronological order and a current non-null checkpoint, even when empty. Subsequent polls advance from that recipient-scoped checkpoint; bounded catch-up uses `hasMore`. Older history uses the separate descending `/notifications/history` cursor and never triggers toasts. Do not make a new login drain years of history before it can receive current activity.

Company start/finish activity carries only the safe actor nickname/game and transition message. It does not grant access to another member's pending report. `Notification.target` is null when the underlying trip is inaccessible, while private event/review notifications require their current recipient permissions and never include private reasons in display arguments. Members can therefore see the agreed live activity without fetching private trip evidence. Event RSVP uses its own `GET .../my-response` version/ETag; an event-detail ETag does not authorise overwriting a newer response.

Analytics/progress responses carry `computedAt`, `projectionVersion` and pending/stale indicators. Only accepted canonical trip contributions count. Telemetry periods use actual completion; undated manual periods use confirmation. If reporting timezone/configuration is missing, return setup-required with safe missing-setting codes. User display timezone never silently changes reporting boundaries.

Analytics includes day/month buckets for charts and a stable projection-bound leaderboard. Enforce a configured bounded date window and `fromDate < toDateExclusive`. Own status counts are separate; `activeTrips` and `correctionPending` overlap the decision partition and must not be added to produce a total. Public member progress excludes private correction-review flags; owner/admin projections expose them. Catalog publication validates both candidate ETag and `expectedPublicationVersion`; source mapping changes belong to a draft revision, never mutate published mappings.

Public company statistics (`getPublicCompanyStats`, VTC-052) is an anonymous closed aggregate for the landing: `activeMembers` (active memberships, all roles) and `currentMonth` for the current calendar month in the company reporting timezone. When a valid timezone is configured, `currentMonth.status = available` carries `month`, half-open `fromDate`/`toDateExclusive`, accepted canonical `acceptedTrips`, `actualDistanceM` (same tenth-metre arithmetic as the company analytics total) and the `games` with at least one accepted trip in that month (`ets2` before `ats`); an empty month returns real zeros. Without a valid timezone it is `unavailable` with reason `company_reporting_timezone`, never zeros; a missing company returns 409 `SETUP_REQUIRED`. The response contains no IDs, names, per-driver or per-game totals, pending/review counts or projection fields. It does not read or set cookies, uses the public read rate limit, accepts no query parameters and has no ETag; cached copies may repeat `meta.requestId` for up to 60 seconds.

Authenticated background import status uses `/operations/{id}` with creator **and current initiating capability** checks. Public invitation redemption is synchronous/atomic with a 201 safe result, not a password-bearing background job. Initial Steam linking returns a bound verification URL; VTC-018 owns the external signed-provider callback/state protocol outside this browser API. A generic callback may never directly assign a different user's identity.

Steam replacement read-back is separate from initial provider verification. `/me/identity.pendingReplacementId` discovers the latest pending request after reload; the owner can read its status. Director/deputy list/detail reads expose the target member, verified candidate profile, bound identity epoch, expiry and terminal state, never callback nonces/provider credentials. Only a fresh, verified, unexpired, unconsumed proof for that member's current epoch can be applied under the member ETag; the server obtains the candidate from the stored proof. Expiry, a newer identity epoch or consumption prevents replay, including after a browser reload.

Catalog administrators maintain six plain lists per game (DLCs, regions, cities, companies, cargo, trailer body types) and the depots that pair a company with a city. Edits apply immediately. Import is CSV or JSON: a dry-run reports per-line errors and returns a token for those exact bytes; apply revalidates and upserts all-or-nothing by `(game, code)` (depots by `(game, company_code, city_code)`) and never deletes. An empty optional cell keeps the current value, so import cannot clear a value.

## Protected email replacement

VTC-013 coordinates an additive identity refinement before account UI integration. Request `email_change` through `POST /me/credential-challenges` (`newEmail` maxLength254). Confirming its old-channel code through `POST /me/credential-changes` returns 202 with a pending challenge for a separately delivered proposed-address proof; 200 on that route remains password-change completion only. The old verified login address and sessions stay usable while pending. `GET /me/email-change` discovers only the caller's active stage, proposed target, ID and expiry, with explicit null when none is usable. Reissue through the same request endpoint with a fresh idempotency key replaces either stage.

`POST /me/email-change-confirmations` consumes only the proposed-address proof bound to the same actor, target and current security epochs. Only its committed 200 means the address was replaced and verified by that proof; it invalidates all sessions and requires sign-in again. Both stages expire after ten minutes and have bounded attempts. Wrong/expired/replaced/used proofs, same-current address and final uniqueness conflicts return generic 401 without address-availability hints. Exact retries preserve committed safe results, subject to current-session authorization; a failed required delivery/event transaction leaves the old channel intact. There is no admin or unverified-session repair bypass. See the [identity implementation contract](../../development/identity.md) for rollout and missing-adapter gates.

## Safe mail delivery evidence

VTC-014 adds GET /mail-deliveries/{deliveryId} and bodyless POST /mail-deliveries/{deliveryId}/resends. Status contains safe identifiers, kind, state, version, attempts, timestamps and fixed recovery category only, with ETag/no-store. Security IDs equal the owning challenge ID; admissions receives its delivery ID from the producer port. Only the current account owner can inspect/retry security mail; applications.manage applies to admissions and never authorizes serving-director code access. Inaccessible resources return 404. Resend requires exact Origin, signed session CSRF, If-Match and actor-scoped UUID Idempotency-Key, rechecks current authority/state under transaction locks and accepts no recipient/payload/expiry override. It reopens only known rejected requests within original expiry/attempt/idempotency bounds. Accepted/simulated/ambiguous/obsolete mail cannot be generically resent. VTC-015 installs the admissions producer; frontend account/admin UI remains separate. See [mail operations](../../operations/email.md).

Mail reserves same-origin /password-reset?token=... and /invitation?token=... entry URLs for the VTC-017 UI flows. The current package renders links but supplies no redemption page. That UI owner must consume tokens through the reviewed POST contracts, remove secrets from browser history/referrers and avoid URL/body logging; a GET link never mutates account state.

## Implemented admissions contract

VTC-015 implements the explicit admissions routes and adds `GET /admin/applications/{applicationId}/history`, returning the same bounded application page for retained applications sharing the normalized email. Optional Discord/introduction may be omitted or null and are normalized to null in staff DTOs. Application decisions expose immutable reviewer/time/version/outcome/reason metadata and safe delivery ID. Invitation status exposes current safe mail state and delivery ID, with `not_requested` when no email has been requested for this generation (including disabled mail) and currently absent adapter `unavailable`; `accepted`/`simulated` never claim inbox delivery. The transport's leading RU `Accept-Language` range selects Russian mail, otherwise English.

Public submission receipts are scoped to the signed private pre-auth/session binding and deliberately differ from staff application IDs, preventing duplicate/existing-identity disclosure. All staff operations require current Director/Deputy authority; copy is bodyless POST with CSRF/If-Match/no-store. Reissue returns a new generation ID and invalidates the old link. Exact-key decision replay reconstructs the original response from immutable facts plus retained original version/invitation metadata; reissue replays its original ordinary metadata. Redemption synchronously creates the account/member/selected-game initial assignments and returns a safe 201 without a session. See [the implementation and activation guide](../../development/admissions.md) for validation, seven-day boundaries, disabled/failed mail, strict replay/rate bounds, lock order and remaining UI/Steam/full-qualification gates.

Admissions staff rate admission authenticates and checks current `applications.manage` before charging a per-user read/command allowance; anonymous and unauthorized requests cannot consume it. Handler authorization remains independently current. Public submission/redemption retain separate bounded source/global abuse guards before parsing or credential work, with eight-byte keyed source identities and serialized bounded allocation. Per-source denial never charges the aggregate allowance. Rate state is persistent and bounded; these controls do not guarantee availability under aggregate abuse.

## Implemented catalog lists

Catalog errors: `CATALOG_ROW_NOT_FOUND` (404), `CATALOG_CODE_CONFLICT` (409), `CATALOG_PARENT_INVALID`, `CATALOG_FILE_INVALID`, `CATALOG_IMPORT_INVALID`, `CATALOG_SELECTION_HIDDEN` (422), `CATALOG_FILE_TOO_LARGE` (413), `CATALOG_IMPORT_TOKEN_REQUIRED` (428), `CATALOG_IMPORT_TOKEN_INVALID` (412).

VTC-084 replaces the versioned catalog routes. `GET /catalogs/{list}` pages rows ordered by display name for the requested locale, then `id`, with a signed keyset cursor bound to the session and filters. `code` is opaque and compared byte-exact; search escapes LIKE wildcards and matches names and code case-insensitively and ignoring accents, including the optional `nameNative` of cities. [Catalogs](../../development/catalogs.md) documents list columns, the import file format and the telemetry code rules per list.

VTC-091 adds `companies` to the plain lists and a separate depot route family. `CatalogItem.logo` is present only on companies and is `{version, byteLength}` or `null`; list queries never select image bytes. `GET /catalogs/depots?game&companyId&cityId&search&dlc&includeHidden&locale&limit&cursor` lists company-in-city depots: `companyId` returns that company's cities ordered by city name, otherwise rows are ordered by company name, then `id`, with the same signed cursor. A depot is listed by default only when the depot, its company and its city are all visible. `POST /admin/catalogs/depots` creates one (duplicate pair `CATALOG_CODE_CONFLICT`, hidden or other-game parents `CATALOG_PARENT_INVALID`); `PATCH` changes only its source or hidden flag. Depot imports use `/admin/catalogs/depots/import-previews` and `/imports` with `game,company_code,city_code,dlc_code`.

Company logos are PNG only, at most 32 KiB and 128x32 pixels, checked on the server and stored unchanged. `PUT` and `DELETE /admin/catalogs/companies/{id}/logo` change one logo; removing an absent logo is a no-op without an audit entry. `POST /admin/catalogs/companies/logo-previews?game=` dry-runs up to 500 files named `<company code>.png` (16 MiB): `line` is the file's position in the upload and issues use the field `file` (`bad_name`, `not_png`, `too_large`, `bad_dimensions`, `corrupt`, `duplicate_in_file`) or `code` (`unknown_reference`). `logo-imports` applies the same files with the token in `If-Match`, all or none. Each committed upload operation writes one audit entry. `GET /catalogs/companies/{id}/logo?v=<version>` needs `company.read` on every request, including a conditional one, and answers `image/png` with a strong `ETag`, `Vary: Cookie`, `nosniff` and `Cache-Control: private, max-age=86400` when `v` is the current version, otherwise `private, no-cache`; `If-None-Match` gets 304. A company without a logo answers 404 and the UI does not request it.

## Implemented qualification semantics

VTC-028 implements its existing routes behind explicit opt-in [configuration](../../development/qualifications.md). `QualificationRuleVersion.effectiveAt` is the historical selection instant, separate from `publishedAt`; omitted publication input `effectiveAt` means immediate server time, and supplied past/duplicate/backward effective instants fail. Historical-resolution assignments require explicit supported `assignedAt`/exclusive `endedAt`; other assignment purposes reject them. Unknown history/rules never fall back to the current level.

Progress reads the authoritative canonical contribution register synchronously and returns `projectionPending:false`; `projectionVersion` is the current assignment contribution revision. Command ETags represent the level or member/game command version. Promotion requires an effective published rule, a next level, meeting every non-null threshold, and explicit Director/Deputy confirmation. A published rule with both thresholds null has no minimum. Own/admin progress includes private `reviewRequired` and stable `reviewReasonCodes`; other-member DTOs omit both. Signed bounded keyset pages bind session/epoch/scope/game/member or level. VTC-029 mounts the trip-scoped assignment-review route when its explicit opt-in [configuration](../../development/trip-decisions.md#activation-migration-and-rollback) is enabled; default-off configuration and separate hosted activation remain unchanged.

## Events backend integration

VTC-034 implements the [Events API](../../development/events.md) with explicit public/member/participant/admin serializers and separate definition, own-RSVP and attendance-collection ETags. EventInput/EventPublic now require server, organizer, meeting location, route and canonical UTC meeting time alongside the existing start. Attendance writes contain 1–100 distinct members; private latest staff notes are admin-only. Field lengths and batch bounds are technical limits. VTC-035 owns rendered RU/EN workflows; VTC-029 owns adjudication and VTC-036 owns reminder effects. This backend integration does not activate hosted services. VTC-058A adds member reads for declined members' safe summaries (`listEventDecliners`, same `ListParticipant` shape and paging, never reasons) and closed `EventResponseCounts` with participating/declined totals only.

VTC-029 implements `EnvelopeTripProposalDecision` for `decideTripProposal`: terminal effective decisions retain the existing `EnvelopeDecision` response; rejection before any terminal effective decision returns the actual rejected `EnvelopeTripProposal` with its immutable `ProposalReview`. Clients distinguish closed `data.outcome` from `data.kind`/`data.state`, refresh the canonical trip using the current ETag, and never infer a rejected trip from a rejected proposal. `Decision` and direct `decideTrip` responses are unchanged apart from the VTC-059A additions below.

TripProposal optionally exposes nullable `eventAssociation` with immutable `eventId`, `eventRevisionId` and nullable `attendanceRevisionId`. Event association proposals capture these safe references through Events at creation; later definition/attendance changes do not rewrite proposal readback. Review must display the selected event and retained revisions, then use the current canonical ETag. Current support guards fence obsolete approval. No RSVP reasons or attendance notes are included. Older responses and fixtures without this additive field remain valid.

VTC-029 resolutions optionally carry nullable `correctionRequestId`, also exposed on TripProposal. Omitted and null inputs have the same command fingerprint. The exact pending request must belong to the current canonical group, and at least one actual supported correction field is required. Approval applies the linked resolution and records the request as `resolved` even when corrected facts prove a rejected trip; rejection records `declined`. The originating author proposal closes with its exact revision and the same staff disposition, reason and instant; that closure disposes of the request and does not apply null changes as separate facts. Only newly closed proposals emit safe proposal-reviewed references. Later rejection of another obsolete linked proposal preserves the first terminal request/history/origin review. Approval cannot reopen a handled request.

Obsolete proposals can be rejected using current authority, complete-group self-review checks, current canonical ETag and the exact proposal revision. Approval still requires matching base trip/fact and current support. Every remaining pending proposal, correction request or source review retains work and evidence holds after rejection, approval or a direct decision. Reviewer summaries, effective facts/history, pending proposal and ETag use current reads after owning locks, including transactions with an earlier Repeatable Read snapshot.

VTC-059A adds explicit over-limit acceptance. `Review.qualificationCheck` lists each historical rule with its outcome, reason, `bypassedByEvent`, decimal observed/limit mass and up to ten offending trailer/ADR entity IDs (unknown values are null). `Review.acceptance.mode` is `ordinary`, `over_limits` or `unavailable` with sorted `blockedReasonCodes`. Only proven mass, trailer and ADR breaches can be waived, and only on a delivered manual-only group with known facts, resolved history, no event review and no event exception (`telemetry_source_present`, `event_exception_applied` and every other gap block it). Optional `DecisionInput.confirmOverLimits` must be `true` exactly when the mode is `over_limits`: a missing, false or stale flag returns 409 `STATE_CONFLICT` (internally `RESOLUTION_REQUIRED`) without effects; re-read `Review.acceptance`; the flag with `reject` or a non-null `proposalId` returns 422. An absent or false flag keeps the earlier receipt fingerprint. The resulting `Decision` has `acceptedOverLimits: true`, reason codes listing the exceeded limits plus `accepted_over_limits`, and a second `report.accepted_over_limits` audit entry. Every `Decision` now also carries the required nullable `reviewer` summary (null for system decisions). `listTrips` adds `hold` and `order` (default `desc`) for `scope=review` only (422 otherwise); both bind the signed cursor, and review items carry the `review` block with hold, reasons, queue time and the current manual revision number/time.

VTC-054 adds the optional `listTrips` `source` query filter (`ets2telemetry` or `manual`, the `TripSummary.sourceKinds` vocabulary) for every scope. A trip matches when its canonical group (root and merged members) has a source of that kind: mixed trips match both values and trips without sources match neither. The server applies it with each scope's visibility rules before keyset paging. When set it is bound into the signed cursor, so replaying a cursor with another or no source returns 409 `VERSION_CONFLICT`; other values return 422 `INVALID_PAYLOAD`. Omitting it keeps the previous behavior and cursor binding.
