# Hostland questions awaiting provider confirmation

**Status:** prepared, unsent. This public draft contains no account identifiers, private tariff, hostnames or credentials. The owner can submit it privately to support; no provider communication is authorized or performed by preparing this file.

We are evaluating a small Node.js/TypeScript application on an existing shared-hosting account, with approximately 10–30 members and a project budget near USD 35/year. We need to keep existing websites and databases unchanged while testing a separate application and empty database.

1. Is maintained **MySQL 8.4 LTS** available on this account without a tariff increase or moving/modifying existing databases? Public hosting/news pages list 8.4, but availability in the current control panel is not yet established. If an account/server move is necessary, what changes, downtime, cost and recovery steps would it entail? Do not perform a move or upgrade based on this inquiry.
2. What MySQL patch/security-update policy applies? If only 8.0 is available, what support/security-fix basis exists after the upstream April 2026 EOL, and what is the supported path to a maintained release?
3. How can this account run an up-to-date **Node.js 24** patch under Passenger and cron? Does the panel list represent the installed runtime or just installation templates? Can a maintained custom Node.js binary be selected per isolated app, and who updates it?
4. Which Passenger version/configuration serves Node.js? Are Fastify's ordinary single HTTP server/startup and Hostland's `server.js`/restart-marker flow supported? What are idle recycling, startup, shutdown, process-count, memory and open-file limits? Do published generic script limits apply to the long-lived Passenger process?
5. Can a Node.js CLI script run **once per minute** from cron even when no one visits the website? Please confirm its CPU/wall-time/memory/file-descriptor limits, scheduling jitter, overlap behavior and whether specific network/command restrictions apply.
6. Are **SSE responses** streamed without proxy buffering? What are response/idle timeouts, permitted heartbeat settings, concurrent HTTP connection limits, and available per-site controls? If not supported, ordinary short authenticated polling will be considered.
7. What connection count, database size, packet size, transaction/DDL/migration privileges, collations and backup limits apply to a new InnoDB/utf8mb4 database? Is MySQL access from Node.js supported with the current authentication plugin, and which verified TLS/transport options are required?
8. Is SSH/SFTP/SCP usable noninteractively from GitHub-hosted Linux runners, with a scoped deployment credential and pinned host key? Are stable application-root loaders, symlinks/atomic renames and private files outside the public document root supported? Do not create credentials or widen access for this inquiry.
9. Can a separate temporary test subdomain/application and empty database be added without changing existing sites or incurring extra charges? How are subdomains/application slots counted? Is a free valid TLS certificate available for that isolated hostname?
10. Can the application perform outbound HTTPS requests to email and identity APIs with normal certificate verification? If SMTP is used instead, what authentication/rate restrictions apply? We do not need real messages sent during the runtime proof.
11. Please clarify the actual file/database backup cadence, retained restore points, exclusions and maximum sizes. The public hosting feature page and backup guide describe different schedules. Can data be exported and restored into an isolated target without overwriting existing services, and what costs apply?
12. What is the **full annual renewal total**, including mandatory domain, TLS, runtime/database/site slots and any required storage/backup add-ons? Account-specific amounts should be returned privately, not posted to the public project repository. No purchase or plan change is authorized by these questions.

Record answers as verified/unsupported/unknown with the observation date. Keep raw replies/account details private; publish only a sanitized compatibility conclusion and approved architecture decisions. A provider statement complements, but does not replace, the isolated application/database proof.
